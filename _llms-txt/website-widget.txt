# Channels

> Connect a website, phone number or messaging account to a published agent release, then update or roll back the release it serves.

A channel is how customers reach an agent. Each channel has one entry point, such as a website widget or a phone number, and serves one published release of one agent. Publishing a new release does not change any channel: you choose when each channel moves to it. New conversations use the release the channel serves when they start. Conversations already in progress keep the release they started with, so updating or rolling back a channel never changes an open conversation. ## Channel types [Section titled “Channel types”](#channel-types) | Type | Console name | How customers reach the agent | | -------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------ | | Website widget | **Live chat widget** | A chat (and optional voice) widget on your website. See [Install the website widget](/channels/website-widget/install/). | | WhatsApp | **WhatsApp Business** | Messages to a connected WhatsApp Business number. | | Messenger | **Facebook Messenger** | Messages to a connected Facebook Page. | | Instagram | **Instagram** | Messages to a connected Instagram professional account. | | Phone | **Telephone** | Inbound calls to a Twilio or Telnyx number you connect. | For WhatsApp, Messenger, Instagram and phone, you first connect the provider account in the console under **Integrations** then **Communication channels**. Caplo verifies the account before you can choose it in a channel. Detailed setup guides for these channel types will be added to these docs later. ## Before you start [Section titled “Before you start”](#before-you-start) * Publish at least one release of the agent. Only agents with a published release can be chosen for a channel. See [Publish an agent](/agents/publishing/). * You need a workspace role that can configure channels: Owner, Admin or Builder. Other roles can view channels but not change them. See [Workspaces and roles](/concepts/workspaces-and-roles/). ## Create a channel [Section titled “Create a channel”](#create-a-channel) 1. In the console, open **Channels** under **Deploy**. 2. Select **Create channel** and choose the channel type. 3. Enter a **Channel name**, choose the **Agent** and the **Agent release** it should serve, then select **Set up connection**. 4. Complete the entry point details for the type. For a website widget, add the allowed website origins and a widget design. For a provider channel, choose the connected account and number, Page or profile. 5. Select **Create channel**. For a website widget, the console opens the entry point editor, where you configure the conversation and copy the embed code. See [Install the website widget](/channels/website-widget/install/). The channel page shows **What customers get**: the agent release, each entry point and its state, and **Launch checks**. Select **Review checks** to see which release, tool, knowledge or entry point settings still need attention. ## Deploy a new release [Section titled “Deploy a new release”](#deploy-a-new-release) When the agent has a newer release than the one a channel serves, the channel shows **Update available**. * Console 1. Open the channel in **Channels**. 2. Under **Agent release**, select **Update to** followed by the newest release. The dialog shows the release you serve now, the release after the update and its release note. 3. Confirm the update. New conversations start on the new release. To pick a specific release, or to point the channel at a different agent, select **Change release** (or **Edit channel**), choose the **Agent** and **Agent release**, then select **Save changes**. * CLI List your channels and the release each one serves: 
  ```sh
  caplo channel list
  caplo channel get "Website"
  ```
 Point a channel at its agent’s newest release that is not revoked: 
  ```sh
  caplo channel deploy "Website"
  ```
 Pick a release with `@` and a version or release number, or point the channel at another agent: 
  ```sh
  caplo channel deploy "Website" --agent "Shop Concierge@1.4.0"
  ```
 When two channels share a name, name the channel as `kind/name` (for example `website/Website` or `whatsapp/Support`) or use its ID. `deploy` asks for confirmation; add `--yes` in scripts. See [`caplo channel deploy`](/reference/cli/channel/#caplo-channel-deploy). ## Roll back [Section titled “Roll back”](#roll-back) * Console Open the channel, select **Change release**, choose the earlier **Agent release** and select **Save changes**. New conversations use that release from then on. * CLI Point a channel back at the newest release of its agent that is older than the one it serves and not revoked: 
  ```sh
  caplo channel rollback "Website"
  ```
 The release is served exactly as it was published. To move forward again, run `caplo channel deploy`. See [`caplo channel rollback`](/reference/cli/channel/#caplo-channel-rollback). ## Pause a channel [Section titled “Pause a channel”](#pause-a-channel) **Pause channel** stops new conversations on every entry point of the channel. Conversations in progress continue. Select **Resume channel** to accept new conversations again. A website widget channel can be deleted with **Delete**. WhatsApp, Messenger, Instagram and phone channels can be paused but not deleted from the console. ## Related [Section titled “Related”](#related) * [Channels concept](/concepts/channels/) * [Agents and releases](/concepts/agents-and-releases/) * [`caplo channel` reference](/reference/cli/channel/)

# Design the website widget

> Create a reusable widget design, set its brand, welcome screen, launcher and language, then publish a revision and apply it to your website channels.

A widget design controls how the website widget looks: colours, logo, fonts, welcome screen, launcher and layout. Designs are reusable. One design can serve several website channels, and each channel shows the design revision you apply to it. A design has a draft you edit and a history of published revisions. Websites never show a draft. They change only when you apply a published revision to a channel, so you can work on a design while the live widget stays the same. Who answers, which modes are offered and how visitors verify are not part of the design. Those are [entry point settings](/channels/website-widget/settings/). ## Create a design [Section titled “Create a design”](#create-a-design) 1. In the console, open **Widget designs** under **Deploy** and select **Create design**. 2. Enter a **Design name**. It is internal and only shown in the console; visitors see the widget title instead. 3. Choose a template to start from: **Standard**, **Concierge**, **Evergreen**, **Orbit**, **Help center** (an inline layout) or **Midnight** (dark). A template only seeds the first draft. 4. Select **Create design**. The design editor opens on the draft. You can also create a design while creating a website channel, with **Create a design here**. ## Design sections [Section titled “Design sections”](#design-sections) The editor groups settings into sections. The preview beside them updates as you edit. Select **Save draft** to keep your changes; **Discard** returns to the last saved draft. ### Brand and colours [Section titled “Brand and colours”](#brand-and-colours) * **Header**: the **Widget title** and **Subtitle** visitors see at the top of the widget. * **Colours**: pick from the **Brand palette** or set **Brand colour** and **Soft surface** yourself. * **Style**: **Colour mode** (Light or Dark) and **Corner radius (px)**. ### Logo and fonts [Section titled “Logo and fonts”](#logo-and-fonts) * **Logo**: PNG or WebP, at most 256 KiB and 16 to 1024 px per side. Shown in the header and welcome area. * **Assistant avatar**: PNG or WebP, at most 256 KiB. Shown beside assistant replies. * **Body font** and **Heading font**: **DM Sans**, **Manrope**, **Device system font** or **Uploaded font**. An uploaded font is a WOFF2 file of at most 512 KiB. Visitors see the device font if it cannot load. Each upload is kept as its own version, and published revisions keep the version they used. Open **Reuse an uploaded asset** to pick a logo, avatar or font you uploaded before. Withdrawing an asset version keeps it on revisions that already use it, but stops new drafts, publications and applies from using it. ### Welcome screen [Section titled “Welcome screen”](#welcome-screen) What visitors see before their first message: * **Welcome heading** and **Welcome description**. * **Suggested questions**: up to 4 shortcuts. Each has a **Suggestion label**, a **Suggestion description** and the **Message to send** when a visitor taps it. * **Message placeholder**: the hint text in the message box. The agent’s own greeting is set on the agent, not in the design. ### Launcher and layout [Section titled “Launcher and layout”](#launcher-and-layout) * **Display mode**: **Floating popup** opens from a launcher button in a corner of the page. **Inline container** renders inside an element on your page, with no launcher button. * **Width (px)** and **Height (px)** of the widget. * For a popup: **Corner** (Bottom right or Bottom left) and **Edge spacing (px)**. * **Launcher button**: **Launcher label** and **Launcher icon** (Message or Sparkles). * **Open automatically on desktop**, with an **Opening delay (seconds)** from 0 to 60. Caution Popup and inline need different embed code. If you change **Display mode** and apply the revision to a live channel, update the markup on your site at the same time. See [Install the website widget](/channels/website-widget/install/). ### Language [Section titled “Language”](#language) * **Locale**: for example `en-US`. This sets the language of the widget’s own labels and buttons. Translated labels need a supported language pack. * **Text direction**: **Left to right** or **Right to left**. The language the agent answers in is set on the agent, not here. ## Publish a revision [Section titled “Publish a revision”](#publish-a-revision) 1. Save your draft. Only the saved draft is published. 2. Open **Publish and install** and select **Publish revision** followed by the next revision number. 3. Review the comparison with the previous published revision, then select **Publish revision**. A published revision is immutable. Publishing does not change any website. ## Apply a revision to a website [Section titled “Apply a revision to a website”](#apply-a-revision-to-a-website) You can apply from the design or from the channel. Either way, the change takes effect right away; you do not need to save anything else. From the design: 1. Open **Publish and install**. **Live on websites** lists the channels that use this design and the revision each shows. 2. Choose the **Revision to apply** and select **Review and apply**. 3. Review the before and after, then confirm. From the channel: open the website entry point (**Configure & install**), and on the **General** tab under **Appearance**, choose the **Widget design** and **Revision**, then select **Apply revision**. Widgets that are already open keep their look until the visitor reloads the page. The widget ID and the embed code stay the same, except when the display mode changes between popup and inline. To roll a website back, apply an earlier revision. Select **Load older revisions** if the one you want is not listed. ## Archive a design [Section titled “Archive a design”](#archive-a-design) In **Design settings**, **Archive design** hides a design from the library and stops it being published or applied. It is available once no website uses the design. **Restore design** makes it available again. ## Related [Section titled “Related”](#related) * [Install the website widget](/channels/website-widget/install/) * [Website widget settings](/channels/website-widget/settings/) * [Present tool results](/tools/present-results/) for how rich results such as cards and tables appear in the widget

# Install the website widget

> Copy the widget embed code from the console and add it to a plain HTML site, a Next.js app or a React single page app.

The website widget is one script tag. It loads the widget from Caplo, shows the published design you applied to the channel, and connects visitors to the agent release the channel serves. ## Before you start [Section titled “Before you start”](#before-you-start) * Create a website channel (**Live chat widget**) for a published agent. See [Channels](/channels/). * Publish a widget design and apply a revision to the channel. The console only gives you embed code once a design is applied, because the code depends on whether the design is a popup or an inline container. See [Design the widget](/channels/website-widget/design/). * Know the exact origin of every site that will show the widget, for example `https://www.example.com`. ## Get the embed code [Section titled “Get the embed code”](#get-the-embed-code) 1. In **Channels**, open the website channel and select **Configure & install** on its website entry point. 2. On the **General** tab, check **Allowed website origin**. Add every origin that will show the widget, then select **Save entry point**. 3. Open the **Install** tab and select **Copy embed code**. If **Copy embed code** is disabled, the hint next to it says why: no design is applied, there are unsaved edits, the entry point is disabled, or the channel is paused. The **Widget ID** on the Install tab is a public identifier. The snippet contains no credentials, and you never need to add any. ## The embed code [Section titled “The embed code”](#the-embed-code) A popup design (a launcher button in a corner of the page): 
```html
<script
  src="https://api.caplo.si/v1/messaging/widget/loader.js"
  data-widget-id="<WIDGET_ID>"
  async
></script>
```
 An inline design (the conversation sits inside an element on your page) adds a container and points the script at it: 
```html
<div id="caplo-<WIDGET_ID>"></div>
<script
  src="https://api.caplo.si/v1/messaging/widget/loader.js"
  data-widget-id="<WIDGET_ID>"
  data-container="#caplo-<WIDGET_ID>"
  async
></script>
```
 Always copy the code from the console rather than typing it: the console escapes the container selector when the widget ID contains a dot. | Attribute | Required | What it does | | ------------------ | ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | | `src` | Yes | The widget loader. Load it from Caplo; a self-hosted copy cannot reach the widget service. | | `data-widget-id` | Yes | The widget ID from the Install tab. | | `data-container` | Inline designs | A CSS selector for the element the widget renders into. The element must exist on the page when the loader runs. | | `data-persistence` | No | By default the widget restores the visitor’s conversation after a reload in the same browser tab. Set `data-persistence="none"` to start fresh on every page load. | | `nonce` | When your CSP uses nonces | Add your page’s nonce. The widget applies it to the styles it adds. | | `async` | Recommended | Loads the widget without blocking your page. | The widget ID stays the same when you apply a new design revision, so you do not need to change your site when the appearance changes. Switching a design between popup and inline is the exception: inline needs the container element and `data-container`. ## Allowed origins [Section titled “Allowed origins”](#allowed-origins) The widget only works on the origins listed on the entry point. * List exact origins: scheme and host, plus the port if it is not the default. No paths and no wildcards. * `https://example.com` and `https://www.example.com` are different origins. List both if you use both. * Use HTTPS. HTTP is accepted only for `localhost`, `127.0.0.1` and `.localhost` hosts, which is useful for local development. * You can list up to 10 origins per entry point. On any other site, including a staging host you have not listed, the widget shows a **Chat unavailable · Try again** button instead of the chat. Removing an origin closes open conversations on that site. ## Add it to your site [Section titled “Add it to your site”](#add-it-to-your-site) * HTML Paste the code just before the closing `</body>` tag on every page that should show the widget. For an inline design, place the `<div>` where the conversation should appear and keep the script after it. 
  ```html
      <!-- your page content -->
      <script
        src="https://api.caplo.si/v1/messaging/widget/loader.js"
        data-widget-id="<WIDGET_ID>"
        async
      ></script>
    </body>
  </html>
  ```
 * Next.js (App Router) For a popup design, load the script once in the root layout with `next/script`. It stays on the page across client-side navigation. app/layout.tsx 
  ```tsx
  import Script from 'next/script';


  export default function RootLayout({ children }: { children: React.ReactNode }) {
    return (
      <html lang="en">
        <body>
          {children}
          <Script
            src="https://api.caplo.si/v1/messaging/widget/loader.js"
            data-widget-id="<WIDGET_ID>"
            strategy="afterInteractive"
          />
        </body>
      </html>
    );
  }
  ```
 For an inline design shown on one route, use the client component from the React tab instead of `next/script`. `next/script` loads a given script only once per page session, so the widget would not come back after a visitor navigates away and returns. If your site sets a Content Security Policy with a nonce, pass it to `<Script nonce={nonce} />`. * React SPA For a popup design, add the embed code to your `index.html`, before `</body>`. The widget stays mounted while your router changes pages. For an inline design, render the container and add the loader from an effect: 
  ```tsx
  import { useEffect } from 'react';


  const LOADER = 'https://api.caplo.si/v1/messaging/widget/loader.js';


  export function CaploInlineWidget({ widgetId }: { widgetId: string }) {
    const containerId = `caplo-${widgetId}`;
    useEffect(() => {
      const script = document.createElement('script');
      script.src = LOADER;
      script.async = true;
      script.dataset.widgetId = widgetId;
      script.dataset.container = `#${CSS.escape(containerId)}`;
      document.body.append(script);
      return () => script.remove();
    }, [widgetId, containerId]);
    return <div id={containerId} />;
  }
  ```
 When the container leaves the page, the widget unmounts itself. Mounting the component again adds a new script, and the widget renders into the new container. Loading the same widget ID twice on one page is harmless: the second script does nothing. ## Content Security Policy [Section titled “Content Security Policy”](#content-security-policy) If your site sends a `Content-Security-Policy` header, add these sources to the matching directives and keep your existing sources: 
```text
script-src https://api.caplo.si;
connect-src https://api.caplo.si;
font-src https://api.caplo.si;
img-src blob:;
worker-src blob:;
```
 The console shows the same list under **Content Security Policy additions** on the Install tab. Brand logos and avatars render from `blob:` URLs, and map results start a worker from a `blob:` URL. If the channel allows voice, the browser also connects to Caplo’s media server for the call. Add it to `connect-src`: 
```text
connect-src https://api.caplo.si wss://livekit.caplo.si;
```
 Caplo never changes your site’s policy. See [Troubleshoot the website widget](/channels/website-widget/troubleshooting/) for how CSP errors show up. ## Single page apps [Section titled “Single page apps”](#single-page-apps) * The loader runs once per script element. Calling it again with the same widget ID on the same page does nothing until the widget is unmounted. * A popup widget stays mounted across client-side route changes. To remove it on some routes, call `unmount()` from the [JavaScript API](/channels/website-widget/javascript-api/); add the script again to bring it back. * An inline widget unmounts itself when its container is removed from the page. * On a full page unload the widget closes its connection. With the default persistence, the conversation resumes when the visitor returns in the same tab. ## Check the installation [Section titled “Check the installation”](#check-the-installation) 1. Open a page on an allowed origin. The launcher appears in the corner you chose, or the conversation appears in its container. 2. Send a message and check that the agent replies. The conversation appears in **Conversations** in the console. 3. If you see **Chat unavailable · Try again**, or nothing, see [Troubleshoot the website widget](/channels/website-widget/troubleshooting/). # Website widget JavaScript API

> Control the website widget from your page with window.CaploWidget, sign visitors in from your own site, and listen to widget events.

The widget loader adds a small API to your page so your own code can open the widget, pass hints about the visitor, sign the visitor in, and react to widget events. Everything here runs in the visitor’s browser; nothing on this page needs a Caplo credential. ## Get the widget control [Section titled “Get the widget control”](#get-the-widget-control) 
```js
const chat = window.CaploWidget.get('<WIDGET_ID>');
```
 `window.CaploWidget` exists once the loader script has run. `get(id)` returns the control for that widget ID, or `undefined` if no widget with that ID is loaded on the page. `window.CaploWidget.protocolVersion` is `2`. The control is available as soon as the loader runs, before the widget has finished loading. Calls you make early are kept and applied when the widget mounts, so you do not need to wait for `caplo:mounted` to call `open()` or `setVisitorHints()`. Because the loader script is `async`, run your code after it loads: 
```js
function withCaplo(widgetId, callback) {
  const chat = window.CaploWidget?.get(widgetId);
  if (chat) return callback(chat);
  const script = document.querySelector(`script[data-widget-id="${widgetId}"]`);
  script?.addEventListener('load', () => callback(window.CaploWidget.get(widgetId)), { once: true });
}
```
 ## Methods [Section titled “Methods”](#methods) | Method | What it does | | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | | `open()` | Opens the popup widget. If the widget is still loading, it opens when it mounts. | | `close()` | Closes the popup widget. | | `setVisitorHints(hints)` | Passes unverified hints about the visitor to the conversation. Pass `null` to clear them. | | `unmount()` | Removes the widget from the page and closes its connection. To show it again, add the loader script again. | | `identity.configure({ getToken, when })` | Registers your page as a sign-in provider. See [Sign visitors in from your page](#sign-visitors-in-from-your-page). | | `identity.refresh()` | Tells the widget your page’s signed-in user changed. Returns a promise. | | `identity.signOut()` | Tells the widget your page signed its user out. Returns a promise. | | `addEventListener(type, listener)` and `removeEventListener(type, listener)` | Listen to `caplo:identity` and `caplo:identity-signout-requested`. | ### Open the widget from your own button [Section titled “Open the widget from your own button”](#open-the-widget-from-your-own-button) 
```js
withCaplo('<WIDGET_ID>', (chat) => {
  document.querySelector('#help-button').addEventListener('click', () => chat.open());
});
```
 ### Visitor hints [Section titled “Visitor hints”](#visitor-hints) Hints give the agent context it would otherwise have to ask for. They are never treated as identity: a visitor’s name in a hint does not let tools act on that person’s account. 
```js
chat.setVisitorHints({
  name: 'Ada',
  locale: 'en-GB',
  page: window.location.href,
});
```
 | Field | Rules | | -------- | ------------------------------------------------------------------------------- | | `name` | 1 to 80 characters, no control characters. | | `locale` | A BCP 47 language tag, such as `en-GB` or `fr`, up to 35 characters. | | `page` | An `http` or `https` URL without a user name or password, up to 512 characters. | Other fields are ignored. A value that breaks these rules throws a `TypeError`; if you set it before the widget has loaded, the widget fails to load and shows **Chat unavailable · Try again**. Check values before you pass them, and leave a field out rather than sending an empty string. Each call replaces the previous hints. Hints travel with the visitor’s messages, so call `setVisitorHints` again when the page changes in a single page app. ## Sign visitors in from your page [Section titled “Sign visitors in from your page”](#sign-visitors-in-from-your-page) If visitors are already signed in to your site, your page can sign them in to the widget too. This uses a **Host sign-in** connection that you set up under **Settings** then **Customer identity**, with these settings on the website entry point: * **Customer verification** allows verified visitors, and the host sign-in connection is one of the **Sign-in methods**. * **Consent mode** is **Show a notice after verification**. With the agreement mode, host sign-in does not run automatically. Your backend signs a short-lived assertion for the signed-in user; the browser never holds your signing key. See [Website widget settings](/channels/website-widget/settings/#customer-verification). 
```js
chat.identity.configure({
  when: 'open',
  getToken: async ({ nonce, requirement }) => {
    const response = await fetch('/support/caplo-token', {
      method: 'POST',
      headers: { 'content-type': 'application/json' },
      body: JSON.stringify({ nonce, requirement }),
    });
    return response.status === 200 ? response.text() : null;
  },
});
```
 `getToken` receives: | Field | Meaning | | ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `nonce` | A one-time value your backend must put in the assertion. | | `requirement` | `null`, or the level the conversation needs: `level` (`low`, `standard` or `high`), optionally `maxAuthAgeSeconds`, and for a confirmation of a specific action, `action` with an `id`, `summary` and `digest`. | Return the signed assertion as a string, or `null` when nobody is signed in on your page. The widget waits up to 30 seconds for an ordinary sign-in and up to 5 minutes when a specific action needs confirmation. `when` decides when the widget asks for a token: | `when` | The widget signs the visitor in | | ---------------- | ----------------------------------------------------------- | | `open` (default) | When the widget opens, or when the visitor sends a message. | | `first-message` | When the visitor sends their first message. | | `required` | Only when the channel or an action requires verification. | Call `identity.refresh()` after your user signs in or switches account, and `identity.signOut()` after they sign out. Both return promises. Caution Never put assertions in URLs, logs or browser storage. Treat them like passwords: each one proves who the visitor is. ## Events [Section titled “Events”](#events) The loader dispatches two events on its `<script>` element. They bubble, so you can listen on `document`: | Event | When | `event.detail` | | --------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | | `caplo:mounted` | The widget has loaded and rendered. | `{ installationId, bundleId, designId, revision }`: the widget ID, the widget release, and the design and revision shown. | | `caplo:error` | The widget could not load, so the page shows a **Chat unavailable · Try again** button instead. | `{ installationId, code }`, with `code` `"presentation-unavailable"`. | Listen to identity events on the control: | Event | When | `event.detail` | | ---------------------------------- | ---------------------------------------------------------------------- | ---------------------------- | | `caplo:identity` | The visitor’s verification state changed. | `{ state, level?, reason? }` | | `caplo:identity-signout-requested` | A visitor signed in through your page chose to sign out in the widget. | `{}` | `state` is `anonymous`, `verified`, `reauthenticate` (the visitor must verify again) or `ended` (the verified conversation ended). `level` is present when `state` is `verified`. `reason` explains the change when there is one, for example `signed_in`, `stepped_up`, `signed_out` or `host_signed_out`. 
```js
document.addEventListener('caplo:error', (event) => {
  console.warn('Caplo widget unavailable', event.detail);
});


chat.addEventListener('caplo:identity', (event) => {
  console.log('Visitor is now', event.detail.state);
});


chat.addEventListener('caplo:identity-signout-requested', async () => {
  await signOutOfMySite();
  await chat.identity.signOut();
});
```
 The widget also dispatches `caplo:open` and `caplo:close` (no detail) on its own element when a visitor opens or closes the popup. They bubble to `document`. # Website widget settings

> Configure a website entry point's allowed origins, text and voice modes, customer verification and visitor file uploads.

Entry point settings decide where the widget may run and how visitors talk to the agent. They are separate from the [widget design](/channels/website-widget/design/), which only controls appearance. To open them, go to **Channels**, open the website channel and select **Configure & install**. Settings are on the **General** and **Conversation** tabs. Select **Save entry point** to apply your changes; **Discard** drops them. Saving keeps the same widget ID, so your embed code does not change. You need the Owner, Admin or Builder role to change these settings. ## General [Section titled “General”](#general) | Setting | What it does | | ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | **Entry point name** | Shown in the console only. | | **Allowed website origin** | The exact origins that may show the widget, up to 10. Use HTTPS, or HTTP on `localhost`, `127.0.0.1` or a `.localhost` host. Select **Add origin** for more. See [Allowed origins](/channels/website-widget/install/#allowed-origins). | | **Enable this website entry point** | Turn off to stop the widget accepting new conversations without deleting the channel. | | **Remove entry point** | Deletes this website channel and its installation. The agent and the widget design are kept. | The **Appearance** card on the same tab is where you apply a published design revision. Applying takes effect immediately and is not part of **Save entry point**. ## Text and voice [Section titled “Text and voice”](#text-and-voice) The widget supports text chat and, optionally, voice conversations in the browser. Voice is off for a new website channel unless you selected **Allow voice conversations** when creating it. To turn it on later: 1. On the channel page, select **Edit channel**. 2. Select **Allow website voice**, then **Save changes**. 3. In the entry point’s **Conversation** tab, set **Conversation modes** to **Text + voice** and select **Save entry point**. | Conversation mode | Visitors can | | ----------------- | ------------------------------------------------------------------------------------------------------------------- | | **Text only** | Chat by text. | | **Text + voice** | Chat by text and start a voice conversation from the widget. The browser asks for microphone access the first time. | Turning **Allow website voice** off switches every website entry point of the channel back to text only. ### Voice engine and turn-taking [Section titled “Voice engine and turn-taking”](#voice-engine-and-turn-taking) A website voice conversation uses the voice settings of the agent release the channel serves: voice language, speech recognition model, voice, optional realtime model, and timing such as **Start replies early**. If the agent has no voice settings, Caplo uses its default English speech recognition and voice, and no setup is needed. You change these on the agent, under **Advanced settings** then **Voice** in its configuration, and they reach the website after you publish a release and update the channel. See [Voice and speech](/providers/voice-and-speech/). ## Conversation actions [Section titled “Conversation actions”](#conversation-actions) **Conversation actions** lists the actions this entry point allows, such as **Transfer to a human**. An action is available only when the agent release also allows it. For a transfer, choose the **Transfer destination** from your handoff destinations. See [Handoff and end actions](/agents/handoff-and-end-actions/). ## Customer verification [Section titled “Customer verification”](#customer-verification) Customer verification lets visitors prove who they are, so the agent’s tools can act on their own account. You set up the verification methods themselves as connections under **Settings** then **Customer identity**: **Host sign-in** (your website’s backend signs a short assertion for a visitor it already knows), **Provider sign-in** (your OpenID Connect provider in a popup) or **Verification code** (a one-time code sent to the visitor’s email or phone on file). On the entry point you choose which of them this website offers. | **Customer verification** | Behavior | | ---------------------------------------- | --------------------------------------------------------------------- | | **Anonymous visitors only** | No verification is offered. | | **Visitors may verify who they are** | Visitors can chat anonymously and verify when they or a tool need it. | | **Visitors must verify before chatting** | Visitors verify before the agent answers. | When verification is allowed, select **Choose sign-in methods and consent for this channel** to set: * **Sign-in methods**: up to 4 connections, in the order the widget offers them, each with an optional button label. Host sign-in (your own page passing a signed token) runs on its own when your page registers a token provider with the [JavaScript API](/channels/website-widget/javascript-api/#sign-visitors-in-from-your-page). * **Consent mode**: **Ask for agreement before the first verification**, or **Show a notice after verification**. Host sign-in only runs automatically with the notice mode. * **Consent version** and **Consent text**: the text visitors agree to, in English and any translations you add. Change the version whenever the text changes; visitors agree to a specific version. * **Previous conversation**: **Never show earlier conversations**, or **Show the most recent one after verification**. If the agent’s tools declare verified operations, **Verified tool operations** lets you raise the verification level an operation needs, require recent authentication, and send your API a customer context token. See [Customer-aware tools](/tools/customer-aware-tools/). ## Visitor files during handoff [Section titled “Visitor files during handoff”](#visitor-files-during-handoff) While a person from your team handles the conversation, visitors can attach files for them. The agent never sees these files, and each file is checked for type and malware. Select **Let visitors send files during a handoff**, then choose: * **Accepted files**: **Images (JPEG, PNG, GIF, WebP)** and **PDF documents**. Both are selected by default. * **Largest file**: 1 MB, 5 MB (the default) or 10 MB. ## Related [Section titled “Related”](#related) * [Install the website widget](/channels/website-widget/install/) * [JavaScript API](/channels/website-widget/javascript-api/) * [Conversations and handoff](/concepts/conversations-and-handoff/)

# Troubleshoot the website widget

> Find out why the website widget does not appear, shows Chat unavailable, is blocked by a Content Security Policy, or cannot use the microphone.

Start with the browser’s developer tools on the page that should show the widget. The **Console** shows script and Content Security Policy errors, and the **Network** tab shows the widget’s requests to `api.caplo.si`. ## See why the widget failed [Section titled “See why the widget failed”](#see-why-the-widget-failed) When the widget cannot load, the loader replaces it with a **Chat unavailable · Try again** button in the bottom right corner and dispatches a `caplo:error` event. Log it to confirm which widget failed: 
```js
document.addEventListener('caplo:error', (event) => {
  console.warn('Caplo widget unavailable', event.detail);
});
```
 `event.detail` is `{ installationId, code: "presentation-unavailable" }`. For the reason, look in the **Network** tab for the `POST` request to `/v1/messaging/widget/presentation`. Its response title says what is wrong: | Response | Meaning | Fix | | -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- | | 403 **Origin denied** | The page’s origin is not an allowed origin of the entry point. | Add the exact origin. See [below](#origin-not-allowed). | | 409 **Publish and apply a widget design before installing it** | No design revision is applied to the channel. | Publish a design revision and apply it. See [Design the widget](/channels/website-widget/design/). | | 503 **The selected widget release is unavailable** | The applied revision was built for a widget release that is no longer offered. | Publish a new revision of the design and apply it. | | Another status with **Widget presentation is unavailable** | The entry point is disabled, the channel is paused or deleted, the widget ID is unknown, or the service was briefly unavailable. | Check the channel and entry point in the console, then select **Try again**. | ## The widget does not appear at all [Section titled “The widget does not appear at all”](#the-widget-does-not-appear-at-all) * **The script is missing or never ran.** Check that the page source contains the loader script and that the **Network** tab shows `loader.js` loading with status 200. * **The widget ID is wrong.** The loader silently does nothing when `data-widget-id` is missing or malformed. Copy the code again from the **Install** tab. * **An inline container is missing.** For an inline design, the element named in `data-container` must exist when the loader runs. Otherwise the widget fails to load. Put the container before the script, or add the script after your app renders the container. * **The design changed between popup and inline.** If you applied a revision with a different **Display mode**, update the embed code. A popup snippet does not render an inline design. * **It is still loading.** The loader waits up to 12 seconds for the widget’s settings and 20 seconds for the widget itself before it shows **Chat unavailable**. ## Origin not allowed [Section titled “Origin not allowed”](#origin-not-allowed) The widget works only on the exact origins listed on the website entry point, under **General** then **Allowed website origin**. * Scheme, host and port must match exactly. `https://example.com` does not cover `https://www.example.com` or `https://shop.example.com`. * Paths and wildcards are not allowed. Enter `https://example.com`, not `https://example.com/support`. * HTTP only works for `localhost`, `127.0.0.1` and `.localhost` hosts. ## The widget is unavailable on other hosts [Section titled “The widget is unavailable on other hosts”](#the-widget-is-unavailable-on-other-hosts) A staging, preview or test site is a different origin. Either add it as an allowed origin (up to 10 per entry point) or, to keep test traffic separate, create a second website channel for your test hosts and use its widget ID there. ## Content Security Policy errors [Section titled “Content Security Policy errors”](#content-security-policy-errors) If your site sends a `Content-Security-Policy`, the browser console shows messages such as “Refused to load the script” or “Refused to connect”. Add the sources the widget needs and keep your existing ones: 
```text
script-src https://api.caplo.si;
connect-src https://api.caplo.si;
font-src https://api.caplo.si;
img-src blob:;
worker-src blob:;
```
 * A missing `script-src` stops the widget loading. * A missing `connect-src` shows **Chat unavailable**, or the widget opens but cannot send messages. * A missing `font-src` falls back to the device font. A missing `img-src blob:` hides your logo and avatar. A missing `worker-src blob:` stops map results rendering. * For voice, also allow `wss://livekit.caplo.si` in `connect-src`. * If your policy uses nonces, add `nonce="<NONCE>"` to the loader script tag. The widget applies the same nonce to its styles. The **Install** tab shows these sources under **Content Security Policy additions**. ## Voice does not start [Section titled “Voice does not start”](#voice-does-not-start) * **No voice button.** The channel must allow website voice, and the entry point’s **Conversation modes** must be **Text + voice**. See [Website widget settings](/channels/website-widget/settings/#text-and-voice). * **“Microphone access is unavailable. Check your browser permissions and audio device.”** The visitor blocked the microphone, or the browser has no input device. The visitor needs to allow microphone access for your site in the browser’s site settings and try again. * **Embedded in an iframe.** If your page shows the widget inside an iframe, the iframe needs `allow="microphone"`. * **“Voice is busy or unavailable. Please try again shortly.”** The call could not start. Try again; if it keeps happening, check the agent’s voice settings and that its speech providers are on under **Integrations** then **Service providers**. See [Voice and speech](/providers/voice-and-speech/). * **“Enable audio playback”** appears when the browser blocked sound until the visitor interacts with the page. The visitor selects it to hear the agent. ## Still stuck [Section titled “Still stuck”](#still-stuck) Collect the widget ID, the page URL, the `caplo:error` detail and the failing request from the **Network** tab, then [contact support](/resources/support/).
