# Channels

> Connect a website, phone number or messaging account to a published agent release, then update or roll back the release it serves.

A channel is how customers reach an agent. Each channel has one entry point, such as a website widget or a phone number, and serves one published release of one agent. Publishing a new release does not change any channel: you choose when each channel moves to it. New conversations use the release the channel serves when they start. Conversations already in progress keep the release they started with, so updating or rolling back a channel never changes an open conversation. ## Channel types [Section titled “Channel types”](#channel-types) | Type | Console name | How customers reach the agent | | -------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------ | | Website widget | **Live chat widget** | A chat (and optional voice) widget on your website. See [Install the website widget](/channels/website-widget/install/). | | WhatsApp | **WhatsApp Business** | Messages to a connected WhatsApp Business number. | | Messenger | **Facebook Messenger** | Messages to a connected Facebook Page. | | Instagram | **Instagram** | Messages to a connected Instagram professional account. | | Phone | **Telephone** | Inbound calls to a Twilio or Telnyx number you connect. | For WhatsApp, Messenger, Instagram and phone, you first connect the provider account in the console under **Integrations** then **Communication channels**. Caplo verifies the account before you can choose it in a channel. Setup guides: [WhatsApp](/channels/whatsapp/), [Messenger and Instagram](/channels/messenger-and-instagram/) and [phone](/channels/phone/). To have your team answer in Chatwoot, see [Hand off to Chatwoot](/channels/handoff-to-chatwoot/). ## Before you start [Section titled “Before you start”](#before-you-start) * Publish at least one release of the agent. Only agents with a published release can be chosen for a channel. See [Publish an agent](/agents/publishing/). * You need a workspace role that can configure channels: Owner, Admin or Builder. Other roles can view channels but not change them. See [Workspaces and roles](/concepts/workspaces-and-roles/). ## Create a channel [Section titled “Create a channel”](#create-a-channel) ![The channel types offered by Create channel](/_astro/create-channel.BaxZzUD__yIqxJ.webp) 1. In the console, open **Channels** under **Deploy**. 2. Select **Create channel** and choose the channel type. 3. Enter a **Channel name**, choose the **Agent** and the **Agent release** it should serve, then select **Set up connection**. 4. Complete the entry point details for the type. For a website widget, add the allowed website origins and a widget design. For a provider channel, choose the connected account and number, Page or profile. 5. Select **Create channel**. For a website widget, the console opens the entry point editor, where you configure the conversation and copy the embed code. See [Install the website widget](/channels/website-widget/install/). The channel page shows **What customers get**: the agent release, each entry point and its state, and **Launch checks**. Select **Review checks** to see which release, tool, knowledge or entry point settings still need attention. ![A channel page showing the agent release, the website entry point and launch checks](/_astro/channel-capabilities.Y9R8VBoN_ZFKS4N.webp) ## Deploy a new release [Section titled “Deploy a new release”](#deploy-a-new-release) When the agent has a newer release than the one a channel serves, the channel shows **Update available**. * Console 1. Open the channel in **Channels**. 2. Under **Agent release**, select **Update to** followed by the newest release. The dialog shows the release you serve now, the release after the update and its release note. 3. Confirm the update. New conversations start on the new release. To pick a specific release, or to point the channel at a different agent, select **Change release** (or **Edit channel**), choose the **Agent** and **Agent release**, then select **Save changes**. * CLI List your channels and the release each one serves: 
  ```plaintext
  caplo channel list
  caplo channel get "Website"
  ```
 Point a channel at its agent’s newest release that is not revoked: 
  ```plaintext
  caplo channel deploy "Website"
  ```
 Pick a release with `@` and a version or release number, or point the channel at another agent: 
  ```plaintext
  caplo channel deploy "Website" --agent "Shop Concierge@1.4.0"
  ```
 When two channels share a name, name the channel as `kind/name` (for example `website/Website` or `whatsapp/Support`) or use its ID. `deploy` asks for confirmation; add `--yes` in scripts. See [`caplo channel deploy`](/reference/cli/channel/#caplo-channel-deploy). ## Roll back [Section titled “Roll back”](#roll-back) * Console Open the channel, select **Change release**, choose the earlier **Agent release** and select **Save changes**. New conversations use that release from then on. * CLI Point a channel back at the newest release of its agent that is older than the one it serves and not revoked: 
  ```plaintext
  caplo channel rollback "Website"
  ```
 The release is served exactly as it was published. To move forward again, run `caplo channel deploy`. See [`caplo channel rollback`](/reference/cli/channel/#caplo-channel-rollback). ## Pause a channel [Section titled “Pause a channel”](#pause-a-channel) **Pause channel** stops new conversations on every entry point of the channel. Conversations in progress continue. Select **Resume channel** to accept new conversations again. A website widget channel can be deleted with **Delete**. WhatsApp, Messenger, Instagram and phone channels can be paused but not deleted from the console. ## Related [Section titled “Related”](#related) * [Channels concept](/concepts/channels/) * [Agents and releases](/concepts/agents-and-releases/) * [`caplo channel` reference](/reference/cli/channel/)

# Hand off to Chatwoot

> Connect a Chatwoot API inbox so your team receives agent handoffs from the website widget and can follow and take over WhatsApp, Messenger and Instagram conversations.

Chatwoot is a customer support inbox. Connecting it lets your team answer customers from Chatwoot while Caplo keeps the conversation on the channel the customer started on. A Chatwoot destination does one of two jobs: | Job | Channels | What happens | | ------------------------- | ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- | | **Agent handoff** | Website widget | When the agent hands a chat to a person, Caplo opens a conversation in the Chatwoot inbox and relays messages both ways until your team resolves it. | | **Provider inbox mirror** | WhatsApp, Messenger, Instagram | Every new conversation on these channels appears in the Chatwoot inbox as it happens. Your team can read along and take over at any time by replying. | Phone channels transfer calls to a phone number or SIP address instead; see [Hand off to a person or end a call](/agents/handoff-and-end-actions/). Each job needs its own Chatwoot API inbox. A destination with mirroring on cannot receive agent handoffs, and a destination that an entry point uses for handoffs cannot mirror. ## Before you start [Section titled “Before you start”](#before-you-start) In Chatwoot (Chatwoot Cloud or your own installation): * Create an **API** channel inbox for each job you want. Only API inboxes are accepted. * Note the **account ID** and the **inbox ID**. Both are numbers, shown in the Chatwoot address bar when you open the account and the inbox settings. * Copy the **access token** from the profile settings of a Chatwoot administrator. An administrator token lets Caplo configure Chatwoot’s webhooks and read their signing secrets for you. * For mirroring, use a Chatwoot account dedicated to this Caplo workspace. Caplo refuses to mirror two workspaces into the same Chatwoot account. In Caplo, you need a role that can manage integrations: Owner, Admin or Developer. ## Add the destination [Section titled “Add the destination”](#add-the-destination) 1. In the console, open **Integrations** then **Handoff destinations**, and select **Add destination**. 2. Enter a **Destination name** and keep **Destination type** set to **Chatwoot**. 3. Fill in the Chatwoot details: | Field | Value | | ---------------------- | -------------------------------------------------------------------------------------------------------------- | | **Chatwoot URL** | The address of your Chatwoot, for example `https://chat.example.com`. | | **Account ID** | The Chatwoot account ID. | | **API inbox ID** | The ID of the API inbox for this job. | | **Assignee ID** | Optional. A Chatwoot agent ID to assign every handoff to. Leave blank to use the inbox’s own assignment rules. | | **API access token** | The administrator access token. Caplo stores it encrypted and never shows it again. | | **Caplo callback URL** | Leave the default, `https://api.caplo.si`. Caplo builds the webhook addresses Chatwoot calls from it. | 4. To mirror WhatsApp, Messenger and Instagram conversations into this inbox, check **Mirror provider conversations into this inbox**. Leave it unchecked for an agent handoff inbox. 5. Select **Save and verify**. Verification uses the token to confirm the inbox is an API inbox, creates or updates a Chatwoot account webhook named “Caplo handoff”, points the inbox’s webhook at Caplo, and stores the signing secrets Chatwoot reports. Caplo accepts only callbacks signed with those secrets. When it succeeds, the destination shows **Ready**. The **Edit** dialog then shows the **Account webhook** and **API inbox webhook** addresses. If the token cannot read the webhook secrets, the destination shows **Needs attention** with “Chatwoot did not reveal the webhook secrets to this token; enter them from Chatwoot.” Copy the secrets from the account webhook and the API inbox settings in Chatwoot into **Account webhook secret** and **API inbox webhook secret**, then save again. Any later edit returns the destination to unverified until it is verified again; use **Verify** to check it at any time. ![A Chatwoot handoff destination on the Handoff destinations page](/_astro/handoff-destinations.C4oCtRt1_Z1SyYkw.webp) ## Use it for agent handoffs [Section titled “Use it for agent handoffs”](#use-it-for-agent-handoffs) An agent hands off only when both the agent and the website entry point allow it: 1. Allow the **Transfer to a human** action on the agent and publish a release. See [Hand off to a person or end a call](/agents/handoff-and-end-actions/). 2. In **Channels**, open the website channel, select **Configure & install** on its entry point and open the **Conversation** tab. 3. Under **Conversation actions**, check **Transfer to a human** and choose the destination under **Transfer destination**. Save the entry point. When the agent hands off, Caplo opens a conversation in the inbox, assigns it if you set an **Assignee ID**, and adds one private note: “Caplo handoff” with the handoff ID, the reason the agent gave, and the conversation so far (up to the last 20 messages and 4,000 characters, each line quoted). The note is never shown to the customer; treat the quoted text as information from the customer, not instructions. The first public reply from a Chatwoot agent accepts the handoff. It must come within 3 minutes, otherwise the customer is told nobody is available and the agent carries on. Files the customer sends during the handoff are scanned and attached in Chatwoot, up to 10 MiB each. ## Use it as a provider inbox mirror [Section titled “Use it as a provider inbox mirror”](#use-it-as-a-provider-inbox-mirror) With **Mirror provider conversations into this inbox** on, a workspace has one mirror inbox for all its WhatsApp, Messenger and Instagram channels. Mirroring starts with new messages from the moment you turn it on; earlier conversations are not copied. * Each customer becomes a Chatwoot contact, and each Caplo conversation a Chatwoot conversation. Customer messages appear as incoming messages. * Agent replies appear once Meta has accepted them. A reply that failed or whose outcome is unknown is not shown as sent. * A public reply in Chatwoot takes the conversation over: the agent stops replying and your reply is sent to the customer on the original channel. * Resolving the Chatwoot conversation hands it back to the agent. Turning mirroring off stops new conversations from appearing and stops new takeovers from Chatwoot. Conversations already mirrored keep syncing until they end. ## Reply and hand back from Chatwoot [Section titled “Reply and hand back from Chatwoot”](#reply-and-hand-back-from-chatwoot) | In Chatwoot | Effect | | ------------ | ---------------------------------------------------------------------------------------------------------------------------- | | Public reply | Sent to the customer as text, up to 4,000 characters. The first one accepts a handoff or takes over a mirrored conversation. | | Private note | Stays in Chatwoot. Never sent and never takes over. | | Attachment | Not sent. If the reply also has text, the text is sent and a private note says the attachments were not. | | Resolve | Hands the conversation back to the agent. | Reopen a resolved conversation before replying again. A reply Caplo cannot send is never lost silently: Caplo adds a private note under it explaining why, for example “Reopen this conversation in Chatwoot before replying. This message was not sent to the customer.” or “This reply is longer than 4,000 characters, so it was not sent to the customer.” On WhatsApp, Messenger and Instagram the 24-hour customer service window still applies. A reply after it has closed is refused with a private note. On WhatsApp, send an approved template from the Caplo console instead; see [Connect WhatsApp](/channels/whatsapp/#message-templates). ## What customers see [Section titled “What customers see”](#what-customers-see) On the website widget, during an agent handoff: 1. When the agent hands off: “I’ve asked a member of our team to join. They’ll reply here as soon as they can.” 2. If nobody replies within 3 minutes: “No one from our team is available right now, so I’ll keep helping here.” 3. When your team resolves the conversation: “Our team has finished here. I’m back to help with anything else.” On WhatsApp, Messenger and Instagram, customers get no notice when someone takes over or hands back. Your team’s replies arrive from the same number, Page or account as the agent’s. In the Caplo console, a conversation that Chatwoot holds shows **External inbox** in [Conversations](/operate/conversations-inbox/), with **Waiting to be accepted** or **Transfer accepted**. Your team cannot take it over or send a WhatsApp template from the console until it is handed back. ## Troubleshooting [Section titled “Troubleshooting”](#troubleshooting) | Problem | What to do | | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | | “The inbox is not a Chatwoot API inbox.” | Create an API channel inbox in Chatwoot and use its ID. | | “Chatwoot could not be reached with these settings: …” | Check the **Chatwoot URL**, that Chatwoot is reachable from the internet, and that the token belongs to that account. | | “This destination is assigned to a transfer entry point.” | You tried to turn on mirroring for an inbox used by agent handoffs. Use a separate API inbox for the mirror. | | The destination is missing from **Transfer destination** | Mirroring is on for it. Mirror inboxes cannot receive agent handoffs. | | The agent’s handoff ends with “No one from our team is available right now” | Nobody replied publicly within 3 minutes. Set an **Assignee ID** or adjust the inbox’s assignment and notifications in Chatwoot. | | Replies from Chatwoot do not reach the customer | Look for Caplo’s private note under the reply. Check that the conversation is open, the reply has text, and the customer’s 24-hour window is open. | | An item appears under **Provider inbox review** | Caplo wrote to Chatwoot but has no confirmation that Chatwoot received it. Caplo does not resend it automatically, to avoid duplicates; it keeps checking for a matching receipt. Select **Refresh review list** to see the current state. | ## Related [Section titled “Related”](#related) * [Hand off to a person or end a call](/agents/handoff-and-end-actions/) * [Conversations and handoff](/concepts/conversations-and-handoff/) * [Conversations inbox](/operate/conversations-inbox/) * [Connect WhatsApp](/channels/whatsapp/) * [Connect Messenger and Instagram](/channels/messenger-and-instagram/)

# Connect Messenger and Instagram

> Connect a Facebook Page or an Instagram professional account through Meta, serve an agent release on it, and understand the messaging window and what customers see.

A Messenger channel answers messages sent to one of your Facebook Pages. An Instagram channel answers direct messages sent to one of your Instagram professional accounts. Both work the same way: you authorize the account with Meta once under **Integrations**, then create a channel that serves a published agent release on it. ## Before you start [Section titled “Before you start”](#before-you-start) * **Messenger**: a Facebook Page, and a Facebook account that can manage it. * **Instagram**: an Instagram professional account (business or creator) that belongs to a Meta business portfolio, and a Facebook or Instagram login that can manage it. * A workspace role that can manage integrations (Owner, Admin or Developer) to connect the account, and one that can configure channels (Owner, Admin or Builder) to create the channel. * A published agent release. See [Publish an agent](/agents/publishing/). * A browser that allows popups from the console, because Meta’s authorization opens in a popup. ## Connect the account [Section titled “Connect the account”](#connect-the-account) 1. In the console, open **Integrations** then **Communication channels**. 2. Select **Add integration**, then **Facebook Messenger** or **Instagram**. 3. Enter an **Integration name** and select **Prepare Meta connection**. A setup row appears with the status **Awaiting authorization**. 4. Select **Continue with Meta** and authorize in the popup: * **Messenger**: sign in with Facebook and grant access to the Page. * **Instagram**: sign in with Instagram or Facebook (Meta Unified Login), then choose the business portfolio and the professional account. When Meta returns, the popup says “Authorization returned to your original Caplo window.” You can close it. 5. Back in the console, the row shows **Choose account**. Pick the **Facebook Page** or **Instagram professional account** and select **Connect selected account**. 6. Caplo checks the access Meta granted, subscribes the Page or account to Caplo’s webhooks, and reads the subscription back to confirm it. The connection then shows **Connected**. Meta asks you to grant these permissions. Caplo checks each of them and refuses the connection when one is missing: | Channel | Permissions | | --------- | ------------------------------------------------------------- | | Messenger | `pages_show_list`, `pages_manage_metadata`, `pages_messaging` | | Instagram | `instagram_basic`, `instagram_manage_messages` | If the account list is empty (“No eligible accounts were granted”), select **Cancel setup**, start again, and select the Page or account in Meta’s popup. A Page or Instagram account can be connected to one Caplo workspace at a time. ## Create the channel [Section titled “Create the channel”](#create-the-channel) 1. Open **Channels** under **Deploy**, select **Create channel** and choose **Facebook Messenger** or **Instagram**. 2. Enter a **Channel name**, choose the **Agent** and **Agent release**, then select **Set up connection**. 3. Choose the connection, then the **Facebook Page** or **Instagram professional account**. Only verified accounts that no other channel uses can be selected. Select **Continue**. 4. Choose **Who answers**: **AI agent** (the agent answers every customer) or **Your team** (the agent stays silent, also in open conversations, and messages wait in **Conversations** for your team). 5. Set the **Conversation inactivity timeout (seconds)**, from 300 to 604800. The default is 86400, one day. 6. Select **Create channel**, then send a message to the Page or account from another Facebook or Instagram account to test it. A channel keeps its Page or account; create another channel for a different one. Update the release it serves as described in [Channels](/channels/#deploy-a-new-release). You can pause these channels but not delete them. Customers on Messenger and Instagram are not signed in, so tools that need a [verified customer](/tools/customer-aware-tools/) do not run there, and customer memory is off. A conversation lasts at most seven days, whatever the inactivity timeout. ## The 24-hour messaging window [Section titled “The 24-hour messaging window”](#the-24-hour-messaging-window) Meta allows a business to reply for 24 hours after the customer’s last message. Caplo follows that rule for the agent and for your team: * The agent replies only within 24 hours of the customer’s message. A message that reaches Caplo late, for example after a Meta outage, is recorded without a reply. * Your team’s replies from the console or from Chatwoot are refused once the window has closed. The customer must write again to reopen it. * Confirmation buttons work only while the window is open. Caplo does not send message tags or other messages outside the window on Messenger or Instagram. If you need to reach a customer later, ask them to write to you. ## What is supported [Section titled “What is supported”](#what-is-supported) | | Messenger and Instagram | | -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | Customer messages | Text, taps on Caplo’s buttons and carousels, and your Page’s Get Started button, persistent menu, ice breakers and quick replies (the agent receives their visible text). | | Attachments from customers | Not supported. A message with only an image or file reaches the agent as a placeholder such as “\[image, file]”; text sent with an attachment is kept. | | Long messages | A customer message over 4,000 characters reaches the agent shortened and marked “\[message shortened]”. Long agent replies are split into several messages: over 2,000 characters on Messenger and 1,000 bytes on Instagram. | | Suggested replies | Up to three reply buttons of up to 20 characters, when the reply is 640 characters or shorter. See [Replies and feedback](/agents/replies-and-feedback/). | | Tool results | Cards become a carousel. Choices become reply buttons when three or fewer fit, otherwise a carousel. A detail with reply actions becomes a one-card carousel. Other results are sent as short numbered text. See [Present results](/tools/present-results/). | | Confirmations | A message with the details, “Confirm to approve these details, or Cancel.”, and **Confirm** and **Cancel** buttons. A confirmation that does not fit in 640 characters, or that needs editing, is not offered; the customer is told it cannot be confirmed here. See [Write tools](/tools/write-tools/). | | Handoff | No transfer destination: the agent cannot hand off on its own. Your team takes over from **Conversations**, or from Chatwoot when you mirror these channels there. See [Hand off to Chatwoot](/channels/handoff-to-chatwoot/). | | Sending rate | One message a second per Page or account. Replies queue behind each other in order. | ## Check the connection [Section titled “Check the connection”](#check-the-connection) Select **Check connection** on the account under **Integrations**. The **Deliveries** tab lists outgoing messages with their status and Meta’s reason for a failure. **Check delivery evidence** looks for Meta’s receipt; **Retry delivery** is offered only when the earlier attempt is proven not to have been accepted. Caplo never resends a message whose outcome is unknown. **Disconnect** stops new messages and replies for every channel that uses the account and releases the Page or account, so it can be connected again later or to another workspace. Existing conversations are kept. **Reconnect** restores it. ## Troubleshooting [Section titled “Troubleshooting”](#troubleshooting) | Problem | What to do | | ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | | “Allow popups for this console, then continue with Meta again.” | Allow popups for `app.caplo.si`, then select **Continue with Meta**. | | “This authorization window is no longer connected to Caplo.” | The console tab that started setup was closed or reloaded. Close the popup and select **Continue with Meta** in the original tab. | | “Meta did not grant the account access required for messaging.” | A permission in the table above was not granted. Start again and accept all requested permissions. | | Connection shows **Reconnect required** or **Authorization expired** | Meta access was revoked or expired, or a permission was removed. Select **Reconnect**. | | Connection shows **Needs attention** | Caplo could not complete a check, often because Meta was briefly unavailable. It keeps sending and checks again. If it stays, select **Check connection**. | | Instagram messages never arrive | In the Instagram app, allow connected tools to access messages (in the account’s message settings), and check that the account is a professional account. | | Delivery failed with a reason ending in `2018278`, `2018065` or `2534022` | The 24-hour window had closed. Wait for the customer to write again. | | Delivery failed with a reason ending in `2018108` or `1545041` | The person no longer receives messages from the Page or is unavailable. | | The agent does not answer | Check that the channel is not paused, **Who answers** is **AI agent**, and the customer wrote within the last 24 hours. | ## Related [Section titled “Related”](#related) * [Channels](/channels/) * [Connect WhatsApp](/channels/whatsapp/) * [Hand off to Chatwoot](/channels/handoff-to-chatwoot/) * [Conversations inbox](/operate/conversations-inbox/)

# Phone calls

> Answer calls to your own Twilio or Telnyx number with an agent, transfer callers to your team, and know what callers hear, what it costs and how to fix common problems.

A phone channel lets customers call an agent. You bring a phone number from your own Twilio or Telnyx account and point it at Caplo. When someone calls, your carrier sends the call to Caplo over SIP, and the agent release the channel serves answers it. Phone channels take **inbound calls only**. Caplo does not buy numbers in your carrier account, place outbound calls to customers, or change your carrier account beyond what you configure yourself. On Standard, Pro and Enterprise you can instead buy a Caplo phone number in the console, with no carrier account; see [Phone numbers](/billing/how-billing-works/#phone-numbers). ## How a call reaches your agent [Section titled “How a call reaches your agent”](#how-a-call-reaches-your-agent) 1. A caller dials your Twilio or Telnyx number. 2. Your carrier sends the call over SIP to the address Caplo shows for your account (a Twilio Elastic SIP trunk or a Telnyx FQDN connection). 3. Caplo checks that the number is connected to an active phone channel in your workspace, then starts a conversation on the release that channel serves. 4. The agent speaks its greeting, listens, and answers by voice until the call ends or is transferred. Each call is one conversation. It appears under **Monitor** then **Conversations** with the channel’s name, so you can read the transcript. See [Conversations inbox](/operate/conversations-inbox/). ## Before you start [Section titled “Before you start”](#before-you-start) * **Phone channels are enabled per workspace.** If the **Twilio** or **Telnyx** tab under **Integrations** then **Communication channels** shows an error, or connecting an account fails, ask [Caplo support](/resources/support/) to enable phone numbers for your workspace. * A Twilio or Telnyx account with at least one voice-capable phone number. Your carrier bills you for the number and the call minutes. * A published agent release. See [Publish an agent](/agents/publishing/). * A role that can manage integrations (Owner, Admin or Developer) to connect the carrier account, and one that can configure channels (Owner, Admin or Builder) to create the channel. ## Choose Twilio or Telnyx [Section titled “Choose Twilio or Telnyx”](#choose-twilio-or-telnyx) Both carriers work the same way once connected. Pick the one where your numbers already are. | | Twilio | Telnyx | | ------------------------------ | ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------- | | What you connect | Account SID, an API key and the account’s Auth Token | An API v2 key and the account’s public key | | Where calls are routed | An Elastic SIP trunk with Caplo’s origination URI | An FQDN SIP connection to Caplo’s SIP host, with credentials Caplo gives you | | Account limits | US1 region accounts only | None specific to Caplo | | Number checks | When you connect, rotate credentials or select **Refresh account and numbers** | Automatically about once an hour, and when you refresh | | Extra setup for warm transfers | A termination SIP URI and a credential list on the trunk | The connection must be allowed to place outbound calls | Setup guides: [Connect a Twilio number](/channels/phone/twilio/) and [Connect a Telnyx number](/channels/phone/telnyx/). ## Set up a phone channel [Section titled “Set up a phone channel”](#set-up-a-phone-channel) 1. **Connect your carrier account** in **Integrations** then **Communication channels**, and route your number to Caplo as the carrier guide describes. When **Connection details** lists the number as **Eligible for binding**, it is ready. 2. **Create the channel.** In **Channels** (under **Deploy**), select **Create channel** and choose **Telephone**. Enter a **Channel name**, choose the **Agent** and **Agent release**, then select **Set up connection**. 3. On **Phone connection**, choose the **Voice provider** (Twilio or Telnyx), the connected account, and the **Phone number**. Only verified numbers that no other channel uses can be chosen. Select **Continue**. 4. On **Conversation**, optionally set **Transfer calls to** and **Transfer type** (see [Transfer calls to a person](#transfer-calls-to-a-person)), then select **Create channel**. 5. Caplo creates the number’s route. Under **Number routes** in the SIP connection panel, the number shows **Provisioning** and then **Ready**, usually within a minute. 6. **Call the number.** You should hear the agent’s greeting. Check the call in **Monitor** then **Conversations**. Discovering a number does not prove that audio works both ways, so always make a real test call before you give the number to customers. The provider and the number are fixed once the channel exists. To have a different agent answer the same number, change the channel’s release or agent instead. ### Change the release a number serves [Section titled “Change the release a number serves”](#change-the-release-a-number-serves) * Console Open the channel in **Channels** and select **Update to** the newest release, or **Change release** to pick any release or another agent. New calls use the new release; calls in progress keep theirs. See [Channels](/channels/). * CLI Phone channels are named `twilio/<name>` or `telnyx/<name>`: 
  ```plaintext
  caplo channel list
  caplo channel deploy "twilio/Support line"
  caplo channel deploy "telnyx/Support line" --agent "Support Desk@1.4.0"
  caplo channel rollback "twilio/Support line"
  ```
 See [`caplo channel deploy`](/reference/cli/channel/#caplo-channel-deploy). To change transfer settings later, open the channel and select **Configure** on its phone entry point. ## Voice settings for phone calls [Section titled “Voice settings for phone calls”](#voice-settings-for-phone-calls) How the agent listens and speaks is set on the agent, under **Advanced settings** then **Voice**, so it is the same on the phone and in the website widget. [Voice and speech](/providers/voice-and-speech/) explains every setting. On the phone, these matter most: * **Voice language** and **Speech recognition**: callers are understood only in the agent’s voice language. Test with real phone audio, which is lower quality than a browser microphone. * **Greeting**: the caller hears the agent’s greeting as soon as the call connects. Keep it short. * **Fixed lines**: the transfer, transfer failed, time limit and silence lines are what callers hear at those moments. The **Continue in chat line** never plays on a phone call. * **Silence check after** and **End call after**: with the defaults, a silent caller hears “Are you still there?” after 15 seconds and the call ends 10 seconds later. * **Typing sound while working**: plays a soft typing sound while the agent looks something up, so the caller does not hear dead air. * **Start replies early** and a **Realtime model** make replies start sooner. Callers can interrupt the agent at any time. The agent stops speaking, and its next reply knows how much of the interrupted answer the caller actually heard. To let the agent hang up when the caller is done, allow the **End call** action on the agent. See [Hand off to a person or end a call](/agents/handoff-and-end-actions/). Voice changes reach callers after you publish a release and update the channel to it. ## Transfer calls to a person [Section titled “Transfer calls to a person”](#transfer-calls-to-a-person) A phone channel can send callers to your team when the agent hands off. It needs both: * The agent allows the **Transfer to a human** action in a published release, and its instructions say when to use it. See [Hand off to a person or end a call](/agents/handoff-and-end-actions/). * The channel’s **Transfer calls to** field holds a phone number in international format (for example `+15550100142`) or a `sip:` or `sips:` URI, up to 256 characters. Without a **Transfer calls to** target, the call stays with the agent. Phone calls cannot be taken over from the console. Choose the **Transfer type**: | | Cold | Warm | | ---------------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | | Target | Phone number or SIP URI | Phone number only | | What the caller hears | The transfer line, then ringing at your team’s number | The transfer line, then hold music | | What your team hears | A normal incoming call | A briefing with the agent’s reason for the transfer and the caller’s number, then “Press 1 to take the call” | | When the caller is connected | As soon as your team answers | When the person presses 1 | | How it works | Your carrier transfers the call (SIP REFER) | Caplo calls the person through your carrier, then joins them to the caller | The destination rings for up to 30 seconds. For a warm transfer, the briefing plays at most twice, with 10 seconds after each to press 1, and the whole transfer must connect within 150 seconds. Edit the briefing with the **Warm transfer briefing** line in the agent’s voice settings; `{reason}` and `{caller}` are filled in for you. If nobody answers, the person declines, or the carrier refuses the transfer, the caller hears the **Transfer failed line** and the agent carries on. A call can attempt at most two warm transfers. Your carrier must allow transfers on the number. See the carrier guide for the settings: [Twilio](/channels/phone/twilio/#transfers) or [Telnyx](/channels/phone/telnyx/#transfers). ## Maximum call duration [Section titled “Maximum call duration”](#maximum-call-duration) Every call has a time limit, set for the whole workspace in **Settings** then **Data & privacy** under **Voice calls**. It is 60 minutes unless you change it, and you can set 5 to 240 minutes. Owners and Admins can change it. See [Data and privacy](/operate/data-and-privacy/). * One minute before the limit, the caller hears the **Time limit warning line**. * At the limit, the caller hears the **Time limit goodbye line** and the call ends. A transfer already in progress finishes first. * A change applies to calls that start after it. After a warm transfer connects, the conversation between the caller and your team is no longer timed by this setting, but no phone call can last longer than about four hours. ## What callers hear when something goes wrong [Section titled “What callers hear when something goes wrong”](#what-callers-hear-when-something-goes-wrong) | Situation | What the caller hears | | --------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- | | The number has no phone channel, or its route is not **Ready** | Caplo does not answer; the caller gets your carrier’s failed-call treatment. | | The channel is paused, the carrier integration is disabled, the release was revoked, or Caplo is at its call capacity | The call is disconnected without a message. | | A Twilio number has not been checked for 24 hours | The call is disconnected without a message. Select **Refresh account and numbers**. | | A reply cannot be produced right now | The **Unavailable line**, then the agent keeps listening. | | A reply fails | The **Error line**, then the agent keeps listening. | | A speech provider refuses your own key | The call ends. Check the key under **Integrations** then **Service providers**. | | The caller stays silent | The **Silence check line**, then the **Silence goodbye line**, and the call ends. | Fixed lines left empty use the platform’s wording, shown as placeholders in the agent’s voice settings. ## Costs [Section titled “Costs”](#costs) A phone call is billed in two places: * **Caplo** charges **Voice minutes** for connected call time, billed by the second, plus speech recognition, spoken characters and model tokens for providers set to **Caplo Managed**. See [How your bill works](/billing/how-billing-works/) and [what affects the cost of a call](/providers/voice-and-speech/#what-affects-cost). * **Your carrier** bills your Twilio or Telnyx account directly for the number, the inbound call minutes, and any transferred calls. A warm transfer places an outbound call from your account, and the caller’s inbound call stays open while they talk to your team. On a Caplo phone number there is no carrier bill: incoming calls have no network charge, and the number’s own fee is in [Phone numbers](/billing/how-billing-works/#phone-numbers). Shorter silence timings, a lower maximum call duration and short spoken replies all reduce the cost of a call. ## Limits [Section titled “Limits”](#limits) | Limit | Value | | ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | Call direction | Inbound only. Caplo never calls customers. | | Numbers per channel | One. A number can serve only one channel, and the provider and number cannot be changed after the channel is created. | | Simultaneous calls | Your plan’s **Phone calls at once**: 1 on the Free trial, 3 on Standard and 10 on Pro, which can add more. A call over that limit is turned away as busy. Platform capacity is also limited, and a call that arrives when no capacity is free is disconnected. See [Plans](/billing/). | | Call length | 5 to 240 minutes, set per workspace; 60 by default, and never longer than your plan’s longest call. | | Write tools | The caller confirms each change by saying yes or no. Writes that need a verified customer cannot run, because callers are anonymous. | | Caller identity | Callers are anonymous. The caller’s number is not treated as a verified customer. | | Transfer target | One per channel. Warm transfers need a phone number; at most two warm transfer attempts per call. | | Deleting | Phone channels can be paused but not deleted. | Before a write tool runs, the caller hears the change and says yes or no. For a tool with a [`presentation`](/tools/present-results/#confirmation-and-receipt), Caplo reads its title and each field aloud, then asks the caller to say yes to continue or no to cancel. Without one, the caller hears only “Before I go ahead, please confirm this request. Say yes to continue or no to cancel.”, so the agent has to say what will change. See [Write tools](/tools/write-tools/). ## Pause or stop answering a number [Section titled “Pause or stop answering a number”](#pause-or-stop-answering-a-number) Select **Pause channel** on the channel. Caplo then disconnects new calls to the number; calls in progress continue. **Resume channel** takes calls again. To send the number’s calls somewhere else entirely, route it away from Caplo in your carrier account. See [Remove a Twilio number](/channels/phone/twilio/#remove-a-number) or [Remove a Telnyx number](/channels/phone/telnyx/#remove-a-number). ## Troubleshooting [Section titled “Troubleshooting”](#troubleshooting) **The call does not connect, or the caller hears a carrier error.** * In **Integrations**, open the account’s **Connection details**. The number should be **Eligible for binding**, and under **Number routes** it should be **Ready**. A blocker next to the number says what to fix. * Check that the account is enabled and the channel is not paused. * Check the SIP settings in your carrier account against **Connection details**. Copy the values again rather than typing them. * For Twilio, select **Refresh account and numbers**: a Twilio number not checked for 24 hours stops taking calls. **The call connects and then hangs up straight away.** The channel may be paused, the release revoked, or another call may be using your workspace’s call capacity. Try again once other calls have ended. If your speech providers use your own keys, check that the keys still work. **The caller hears nothing, or the agent does not hear the caller.** This is usually a media setting at the carrier. For Telnyx, enable SRTP and the PCMU (G.711 μ-law) codec on the connection. For Twilio, check the trunk has not been changed since you connected it, then select **Refresh account and numbers**. If the greeting plays but the agent never answers, check that the caller speaks the agent’s **Voice language**. **Transfers fail.** The caller hears the transfer failed line when the target does not answer within 30 seconds, the person does not press 1, or the carrier refuses the transfer. Check: * The agent’s published release allows **Transfer to a human**, and the channel has **Transfer calls to** set. * The target number is in international format and can take calls from your carrier. * Your carrier allows transfers on this number. For Twilio, the channel’s **Configure** dialog warns you when the trunk blocks the transfer you chose. **The number is not in the list when creating the channel.** It must be voice-capable, routed to Caplo (an Elastic SIP trunk for Twilio, an FQDN SIP connection for Telnyx), and not already used by another channel. Fix the routing, then select **Refresh account and numbers**. ## Related [Section titled “Related”](#related) [Connect a Twilio number](/channels/phone/twilio/) [Connect a Telnyx number](/channels/phone/telnyx/) [Voice and speech](/providers/voice-and-speech/) [Hand off to a person or end a call](/agents/handoff-and-end-actions/)

# Connect a Telnyx number

> Connect your Telnyx account, route a number to Caplo with an FQDN SIP connection, set up transfers, test a call, and remove the number again.

Caplo answers calls to your Telnyx numbers through a Telnyx FQDN SIP connection. You create the connection in the Telnyx portal and point it at Caplo; Caplo never buys numbers or changes your Telnyx configuration. For how phone channels work as a whole, see [Phone calls](/channels/phone/). ## What you need [Section titled “What you need”](#what-you-need) | Value | Where to find it in Telnyx | What Caplo does with it | | ---------------------- | -------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- | | **Telnyx API v2 key** | The portal’s account settings, under **API Keys**. Create a key for Caplo. | Reads the account’s phone numbers and SIP connections. | | **Ed25519 public key** | The portal’s account settings, next to the API keys, as the account’s public key. A Base64 value of 44 characters ending in `=`. | Required by the connect form and stored with the account. | Copy the **public** key. Never paste a private signing key. Caplo only reads through the API key. It stores the key encrypted and never shows it again. You also need a role that can manage integrations (Owner, Admin or Developer), and phone numbers enabled for your workspace. See [Before you start](/channels/phone/#before-you-start). ## Connect the account [Section titled “Connect the account”](#connect-the-account) 1. In the console, open **Integrations** then **Communication channels**, select the **Telnyx** tab, then **Add integration**. 2. Enter an **Integration name**, the **Telnyx API v2 key** and the **Ed25519 public key**, then select **Verify and connect**. Caplo checks the key with Telnyx and lists the account’s voice numbers. 3. Select **Connection details** on the new account. The **SIP connection** panel shows what your Telnyx connection needs: | Field | Use | | ----------------------------- | ----------------------------------------------------------------------------------------- | | **SIP host** | The address Telnyx sends calls to. | | **Port and transport** | The port and protocol for that address, for example TLS. | | **SIP URI** | The same address as a single SIP URI, for settings that ask for one. | | **Username** and **Password** | Credentials Caplo created for this Telnyx account. Select **Reveal** to see the password. | **Verification key** shows a fingerprint of the public key you entered, so you can tell which key is stored. Connecting changes nothing in Telnyx. Your numbers keep their current routing until you assign them to the connection. ## Route a number to Caplo [Section titled “Route a number to Caplo”](#route-a-number-to-caplo) 1. In the Telnyx portal, create a SIP connection of type **FQDN** that points to Caplo’s **SIP host**, on the port and transport shown in **Connection details**. Copy the values rather than typing them. 2. Use credential authentication with the **Username** and **Password** from **Connection details**. 3. Enable SRTP media encryption and the PCMU (G.711 μ-law) codec on the connection. 4. Assign the phone number to this connection. 5. Back in Caplo, select **Refresh account and numbers** in **Connection details**. The number should now show **Eligible for binding**. 6. Create a phone channel for the number. See [Set up a phone channel](/channels/phone/#set-up-a-phone-channel). Saving the channel creates the number’s route in Caplo. It shows **Provisioning** and then **Ready** under **Number routes**. Caution Assigning a number to the connection replaces how Telnyx handled its calls before, such as a Call Control application. Numbers on a Call Control application or any connection type other than FQDN cannot be connected to Caplo. You can use one FQDN connection for every number you send to Caplo from the same Telnyx account. The username and password belong to the Telnyx account you connected in Caplo, not to a single number. ## Transfers [Section titled “Transfers”](#transfers) **Cold transfers** ask Telnyx to transfer the call (SIP REFER) to the target number or SIP URI. **Warm transfers** make a new call from your Telnyx account to the person, authenticated with the same username and password. Make sure the connection is allowed to place outbound calls to the target, which in Telnyx means an outbound voice profile assigned to the connection that permits the destination. The transferred call is billed to your Telnyx account. ## Test a call [Section titled “Test a call”](#test-a-call) 1. Check that the number shows **Ready** under **Number routes** in **Connection details**. 2. Call the number from a phone. You should hear the agent’s greeting. 3. Talk to the agent, try interrupting it, and hang up. 4. Open **Monitor** then **Conversations** and find the call on the channel to read the transcript. Number discovery does not prove that audio works both ways, so make a real call after every change to the connection. ## Keep the account current [Section titled “Keep the account current”](#keep-the-account-current) Caplo checks a Telnyx account’s numbers and connections automatically about once an hour, and whenever you select **Refresh account and numbers**. After you change something in Telnyx, refresh to apply it straight away. If Caplo cannot check the account for 24 hours, for example because the API key was deleted in Telnyx, its numbers stop taking calls until a check succeeds. Rotate the credentials to fix it. To replace the API key or public key, select **Rotate credentials** on the account, enter the new values and select **Verify and rotate**. The SIP username and password stay the same, so you do not need to change the connection in Telnyx. ## What not to change in Telnyx [Section titled “What not to change in Telnyx”](#what-not-to-change-in-telnyx) While a number serves a phone channel, leave these as they are: * The connection’s host, port and transport. Without them, calls never reach Caplo. * The connection’s username and password. * SRTP and the PCMU codec on the connection. Without them, callers may hear nothing. * The number’s assignment to the connection, and the connection’s enabled state. A disabled connection stops calls. If you change any of them, select **Refresh account and numbers** in Caplo and make a test call. ## Remove a number [Section titled “Remove a number”](#remove-a-number) 1. In Caplo, open the number’s channel and select **Pause channel**. New calls are disconnected; calls in progress finish. 2. In Telnyx, assign the number to another connection or application. 3. In Caplo, select **Refresh account and numbers**, or wait for the next automatic check. The number shows **Needs setup** and its route **Disconnected**. Phone channels cannot be deleted, and a number stays tied to the channel it was first connected to. To have another agent answer the number, change the channel’s agent instead. To stop all numbers of a Telnyx account at once, select **Disable** on the account in **Integrations**. Its numbers stop taking calls until you select **Enable**. ## Troubleshooting [Section titled “Troubleshooting”](#troubleshooting) Blockers next to a number in **Connection details**: | Message | Fix | | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | | The number is no longer available in this account. | The number was released or moved. Check the account in Telnyx, then refresh. | | Enable this account connection. | The account is disabled in Caplo. Select **Enable**. | | Refresh the account and numbers. | The last check is more than 24 hours old. Select **Refresh account and numbers**. | | Enable the number’s SIP connection in Telnyx. | The connection is disabled in Telnyx. Enable it, then refresh. | | Assign the number to an FQDN SIP connection configured with the SIP connection settings. | The number is on another connection type or none. Assign it to the FQDN connection, then refresh. | **No voice-capable numbers found.** Assign an owned number to an FQDN SIP connection in Telnyx, then refresh. **Verify and connect fails.** Check that the API key is active and that the public key is the 44-character Base64 value from your Telnyx account, not a private key. **The call connects but there is no audio.** Check that SRTP and the PCMU (G.711 μ-law) codec are enabled on the connection. **Calls are not answered.** Check the connection’s host, port, transport and credentials against **Connection details**, that the route is **Ready**, and that the channel is not paused. See [Troubleshooting](/channels/phone/#troubleshooting) for more.

# Connect a Twilio number

> Connect your Twilio account, route a number to Caplo with an Elastic SIP trunk, set up transfers, test a call, and remove the number again.

Caplo answers calls to your Twilio numbers through Twilio Elastic SIP Trunking. You create the trunk in your Twilio account and point it at Caplo; Caplo never creates trunks, buys numbers or changes your Twilio configuration. For how phone channels work as a whole, see [Phone calls](/channels/phone/). ## What you need [Section titled “What you need”](#what-you-need) | Value | Where to find it in Twilio | What Caplo does with it | | -------------------------------------- | ----------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | | **Twilio Account SID** | The account dashboard. Starts with `AC`. | Selects the account or subaccount whose numbers you connect. | | **API Key SID** and **API Key Secret** | **API keys & tokens**. Create a key in the same account as the Account SID. The SID starts with `SK`. | Reads the account’s phone numbers, the trunks they are assigned to, and call records after calls end. | | **Account Auth Token** | **API keys & tokens**, under the account’s auth tokens. | Required by the connect form. Caplo stores it encrypted. | The account must be in Twilio’s **US1** region. The API Key Secret and the Account Auth Token are different values; the form needs both. Caplo only reads through the API key: incoming phone numbers, calls, and Elastic SIP trunks. A Standard key works. If you use a Restricted key, give it read access to those three resources. Caplo stores the secrets encrypted and never shows them again. You also need a role that can manage integrations (Owner, Admin or Developer), and phone numbers enabled for your workspace. See [Before you start](/channels/phone/#before-you-start). ## Connect the account [Section titled “Connect the account”](#connect-the-account) 1. In the console, open **Integrations** then **Communication channels**, select the **Twilio** tab, then **Add integration**. 2. Enter an **Integration name**, the **Twilio Account SID**, **API Key SID**, **API Key Secret** and **Account Auth Token**, then select **Verify and connect**. Caplo checks the credentials with Twilio and lists the account’s voice numbers. 3. Select **Connection details** on the new account. The **SIP connection** panel shows the values you need in Twilio: | Field | Use | | ----------------------------------------------------- | --------------------------------------------------------------- | | **Origination URI** | Where the trunk sends calls. Always copy it from here. | | **Termination username** and **Termination password** | Only for warm transfers. Select **Reveal** to see the password. | Connecting changes nothing in Twilio. Your numbers keep their current routing until you assign them to a trunk. ## Route a number to Caplo [Section titled “Route a number to Caplo”](#route-a-number-to-caplo) 1. In the Twilio console, go to **Elastic SIP Trunking** and create a trunk. Use one trunk for all the numbers you send to Caplo. 2. On the trunk’s **Origination** settings, add the **Origination URI** from Caplo’s **Connection details**. No credential list is needed for origination. 3. On the trunk’s **Numbers** settings, add the phone number. Caution Assigning a number to a trunk replaces how Twilio handled its calls before, such as a webhook URL or TwiML app. Calls to that number reach Caplo only from then on. 4. Back in Caplo, select **Refresh account and numbers** in **Connection details**. The number should now show **Eligible for binding**. 5. Create a phone channel for the number. See [Set up a phone channel](/channels/phone/#set-up-a-phone-channel). Saving the channel creates the number’s route in Caplo. It shows **Provisioning** and then **Ready** under **Number routes**. Secure Trunking (encrypted calls) can be on or off. Caplo accepts calls either way. ## Transfers [Section titled “Transfers”](#transfers) If the channel transfers callers to your team, the trunk must allow it. Change these on the trunk in Twilio, then select **Refresh account and numbers** in Caplo, because Caplo reads the trunk’s settings only when the account is checked. **Cold transfers** use SIP REFER: * In the trunk’s general settings, turn on **Call Transfer (SIP REFER)**. * To transfer to a phone number, also allow transfers to the PSTN. With SIP-only transfers, use a `sip:` URI as the target. **Warm transfers** make a new call from your Twilio account to the person: * Set a **Termination SIP URI** on the trunk. * Create a credential list with the **Termination username** and **Termination password** from Caplo’s **Connection details**, and add it to the trunk’s termination authentication. If you change Secure Trunking later, refresh the account so warm transfers use the matching encryption. When the trunk blocks the transfer type you chose, the channel’s **Configure** dialog shows a warning such as “Call transfer is turned off on this number’s Twilio trunk”. The transferred call is billed to your Twilio account. ## Test a call [Section titled “Test a call”](#test-a-call) 1. Check that the number shows **Ready** under **Number routes** in **Connection details**. 2. Call the number from a phone. You should hear the agent’s greeting. 3. Talk to the agent, try interrupting it, and hang up. 4. Open **Monitor** then **Conversations** and find the call on the channel to read the transcript. Number discovery does not prove that audio works both ways, so make a real call after every change to the trunk. ## Keep the account current [Section titled “Keep the account current”](#keep-the-account-current) Caplo checks a Twilio account’s numbers and trunks when you connect it, rotate its credentials, or select **Refresh account and numbers**. It does not check them on its own. Refresh at least every 24 hours A Twilio number whose last check is more than 24 hours old stops taking calls: callers are disconnected without a message. Select **Refresh account and numbers** to bring it back. Select **Refresh account and numbers** whenever you change something in Twilio, such as trunk settings or the numbers on a trunk. To replace the API key or Auth Token, select **Rotate credentials** on the account, enter the new values and select **Verify and rotate**. The name and Account SID stay the same. ## What not to change in Twilio [Section titled “What not to change in Twilio”](#what-not-to-change-in-twilio) While a number serves a phone channel, leave these as they are: * The Origination URI on the trunk. Without it, calls never reach Caplo. * The number’s assignment to the trunk. Moving it off the trunk stops its calls reaching Caplo. * The termination SIP URI and credential list, if you use warm transfers. * **Call Transfer (SIP REFER)** and PSTN transfer settings, if you use cold transfers. If you change any of them, select **Refresh account and numbers** in Caplo and make a test call. ## Remove a number [Section titled “Remove a number”](#remove-a-number) 1. In Caplo, open the number’s channel and select **Pause channel**. New calls are disconnected; calls in progress finish. 2. In Twilio, remove the number from the Elastic SIP trunk and set up its voice handling as you want it. 3. In Caplo, select **Refresh account and numbers**. The number shows **Needs setup** and its route **Disconnected**. Phone channels cannot be deleted, and a number stays tied to the channel it was first connected to. To have another agent answer the number, change the channel’s agent instead. To stop all numbers of a Twilio account at once, select **Disable** on the account in **Integrations**. Its numbers stop taking calls until you select **Enable**. ## Troubleshooting [Section titled “Troubleshooting”](#troubleshooting) Blockers next to a number in **Connection details**: | Message | Fix | | ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- | | The number is no longer available in this account. | The number was released or moved. Check the account in Twilio, then refresh. | | Enable this account connection. | The account is disabled in Caplo. Select **Enable**. | | Refresh the account and numbers. | The last check is more than 24 hours old. Select **Refresh account and numbers**. | | Assign the number to an Elastic SIP trunk configured with the origination URI. | Add the number to the trunk, then refresh. | **No voice-capable numbers found.** Assign an owned voice number to an Elastic SIP trunk in Twilio, then refresh. **Verify and connect fails.** Check that the API key belongs to the account in **Twilio Account SID**, that the key is active, and that the account is in the US1 region. **Calls are not answered.** Check the Origination URI matches **Connection details** exactly, the route is **Ready**, the channel is not paused, and the account was refreshed in the last 24 hours. See [Troubleshooting](/channels/phone/#troubleshooting) for more.

# Design the website widget

> Create a reusable widget design, set its brand, welcome screen, launcher and language, then publish a revision and apply it to your website channels.

A widget design controls how the website widget looks: colours, logo, fonts, welcome screen, launcher and layout. Designs are reusable. One design can serve several website channels, and each channel shows the design revision you apply to it. A design has a draft you edit and a history of published revisions. Websites never show a draft. They change only when you apply a published revision to a channel, so you can work on a design while the live widget stays the same. Who answers, which modes are offered and how visitors verify are not part of the design. Those are [entry point settings](/channels/website-widget/settings/). ## Create a design [Section titled “Create a design”](#create-a-design) 1. In the console, open **Widget designs** under **Deploy** and select **Create design**. 2. Enter a **Design name**. It is internal and only shown in the console; visitors see the widget title instead. 3. Choose a template to start from: **Standard**, **Concierge**, **Evergreen**, **Orbit**, **Help center** (an inline layout) or **Midnight** (dark). A template only seeds the first draft. 4. Select **Create design**. The design editor opens on the draft. You can also create a design while creating a website channel, with **Create a design here**. ![The Widget designs page](/_astro/designs.BqQtj2Vw_ZW4xEk.webp) ## Design sections [Section titled “Design sections”](#design-sections) The editor groups settings into sections. Withdrawing an asset version keeps it on revisions that already use it, but stops new drafts, publications and applies from using it. ### Welcome screen [Section titled “Welcome screen”](#welcome-screen) What visitors see before their first message: * **Welcome heading** and **Welcome description**. * **Suggested questions**: up to 4 shortcuts. Each has a **Suggestion label**, a **Suggestion description** and the **Message to send** when a visitor taps it. * **Message placeholder**: the hint text in the message box. The agent’s own greeting is set on the agent, not in the design. ### Launcher and layout [Section titled “Launcher and layout”](#launcher-and-layout) * **Display mode**: **Floating popup** opens from a launcher button in a corner of the page. **Inline container** renders inside an element on your page, with no launcher button. * **Width (px)** and **Height (px)** of the widget. * For a popup: **Corner** (Bottom right or Bottom left) and **Edge spacing (px)**. * **Launcher button**: **Launcher label** and **Launcher icon** (Message or Sparkles). * **Open automatically on desktop**, with an **Opening delay (seconds)** from 0 to 60. Caution Popup and inline need different embed code. If you change **Display mode** and apply the revision to a live channel, update the markup on your site at the same time. This sets the language of the widget’s own labels and buttons. Translated labels need a supported language pack. * **Text direction**: **Left to right** or **Right to left**. The language the agent answers in is set on the agent, not here. ## Publish a revision [Section titled “Publish a revision”](#publish-a-revision) 1. Save your draft. Only the saved draft is published. 2. Open **Publish and install** and select **Publish revision** followed by the next revision number. 3. Review the comparison with the previous published revision, then select **Publish revision**. A published revision is immutable. Publishing does not change any website. ## Apply a revision to a website [Section titled “Apply a revision to a website”](#apply-a-revision-to-a-website) You can apply from the design or from the channel. Either way, the change takes effect right away; you do not need to save anything else. ![The Appearance card of a website entry point with the live design revision](/_astro/entry-appearance.CIEPBGVD_1rvsOP.webp) From the design: 1. Open **Publish and install**. **Live on websites** lists the channels that use this design and the revision each shows. 2. Choose the **Revision to apply** and select **Review and apply**. 3. Review the before and after, then confirm. From the channel: open the website entry point (**Configure & install**), and on the **General** tab under **Appearance**, choose the **Widget design** and **Revision**, then select **Apply revision**. Widgets that are already open keep their look until the visitor reloads the page. The widget ID and the embed code stay the same, except when the display mode changes between popup and inline. To roll a website back, apply an earlier revision. Select **Load older revisions** if the one you want is not listed. ## Archive a design [Section titled “Archive a design”](#archive-a-design) In **Design settings**, **Archive design** hides a design from the library and stops it being published or applied. # Install the website widget

> Copy the widget embed code from the console and add it to a plain HTML site, a Next.js app or a React single page app.

The website widget is one script tag. It loads the widget from Caplo, shows the published design you applied to the channel, and connects visitors to the agent release the channel serves. ## Before you start [Section titled “Before you start”](#before-you-start) * Create a website channel (**Live chat widget**) for a published agent. See [Channels](/channels/). * Publish a widget design and apply a revision to the channel. The console only gives you embed code once a design is applied, because the code depends on whether the design is a popup or an inline container. See [Design the widget](/channels/website-widget/design/). * Know the exact origin of every site that will show the widget, for example `https://www.example.com`. ## Get the embed code [Section titled “Get the embed code”](#get-the-embed-code) 1. In **Channels**, open the website channel and select **Configure & install** on its website entry point. 2. On the **General** tab, check **Allowed website origin**. Add every origin that will show the widget, then select **Save entry point**. 3. Open the **Install** tab and select **Copy embed code**. ![The Install tab of a website entry point with the embed code](/_astro/entry-embed.Dt2VK7nq_NALOk.webp) If **Copy embed code** is disabled, the hint next to it says why: no design is applied, there are unsaved edits, the entry point is disabled, or the channel is paused. The **Widget ID** on the Install tab is a public identifier. The snippet contains no credentials, and you never need to add any. ## The embed code [Section titled “The embed code”](#the-embed-code) A popup design (a launcher button in a corner of the page): 
```plaintext
<script
  src="https://api.caplo.si/v1/messaging/widget/loader.js"
  data-widget-id="<WIDGET_ID>"
  async
></script>
```
 An inline design (the conversation sits inside an element on your page) adds a container and points the script at it: 
```plaintext
<div id="caplo-<WIDGET_ID>"></div>
<script
  src="https://api.caplo.si/v1/messaging/widget/loader.js"
  data-widget-id="<WIDGET_ID>"
  data-container="#caplo-<WIDGET_ID>"
  async
></script>
```
 Always copy the code from the console rather than typing it: the console escapes the container selector when the widget ID contains a dot. | Attribute | Required | What it does | | ------------------ | ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | | `src` | Yes | The widget loader. Load it from Caplo; a self-hosted copy cannot reach the widget service. | | `data-widget-id` | Yes | The widget ID from the Install tab. | | `data-container` | Inline designs | A CSS selector for the element the widget renders into. The element must exist on the page when the loader runs. | | `data-persistence` | No | By default the widget restores the visitor’s conversation after a reload in the same browser tab. Set `data-persistence="none"` to start fresh on every page load. | | `nonce` | When your CSP uses nonces | Add your page’s nonce. The widget applies it to the styles it adds. | | `async` | Recommended | Loads the widget without blocking your page. | The widget ID stays the same when you apply a new design revision, so you do not need to change your site when the appearance changes. Switching a design between popup and inline is the exception: inline needs the container element and `data-container`. ## Allowed origins [Section titled “Allowed origins”](#allowed-origins) The widget only works on the origins listed on the entry point. * List exact origins: scheme and host, plus the port if it is not the default. No paths and no wildcards. * `https://example.com` and `https://www.example.com` are different origins. List both if you use both. * Use HTTPS. HTTP is accepted only for `localhost`, `127.0.0.1` and `.localhost` hosts, which is useful for local development. * You can list up to 10 origins per entry point. On any other site, including a staging host you have not listed, the widget shows a **Chat unavailable · Try again** button instead of the chat. Removing an origin closes open conversations on that site. ## Add it to your site [Section titled “Add it to your site”](#add-it-to-your-site) * HTML Paste the code just before the closing `</body>` tag on every page that should show the widget. For an inline design, place the `<div>` where the conversation should appear and keep the script after it. 
  ```plaintext
      <!-- your page content -->
      <script
        src="https://api.caplo.si/v1/messaging/widget/loader.js"
        data-widget-id="<WIDGET_ID>"
        async
      ></script>
    </body>
  </html>
  ```
 * Next.js (App Router) For a popup design, load the script once in the root layout with `next/script`. It stays on the page across client-side navigation. app/layout.tsx 
  ```plaintext
  import Script from 'next/script';


  export default function RootLayout({ children }: { children: React.ReactNode }) {
    return (
      <html lang="en">
        <body>
          {children}
          <Script
            src="https://api.caplo.si/v1/messaging/widget/loader.js"
            data-widget-id="<WIDGET_ID>"
            strategy="afterInteractive"
          />
        </body>
      </html>
    );
  }
  ```
 For an inline design shown on one route, use the client component from the React tab instead of `next/script`. `next/script` loads a given script only once per page session, so the widget would not come back after a visitor navigates away and returns. If your site sets a Content Security Policy with a nonce, pass it to `<Script nonce={nonce} />`. * React SPA For a popup design, add the embed code to your `index.html`, before `</body>`. The widget stays mounted while your router changes pages. For an inline design, render the container and add the loader from an effect: 
  ```plaintext
  import { useEffect } from 'react';


  const LOADER = 'https://api.caplo.si/v1/messaging/widget/loader.js';


  export function CaploInlineWidget({ widgetId }: { widgetId: string }) {
    const containerId = `caplo-${widgetId}`;
    useEffect(() => {
      const script = document.createElement('script');
      script.src = LOADER;
      script.async = true;
      script.dataset.widgetId = widgetId;
      script.dataset.container = `#${CSS.escape(containerId)}`;
      document.body.append(script);
      return () => script.remove();
    }, [widgetId, containerId]);
    return <div id={containerId} />;
  }
  ```
 When the container leaves the page, the widget unmounts itself. Mounting the component again adds a new script, and the widget renders into the new container. Loading the same widget ID twice on one page is harmless: the second script does nothing. ## Content Security Policy [Section titled “Content Security Policy”](#content-security-policy) If your site sends a `Content-Security-Policy` header, add these sources to the matching directives and keep your existing sources: 
```plaintext
script-src https://api.caplo.si;
connect-src https://api.caplo.si;
font-src https://api.caplo.si;
img-src blob:;
worker-src blob:;
```
 The console shows the same list under **Content Security Policy additions** on the Install tab. Brand logos and avatars render from `blob:` URLs, and map results start a worker from a `blob:` URL. If the channel allows voice, the browser also connects to Caplo’s media server for the call. Add it to `connect-src`: 
```plaintext
connect-src https://api.caplo.si wss://livekit.caplo.si;
```
 Caplo never changes your site’s policy. See [Troubleshoot the website widget](/channels/website-widget/troubleshooting/) for how CSP errors show up. ## Single page apps [Section titled “Single page apps”](#single-page-apps) * The loader runs once per script element. Calling it again with the same widget ID on the same page does nothing until the widget is unmounted. * A popup widget stays mounted across client-side route changes. To remove it on some routes, call `unmount()` from the [JavaScript API](/channels/website-widget/javascript-api/); add the script again to bring it back. * An inline widget unmounts itself when its container is removed from the page. * On a full page unload the widget closes its connection. With the default persistence, the conversation resumes when the visitor returns in the same tab. ## Check the installation [Section titled “Check the installation”](#check-the-installation) 1. Open a page on an allowed origin. The launcher appears in the corner you chose, or the conversation appears in its container. 2. Send a message and check that the agent replies. The conversation appears in **Conversations** in the console. 3. If you see **Chat unavailable · Try again**, or nothing, see [Troubleshoot the website widget](/channels/website-widget/troubleshooting/). # Website widget JavaScript API

> Control the website widget from your page with window.CaploWidget, sign visitors in from your own site, and listen to widget events.

The widget loader adds a small API to your page so your own code can open the widget, pass hints about the visitor, sign the visitor in, and react to widget events. Everything here runs in the visitor’s browser; nothing on this page needs a Caplo credential. ## Get the widget control [Section titled “Get the widget control”](#get-the-widget-control) 
```plaintext
const chat = window.CaploWidget.get('<WIDGET_ID>');
```
 `window.CaploWidget` exists once the loader script has run. `get(id)` returns the control for that widget ID, or `undefined` if no widget with that ID is loaded on the page. `window.CaploWidget.protocolVersion` is `2`. The control is available as soon as the loader runs, before the widget has finished loading. Calls you make early are kept and applied when the widget mounts, so you do not need to wait for `caplo:mounted` to call `open()` or `setVisitorHints()`. Because the loader script is `async`, run your code after it loads: 
```plaintext
function withCaplo(widgetId, callback) {
  const chat = window.CaploWidget?.get(widgetId);
  if (chat) return callback(chat);
  const script = document.querySelector(`script[data-widget-id="${widgetId}"]`);
  script?.addEventListener('load', () => callback(window.CaploWidget.get(widgetId)), { once: true });
}
```
 ## Methods [Section titled “Methods”](#methods) | Method | What it does | | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | | `open()` | Opens the popup widget. If the widget is still loading, it opens when it mounts. | | `close()` | Closes the popup widget. | | `setVisitorHints(hints)` | Passes unverified hints about the visitor to the conversation. Pass `null` to clear them. | | `unmount()` | Removes the widget from the page and closes its connection. To show it again, add the loader script again. | | `identity.configure({ getToken, when })` | Registers your page as a sign-in provider. See [Sign visitors in from your page](#sign-visitors-in-from-your-page). | | `identity.refresh()` | Tells the widget your page’s signed-in user changed. Returns a promise. | | `identity.signOut()` | Tells the widget your page signed its user out. Returns a promise. | | `addEventListener(type, listener)` and `removeEventListener(type, listener)` | Listen to `caplo:identity` and `caplo:identity-signout-requested`. | ### Open the widget from your own button [Section titled “Open the widget from your own button”](#open-the-widget-from-your-own-button) 
```plaintext
withCaplo('<WIDGET_ID>', (chat) => {
  document.querySelector('#help-button').addEventListener('click', () => chat.open());
});
```
 ### Visitor hints [Section titled “Visitor hints”](#visitor-hints) Hints give the agent context it would otherwise have to ask for. They are never treated as identity: a visitor’s name in a hint does not let tools act on that person’s account. The widget always sends the browser’s language as `locale` and its time zone as `timeZone`, so the agent knows the visitor’s local date and can offer times in their zone without asking. Values you set replace the browser’s. 
```plaintext
chat.setVisitorHints({
  name: 'Ada',
  locale: 'en-GB',
  page: window.location.href,
});
```
 | Field | Rules | | ---------- | ------------------------------------------------------------------------------- | | `name` | 1 to 80 characters, no control characters. | | `locale` | A BCP 47 language tag, such as `en-GB` or `fr`, up to 35 characters. | | `page` | An `http` or `https` URL without a user name or password, up to 512 characters. | | `timeZone` | An IANA time zone, such as `Europe/London`. | Any other field throws a `TypeError`. A value that breaks these rules throws a `TypeError`; if you set it before the widget has loaded, the widget fails to load and shows **Chat unavailable · Try again**. Check values before you pass them, and leave a field out rather than sending an empty string. Each call replaces the previous hints. Hints travel with the visitor’s messages, so call `setVisitorHints` again when the page changes in a single page app. ## Sign visitors in from your page [Section titled “Sign visitors in from your page”](#sign-visitors-in-from-your-page) If visitors are already signed in to your site, your page can sign them in to the widget too. This uses a **Host sign-in** connection that you set up under **Settings** then **Customer identity**, with these settings on the website entry point: * **Customer verification** allows verified visitors, and the host sign-in connection is one of the **Sign-in methods**. * **Consent mode** is **Show a notice after verification**. With the agreement mode, host sign-in does not run automatically. Your backend signs a short-lived assertion for the signed-in user; the browser never holds your signing key. See [Website widget settings](/channels/website-widget/settings/#customer-verification). 
```plaintext
chat.identity.configure({
  when: 'open',
  getToken: async ({ nonce, requirement }) => {
    const response = await fetch('/support/caplo-token', {
      method: 'POST',
      headers: { 'content-type': 'application/json' },
      body: JSON.stringify({ nonce, requirement }),
    });
    return response.status === 200 ? response.text() : null;
  },
});
```
 `getToken` receives: | Field | Meaning | | ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `nonce` | A one-time value your backend must put in the assertion. | | `requirement` | `null`, or the level the conversation needs: `level` (`low`, `standard` or `high`), optionally `maxAuthAgeSeconds`, and for a confirmation of a specific action, `action` with an `id`, `summary` and `digest`. | Return the signed assertion as a string, or `null` when nobody is signed in on your page. The widget waits up to 30 seconds for an ordinary sign-in and up to 5 minutes when a specific action needs confirmation. `when` decides when the widget asks for a token: | `when` | The widget signs the visitor in | | ---------------- | ----------------------------------------------------------- | | `open` (default) | When the widget opens, or when the visitor sends a message. | | `first-message` | When the visitor sends their first message. | | `required` | Only when the channel or an action requires verification. | Call `identity.refresh()` after your user signs in or switches account, and `identity.signOut()` after they sign out. Both return promises. Caution Never put assertions in URLs, logs or browser storage. Treat them like passwords: each one proves who the visitor is. ## Events [Section titled “Events”](#events) The loader dispatches two events on its `<script>` element. They bubble, so you can listen on `document`: | Event | When | `event.detail` | | --------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | | `caplo:mounted` | The widget has loaded and rendered. | `{ installationId, bundleId, designId, revision }`: the widget ID, the widget release, and the design and revision shown. | | `caplo:error` | The widget could not load, so the page shows a **Chat unavailable · Try again** button instead. | `{ installationId, code }`, with `code` `"presentation-unavailable"`. | Listen to identity events on the control: | Event | When | `event.detail` | | ---------------------------------- | ---------------------------------------------------------------------- | ---------------------------- | | `caplo:identity` | The visitor’s verification state changed. | `{ state, level?, reason? }` | | `caplo:identity-signout-requested` | A visitor signed in through your page chose to sign out in the widget. | `{}` | `state` is `anonymous`, `verified`, `reauthenticate` (the visitor must verify again) or `ended` (the verified conversation ended). `level` is present when `state` is `verified`. `reason` explains the change when there is one, for example `signed_in`, `stepped_up`, `signed_out` or `host_signed_out`. 
```plaintext
document.addEventListener('caplo:error', (event) => {
  console.warn('Caplo widget unavailable', event.detail);
});


chat.addEventListener('caplo:identity', (event) => {
  console.log('Visitor is now', event.detail.state);
});


chat.addEventListener('caplo:identity-signout-requested', async () => {
  await signOutOfMySite();
  await chat.identity.signOut();
});
```
 The widget also dispatches `caplo:open` and `caplo:close` (no detail) on its own element when a visitor opens or closes the popup. They bubble to `document`. # Website widget settings

> Configure a website entry point's allowed origins, text and voice modes, customer verification and visitor file uploads.

Entry point settings decide where the widget may run and how visitors talk to the agent. They are separate from the [widget design](/channels/website-widget/design/), which only controls appearance. To open them, go to **Channels**, open the website channel and select **Configure & install**. Settings are on the **General** and **Conversation** tabs. Select **Save entry point** to apply your changes; **Discard** drops them. Saving keeps the same widget ID, so your embed code does not change. You need the Owner, Admin or Builder role to change these settings. ## General [Section titled “General”](#general) ![The General tab of a website entry point, with Appearance, Settings and the live preview](/_astro/entry-general.Bk1L5BqX_1qyyMt.webp) | Setting | What it does | | ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | **Entry point name** | Shown in the console only. | | **Allowed website origin** | The exact origins that may show the widget, up to 10. Use HTTPS, or HTTP on `localhost`, `127.0.0.1` or a `.localhost` host. Select **Add origin** for more. See [Allowed origins](/channels/website-widget/install/#allowed-origins). | | **Enable this website entry point** | Turn off to stop the widget accepting new conversations without deleting the channel. | | **Remove entry point** | Deletes this website channel and its installation. The agent and the widget design are kept. | The **Appearance** card on the same tab is where you apply a published design revision. Applying takes effect immediately and is not part of **Save entry point**. ## Text and voice [Section titled “Text and voice”](#text-and-voice) The widget supports text chat and, optionally, voice conversations in the browser. ![The Conversation tab of a website entry point](/_astro/entry-conversation.DPTUBfTv_1zXjpR.webp) Voice is off for a new website channel unless you selected **Allow voice conversations** when creating it. To turn it on later: 1. On the channel page, select **Edit channel**. 2. Select **Allow website voice**, then **Save changes**. 3. In the entry point’s **Conversation** tab, set **Conversation modes** to **Text + voice** and select **Save entry point**. | Conversation mode | Visitors can | | ----------------- | ------------------------------------------------------------------------------------------------------------------- | | **Text only** | Chat by text. | | **Text + voice** | Chat by text and start a voice conversation from the widget. The browser asks for microphone access the first time. | Turning **Allow website voice** off switches every website entry point of the channel back to text only. ### Voice engine and turn-taking [Section titled “Voice engine and turn-taking”](#voice-engine-and-turn-taking) A website voice conversation uses the voice settings of the agent release the channel serves: voice language, speech recognition model, voice, optional realtime model, and timing such as **Start replies early**. If the agent has no voice settings, Caplo uses its default English speech recognition and voice, and no setup is needed. You change these on the agent, under **Advanced settings** then **Voice** in its configuration, and they reach the website after you publish a release and update the channel. See [Voice and speech](/providers/voice-and-speech/). ## Conversation actions [Section titled “Conversation actions”](#conversation-actions) **Conversation actions** lists the actions this entry point allows, such as **Transfer to a human**. An action is available only when the agent release also allows it. For a transfer, choose the **Transfer destination** from your handoff destinations. See [Handoff and end actions](/agents/handoff-and-end-actions/). ## Customer verification [Section titled “Customer verification”](#customer-verification) Customer verification lets visitors prove who they are, so the agent’s tools can act on their own account. You set up the verification methods themselves as connections under **Settings** then **Customer identity**: **Host sign-in** (your website’s backend signs a short assertion for a visitor it already knows), **Provider sign-in** (your OpenID Connect provider in a popup) or **Verification code** (a one-time code sent to the visitor’s email or phone on file). On the entry point you choose which of them this website offers. | **Customer verification** | Behavior | | ---------------------------------------- | --------------------------------------------------------------------- | | **Anonymous visitors only** | No verification is offered. | | **Visitors may verify who they are** | Visitors can chat anonymously and verify when they or a tool need it. | | **Visitors must verify before chatting** | Visitors verify before the agent answers. | When verification is allowed, select **Choose sign-in methods and consent for this channel** to set: * **Sign-in methods**: up to 4 connections, in the order the widget offers them, each with an optional button label. Host sign-in (your own page passing a signed token) runs on its own when your page registers a token provider with the [JavaScript API](/channels/website-widget/javascript-api/#sign-visitors-in-from-your-page). * **Consent mode**: **Ask for agreement before the first verification**, or **Show a notice after verification**. Host sign-in only runs automatically with the notice mode. * **Consent version** and **Consent text**: the text visitors agree to, in English and any translations you add. Change the version whenever the text changes; visitors agree to a specific version. * **Previous conversation**: **Never show earlier conversations**, or **Show the most recent one after verification**. If the agent’s tools declare verified operations, **Verified tool operations** lets you raise the verification level an operation needs, require recent authentication, and send your API a customer context token. See [Customer-aware tools](/tools/customer-aware-tools/). ## Visitor files during handoff [Section titled “Visitor files during handoff”](#visitor-files-during-handoff) While a person from your team handles the conversation, visitors can attach files for them. The agent never sees these files, and each file is checked for type and malware. Select **Let visitors send files during a handoff**, then choose: * **Accepted files**: **Images (JPEG, PNG, GIF, WebP)** and **PDF documents**. Both are selected by default. * **Largest file**: 1 MB, 5 MB (the default) or 10 MB. ## Related [Section titled “Related”](#related) * [Install the website widget](/channels/website-widget/install/) * [JavaScript API](/channels/website-widget/javascript-api/) * [Conversations and handoff](/concepts/conversations-and-handoff/)

# Troubleshoot the website widget

> Find out why the website widget does not appear, shows Chat unavailable, is blocked by a Content Security Policy, or cannot use the microphone.

Start with the browser’s developer tools on the page that should show the widget. The **Console** shows script and Content Security Policy errors, and the **Network** tab shows the widget’s requests to `api.caplo.si`. ## See why the widget failed [Section titled “See why the widget failed”](#see-why-the-widget-failed) When the widget cannot load, the loader replaces it with a **Chat unavailable · Try again** button in the bottom right corner and dispatches a `caplo:error` event. Log it to confirm which widget failed: 
```plaintext
document.addEventListener('caplo:error', (event) => {
  console.warn('Caplo widget unavailable', event.detail);
});
```
 `event.detail` is `{ installationId, code: "presentation-unavailable" }`. For the reason, look in the **Network** tab for the `POST` request to `/v1/messaging/widget/presentation`. Its response title says what is wrong: | Response | Meaning | Fix | | -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- | | 403 **Origin denied** | The page’s origin is not an allowed origin of the entry point. | Add the exact origin. See [below](#origin-not-allowed). | | 409 **Publish and apply a widget design before installing it** | No design revision is applied to the channel. | Publish a design revision and apply it. See [Design the widget](/channels/website-widget/design/). | | 503 **The selected widget release is unavailable** | The applied revision was built for a widget release that is no longer offered. | Publish a new revision of the design and apply it. | | Another status with **Widget presentation is unavailable** | The entry point is disabled, the channel is paused or deleted, the widget ID is unknown, or the service was briefly unavailable. | Check the channel and entry point in the console, then select **Try again**. | ## The widget does not appear at all [Section titled “The widget does not appear at all”](#the-widget-does-not-appear-at-all) * **The script is missing or never ran.** Check that the page source contains the loader script and that the **Network** tab shows `loader.js` loading with status 200. * **The widget ID is wrong.** The loader silently does nothing when `data-widget-id` is missing or malformed. Copy the code again from the **Install** tab. * **An inline container is missing.** For an inline design, the element named in `data-container` must exist when the loader runs. Otherwise the widget fails to load. Put the container before the script, or add the script after your app renders the container. * **The design changed between popup and inline.** If you applied a revision with a different **Display mode**, update the embed code. A popup snippet does not render an inline design. * **It is still loading.** The loader waits up to 12 seconds for the widget’s settings and 20 seconds for the widget itself before it shows **Chat unavailable**. ## Origin not allowed [Section titled “Origin not allowed”](#origin-not-allowed) The widget works only on the exact origins listed on the website entry point, under **General** then **Allowed website origin**. * Scheme, host and port must match exactly. `https://example.com` does not cover `https://www.example.com` or `https://shop.example.com`. * Paths and wildcards are not allowed. Enter `https://example.com`, not `https://example.com/support`. * HTTP only works for `localhost`, `127.0.0.1` and `.localhost` hosts. ## The widget is unavailable on other hosts [Section titled “The widget is unavailable on other hosts”](#the-widget-is-unavailable-on-other-hosts) A staging, preview or test site is a different origin. Either add it as an allowed origin (up to 10 per entry point) or, to keep test traffic separate, create a second website channel for your test hosts and use its widget ID there. ## Content Security Policy errors [Section titled “Content Security Policy errors”](#content-security-policy-errors) If your site sends a `Content-Security-Policy`, the browser console shows messages such as “Refused to load the script” or “Refused to connect”. Add the sources the widget needs and keep your existing ones: 
```plaintext
script-src https://api.caplo.si;
connect-src https://api.caplo.si;
font-src https://api.caplo.si;
img-src blob:;
worker-src blob:;
```
 * A missing `script-src` stops the widget loading. * A missing `connect-src` shows **Chat unavailable**, or the widget opens but cannot send messages. * A missing `font-src` falls back to the device font. A missing `img-src blob:` hides your logo and avatar. A missing `worker-src blob:` stops map results rendering. * For voice, also allow `wss://livekit.caplo.si` in `connect-src`. * If your policy uses nonces, add `nonce="<NONCE>"` to the loader script tag. The widget applies the same nonce to its styles. The **Install** tab shows these sources under **Content Security Policy additions**. ## Voice does not start [Section titled “Voice does not start”](#voice-does-not-start) * **No voice button.** The channel must allow website voice, and the entry point’s **Conversation modes** must be **Text + voice**. See [Website widget settings](/channels/website-widget/settings/#text-and-voice). * **“Microphone access is unavailable. Check your browser permissions and audio device.”** The visitor blocked the microphone, or the browser has no input device. The visitor needs to allow microphone access for your site in the browser’s site settings and try again. * **Embedded in an iframe.** If your page shows the widget inside an iframe, the iframe needs `allow="microphone"`. * **“Voice is busy or unavailable. Please try again shortly.”** The call could not start. Try again; if it keeps happening, check the agent’s voice settings and that its speech providers are on under **Integrations** then **Service providers**. See [Voice and speech](/providers/voice-and-speech/). * **“Enable audio playback”** appears when the browser blocked sound until the visitor interacts with the page. The visitor selects it to hear the agent. ## Still stuck [Section titled “Still stuck”](#still-stuck) Collect the widget ID, the page URL, the `caplo:error` detail and the failing request from the **Network** tab, then [contact support](/resources/support/).

# Connect WhatsApp

> Connect a WhatsApp Business number through Meta, serve an agent release on it, and send approved templates when the 24-hour customer service window has closed.

A WhatsApp channel answers messages sent to one of your WhatsApp Business numbers. Caplo uses Meta’s WhatsApp Cloud API: you connect your WhatsApp Business account once under **Integrations**, then create a channel that serves a published agent release on one of its numbers. ## Before you start [Section titled “Before you start”](#before-you-start) * A Meta business portfolio and a WhatsApp Business account, or permission to create them during setup. You sign in to Meta with a Facebook account that can manage them. * A phone number for WhatsApp. It is either already on the WhatsApp Cloud API, or a new number that can receive a verification code by SMS or call. * A workspace role that can manage integrations (Owner, Admin or Developer) to connect the account, and one that can configure channels (Owner, Admin or Builder) to create the channel. * A published agent release. See [Publish an agent](/agents/publishing/). * A browser that allows popups from the console, because Meta’s signup opens in a popup. Caution Numbers used in the WhatsApp Business app on a phone cannot be connected. Caplo does not support Business App coexistence. To use such a number, first move it off the app by following Meta’s instructions, then connect it as a new number. ## Connect your WhatsApp Business account [Section titled “Connect your WhatsApp Business account”](#connect-your-whatsapp-business-account) 1. In the console, open **Integrations** then **Communication channels**. 2. Select **Add integration**, then **WhatsApp Business**. 3. Enter an **Integration name**, for example “Customer service account”. 4. Under **How is this number set up?**, choose: * **Already on the WhatsApp Cloud API** for a number that already sends messages through the Cloud API. * **A new number for WhatsApp** for a number you are adding to WhatsApp now. 5. Select **Prepare Meta connection**. A setup row appears on the **WhatsApp** tab with the status **Awaiting authorization**. 6. Select **Continue with Meta**. In Meta’s popup, sign in, choose or create the business portfolio and WhatsApp Business account, choose or add the phone number, and grant access. For a new number, Meta sends the verification code and asks for a display name. 7. When the popup closes, the row shows **Saving authorization**, then **Checking account**. Caplo verifies the access Meta granted, the account and the number, and subscribes your account to Caplo’s webhooks. When it finishes, the console shows “Your WhatsApp account is connected.” Meta must grant Caplo the `whatsapp_business_management` and `whatsapp_business_messaging` permissions. If you clear either one in the popup, setup ends with “Meta did not grant access to this WhatsApp account.” For a new number, Caplo registers the number for messaging after setup. If the number already has a two-step verification PIN, registration waits for it: select **Check connection**, open **Numbers**, enter the six-digit PIN under **Two-step PIN** and select **Register number**. Caplo never guesses a PIN. A number shows **Ready for messages** once Meta has activated it. ## Create the WhatsApp channel [Section titled “Create the WhatsApp channel”](#create-the-whatsapp-channel) 1. Open **Channels** under **Deploy**, select **Create channel** and choose **WhatsApp Business**. 2. Enter a **Channel name**, choose the **Agent** and **Agent release**, then select **Set up connection**. 3. Choose the **WhatsApp Business account** you connected and a **Phone number**. Only numbers that are ready and not used by another channel can be selected; others show **unavailable**. Select **Continue**. 4. Choose **Who answers**: * **AI agent**: the agent answers every customer. Your team can still take over any conversation. * **Your team**: the agent stays silent, also in open conversations. Messages wait in **Conversations** for your team to take over and reply. 5. Set the **Conversation inactivity timeout (seconds)**, from 300 to 604800. The default, 86400, starts a new conversation when the customer writes again after a day of silence. 6. Select **Create channel**, then send a message to the number from your own WhatsApp to test it. A channel keeps its number. To use another number, create another channel. To serve a newer release, update the channel as described in [Channels](/channels/#deploy-a-new-release). You can pause a WhatsApp channel but not delete it. Customers on WhatsApp are not signed in, so tools that need a [verified customer](/tools/customer-aware-tools/) do not run there, and customer memory is off. A WhatsApp conversation lasts at most seven days, whatever the inactivity timeout. ## The 24-hour customer service window [Section titled “The 24-hour customer service window”](#the-24-hour-customer-service-window) WhatsApp lets a business reply freely for 24 hours after the customer’s last message. Outside that window, only approved message templates can be sent. * The agent replies only inside the window. A message that reaches Caplo after its own window has passed, for example after a Meta outage, is recorded in the transcript without a reply. * Your team’s replies from the console are also bound to the window. After it closes, the console refuses a typed reply and asks you to send an approved template. * An open conversation in **Conversations** shows **WhatsApp reply window closes in** with the time left, or **WhatsApp reply window closed. Only approved templates can be sent.** The agent never sends templates. Templates are sent by a person on your team, from a conversation they have taken over. ## Message templates [Section titled “Message templates”](#message-templates) ### Create or sync templates [Section titled “Create or sync templates”](#create-or-sync-templates) Templates you create in Meta’s WhatsApp Manager are synced to Caplo automatically every few minutes. To sync now, select **Check connection** on the account, then **Check connection and templates**. The **Templates** tab lists every template with its status. Caplo can send a template when it is approved, its category is utility or marketing, and it has a text body with optional fixed text header and footer. Templates with media, buttons or variables outside the body are listed but cannot be sent. To create a template from Caplo: 1. On the **Templates** tab, select **New template**. 2. Enter the **Template name** (lowercase letters, digits and underscores; other characters become underscores), the **Language** (for example `en_US`) and the **Purpose**: **Updates about an order, booking or account** (utility) or **Offers and promotions** (marketing). 3. Write the **Message**, up to 1024 characters. Use `{{1}}`, `{{2}}` and so on for values you fill in when sending, numbered in order. A variable cannot start or end the message. Give an **Example** for each variable for Meta’s review. 4. Optionally add a **Header** and **Footer** of up to 60 characters each, without variables. A marketing template must tell people how to opt out, for example “Reply STOP to opt out”. 5. Select **Submit to Meta for review**. Meta usually decides within minutes to a day; the template becomes sendable once it shows as approved. Authentication templates cannot be created or sent from Caplo. ### Send a template from the inbox [Section titled “Send a template from the inbox”](#send-a-template-from-the-inbox) 1. In **Conversations**, open the customer’s WhatsApp conversation and select **Take over**. 2. Open **More actions** and select **Send approved template**. 3. Choose the **Approved template** and fill in each **Body parameter**. The **Message preview** shows exactly what the customer will receive. 4. Record the customer’s opt-in for the template’s category: under **Customer message with explicit opt-in**, pick the customer’s message that gives permission, confirm the check box, and select **Record customer opt-in**. A booking request or an ordinary reply is not an opt-in. 5. Choose the recorded opt-in under **Customer opt-in** and select **Queue template**. Follow its delivery in the transcript. A template can be sent while the conversation is still open, inside or outside the window. Each body parameter is sent as one line of at most 512 characters: line breaks and repeated spaces are collapsed. An opt-in lasts until the conversation ends, and you can revoke it with **Revoke selected opt-in**. Meta charges your WhatsApp Business account for template messages under its own pricing. ## What customers see [Section titled “What customers see”](#what-customers-see) * **Replies** arrive as text from your business number. * **Suggested replies** appear as up to three reply buttons of up to 20 characters, when the reply is short enough to carry buttons. Otherwise the reply is sent as text alone. See [Replies and feedback](/agents/replies-and-feedback/). * **Tool results**: cards with a reply action become a WhatsApp list; choices become reply buttons when three or fewer fit, otherwise a list; a detail with reply actions becomes reply buttons. Other results are sent as short numbered text. See [Present results](/tools/present-results/). * **Confirmations**: before a write tool runs, the customer gets a message with the details and “Confirm to approve these details, or Cancel.”, with **Confirm** and **Cancel** buttons. Only a tap on that message’s **Confirm** approves the request, and the buttons expire after 10 minutes or when the window closes. Fields cannot be edited on WhatsApp. A confirmation WhatsApp cannot show, such as one that needs editing or a stronger sign-in, is not sent; the customer is told the request has not been confirmed and to use your website or contact your team. See [Write tools](/tools/write-tools/). * **Handoff**: WhatsApp channels have no transfer destination, so the agent cannot hand off on its own. Your team takes over from **Conversations**, or from Chatwoot when you mirror WhatsApp conversations there. See [Hand off to Chatwoot](/channels/handoff-to-chatwoot/). WhatsApp customers get no message when your team takes over or hands back; your team’s replies simply arrive from the same number. ## Media and message limits [Section titled “Media and message limits”](#media-and-message-limits) * Caplo reads text messages and taps on its own buttons and lists. Photos, videos, voice notes, documents, stickers, locations and contacts are not passed to the agent, and the customer gets no reply to them. * Replies are text only; the agent cannot send files or images on WhatsApp. * A customer message longer than 4,000 characters reaches the agent cut to its first 3,980 characters, followed by “\[message shortened]”. ## Check the connection [Section titled “Check the connection”](#check-the-connection) Select **Check connection** on the account under **Integrations** to open its status: | Tab | What it shows | | -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | **Deliveries** | Each outgoing message with its status (queued, sent, delivered, read, failed or unknown) and Meta’s reason for a failure. **Check delivery evidence** looks for Meta’s receipt. **Retry delivery** is offered only when the earlier attempt is proven not to have been accepted. | | **Numbers** | Each number, its registration state, and Meta’s account health: whether Meta allows the account to send, limits it, or blocks it. | | **Templates** | Synced templates, their status and why one cannot be sent. | Caplo never resends a message whose outcome is unknown, because the customer may already have it. Until its outcome is known, later replies to that customer wait. Use **Check delivery evidence** to settle it. ## Troubleshooting [Section titled “Troubleshooting”](#troubleshooting) | Problem | What to do | | ------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | “WhatsApp signup isn’t available for this workspace yet.” | Embedded Signup is not enabled for your workspace. Contact [support](/resources/support/). | | “The Meta popup was blocked.” or “Meta could not load.” | Allow popups for `app.caplo.si`, turn off blockers for `facebook.com`, then select **Continue with Meta** again. | | “This WhatsApp account needs the Caplo app subscription before it can connect.” | Meta refused Caplo’s webhook subscription for the account. Check in Meta Business Settings that the account is shared with the Caplo app, then select **Reconnect**. | | “Meta did not return a Cloud API number for this account.” | You chose **Already on the WhatsApp Cloud API** but the number is not on it. Start again and choose **A new number for WhatsApp**, or pick another number. | | A number shows **Needs the number’s two-step PIN** | Enter the PIN on the **Numbers** tab and select **Register number**. If you do not know it, reset it in WhatsApp Manager first. | | A number is **unavailable** when creating a channel | It is not registered yet, it is already used by another channel, it is on the WhatsApp Business app, or the account needs to be reconnected.
