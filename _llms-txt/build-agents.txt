# Agents and releases

> How an agent's editable draft becomes an immutable release, what a release pins, and how releases reach customers.

Every agent has one **draft** and any number of **releases**. You edit and test the draft. Customers only ever talk to a release. ## The draft [Section titled “The draft”](#the-draft) The draft holds the agent’s current configuration: its name, instructions, greeting, model, knowledge bases, tools, sub-agents and conversation settings. Saving it (**Save draft** in the console, or `caplo push` from a project) stores it in the workspace, where anyone who can build agents can change it. You can test a draft at any time in the console’s **Live test** panel or with `caplo agent chat`, without any channel. Editing the draft never changes a published release. The console marks an agent with **Unpublished changes** when its saved draft differs from its latest release. ## Publishing a release [Section titled “Publishing a release”](#publishing-a-release) Publishing turns the saved draft into a release. An Owner or Admin publishes from **Publish agent** in the console or with `caplo publish` or `caplo agent publish`. Caplo then: 1. Checks the configuration, such as the greeting, the model and every reference. 2. Pins the newest published version of each tool package the agent uses, and the newest published version of each knowledge base it attaches. 3. Runs the agent’s eval cases against this exact candidate and applies the workspace’s publication requirements. See [Evaluations](/concepts/evaluations/). 4. Checks that the agent’s instructions, tools and knowledge fit within what its model can handle. 5. Freezes the result as a numbered release with a semantic version (`1.0.0`, then a major, minor or patch bump) and your release note. If any step fails, nothing is published. ## What a release pins [Section titled “What a release pins”](#what-a-release-pins) A release is immutable. It records: * The configuration as it was when published. * The exact tool package versions. A newer tool version reaches customers only when you publish the agent again. * The exact knowledge base versions. Publishing a new knowledge version does not change live answers until the agent is published again. * The exact release of each sub-agent. See [Multi-agent](/concepts/multi-agent/). Eval cases are not part of a release. You can change them without republishing, and the next publish runs the current set. ## How releases reach customers [Section titled “How releases reach customers”](#how-releases-reach-customers) A [channel](/concepts/channels/) serves one specific release. Publishing a new release does not move any channel to it; you choose when: * In the console, open the channel and select **Update to** the new version, or **Change release** to pick any release. * With the CLI, run `caplo channel deploy` for the channel, or give the project an environment with `channels` so that `caplo publish` deploys them. New conversations on the channel start on the new release. **Conversations already in progress keep the release they started with** until they end, so a customer is never switched mid-conversation. To go back, point the channel at an earlier release with **Change release** or `caplo channel rollback`. The earlier release is served exactly as it was published. ## Revoking a release [Section titled “Revoking a release”](#revoking-a-release) Revoking permanently stops a release from running: no channel and no parent agent can run it again. Use it when a release is unsafe, for example if it exposes a tool it should not. Revoke with `caplo agent release revoke <AGENT> <RELEASE> --reason "<REASON>"`. A revocation cannot be undone, so move channels to another release first. ## Archiving and deleting agents [Section titled “Archiving and deleting agents”](#archiving-and-deleting-agents) Archiving removes an agent from the active library while keeping its drafts, releases and history. Detach it from its channels and remove links from parent agents first. You can delete an agent only while it has never been published. ## Related [Section titled “Related”](#related) * [Publish an agent](/agents/publishing/) * [Test an agent](/agents/testing/) * [Agent YAML](/agents/agent-yaml/)

# Channels

> What channels and entry points are, which kinds of channel Caplo supports, and how a channel serves, updates and rolls back an agent release.

A **channel** is how customers reach an agent. It connects one or more **entry points**, such as a widget on your website or a WhatsApp number, to one published release of one agent. You manage channels under **Channels** in the console. ## Kinds of channel [Section titled “Kinds of channel”](#kinds-of-channel) | Channel | Entry point | Conversations | | ---------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------ | | **Live chat widget** | The Caplo widget, installed on your website with an embed snippet and limited to the website origins you allow. | Text, and optionally voice in the browser. | | **WhatsApp Business** | A WhatsApp Business phone number connected through Meta. | Text messages. | | **Facebook Messenger** | A Facebook Page connected through Meta. | Text messages. | | **Instagram** | An Instagram professional account connected through Meta. | Text messages. | | **Telephone** | A phone number from your Twilio or Telnyx account. | Voice calls. | For a website, you only need a published widget design; see [Add an agent to your website](/get-started/add-to-your-website/). Messaging and phone channels first need the account connected under **Integrations** > **Communication channels**. See the [channels overview](/channels/). ## A channel serves one release [Section titled “A channel serves one release”](#a-channel-serves-one-release) Each channel names an agent and a specific release of it. That agent is the channel’s **entry agent**: it greets the customer and may delegate to sub-agents (see [Multi-agent](/concepts/multi-agent/)). Because the channel names a release rather than “the latest”, publishing a new agent release never changes what customers get on its own. You decide when each channel moves. ## Deploying and rolling back [Section titled “Deploying and rolling back”](#deploying-and-rolling-back) | To | In the console | With the CLI | | ------------------------------- | --------------------------------------------------------- | -------------------------------------------------------------- | | Move to the newest release | Open the channel and select **Update to** the new version | `caplo channel deploy "<CHANNEL>"` | | Choose a specific release | **Change release** | `caplo channel deploy "<CHANNEL>" --agent "<AGENT>@<VERSION>"` | | Go back to the previous release | **Change release** | `caplo channel rollback "<CHANNEL>"` | Whichever way you deploy: * **New conversations** start on the new release straight away. * **Conversations in progress** keep the release they started with until they end. A conversation ends after the channel’s inactivity timeout, which is 24 hours unless you change it. * Rolling back serves the earlier release exactly as it was published; to move forward again, deploy or publish again. A CLI project can also deploy channels as part of `caplo publish`, by listing them under an environment’s `channels`. See [Environments](/cli/environments/). ## Channel settings [Section titled “Channel settings”](#channel-settings) Besides the release, a channel’s entry points carry settings that apply to every conversation on them, such as allowed website origins, whether voice is allowed, the inactivity timeout, and conversation actions like transferring to a person or ending a call. Changes to a channel are saved as new revisions, and settings that shape a conversation apply to conversations that start after the change. ## Related [Section titled “Related”](#related) * [Channels overview](/channels/) * [Install the website widget](/channels/website-widget/install/) * [Conversations and handoff](/concepts/conversations-and-handoff/) * [`caplo channel deploy`](/reference/cli/channel/#caplo-channel-deploy)

# Conversations and handoff

> What a conversation is, how your team reads and takes over conversations in the console, and how an agent hands a customer to a person.

A **conversation** is one customer’s chat or call on a channel. It starts when the customer first writes or calls, keeps the agent release and channel settings it started with, and ends after the channel’s inactivity timeout. Test chats in the console and the CLI are private and do not appear among your channel conversations. ## The console inbox [Section titled “The console inbox”](#the-console-inbox) **Conversations** (under **Monitor**) lists calls and chats from every channel. You can filter by channel, status and date, or show only conversations that were **Handed off**. Opening one shows the transcript, the customer’s reply ratings if the agent collects them, and the tools behind each reply. Who sees what depends on the [role](/concepts/workspaces-and-roles/): * Owners, Admins, Builders, Supervisors, Auditors and Viewers can read conversations. * The customer’s identity is hidden as **Participant hidden** until someone with permission selects **Reveal** and gives a reason. Every reveal is recorded in the workspace audit log. * Tool activity behind a reply is visible to Supervisors, Admins and Owners. * **Internal notes** are visible only to your team, never to the customer or the agent. ## Taking over [Section titled “Taking over”](#taking-over) Owners, Admins and Supervisors can step into an open text conversation at any time. Select **Take over**: the agent stops replying, the transcript notes “A member of our team has joined and will reply here.” (website visitors see it; on WhatsApp, Messenger and Instagram it is not sent), and you reply from the console. When you are done, select **Return to agent** and the agent answers the customer’s next message. Taking over needs no setup. Voice calls cannot be taken over from the console. ## Handoff to a person [Section titled “Handoff to a person”](#handoff-to-a-person) An agent can also decide to hand a conversation to your team, for example when the customer asks for a person or the request is outside what the agent should handle. This works only when the channel’s entry point allows the **transfer** conversation action and names a destination: | Channel | Destination | What happens | | -------------- | ----------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | Website widget | A Chatwoot inbox, connected under **Integrations** > **Handoff destinations** | The conversation opens in Chatwoot with a summary, and messages are relayed both ways until your team finishes. WhatsApp, Messenger and Instagram conversations are mirrored into Chatwoot instead; see [Handoff to Chatwoot](/channels/handoff-to-chatwoot/). | | Telephone | A phone number or SIP address set in **Transfer calls to** | The call is transferred, either straight away (cold) or after briefing the person who answers (warm). | What the customer sees during a text handoff: 1. When the agent hands off: “I’ve asked a member of our team to join. They’ll reply here as soon as they can.” 2. If nobody accepts in time: “No one from our team is available right now, so I’ll keep helping here.” The agent carries on. 3. When your team finishes: “Our team has finished here. I’m back to help with anything else.” In the console inbox, a handed-off conversation shows **External inbox** while the destination has it. Without a handoff destination, the agent cannot hand off on its own, but your team can still take over from the console. ## Related [Section titled “Related”](#related) * [Handoff and end actions](/agents/handoff-and-end-actions/): set up transfers and destinations. * [Channels](/concepts/channels/) * [Tools and actions](/concepts/tools-and-actions/): what happens when a write’s outcome needs a person to check.

# Evaluations

> How eval cases test an agent before it publishes, how the grader decides, and how workspace publication requirements gate releases.

**Eval cases** are example conversations that check an agent behaves as you expect. Each agent has one set of cases, its **eval suite**. Caplo runs the suite against the exact draft you are about to publish, and by default an agent publishes only when every case passes. Evals turn “it seemed fine when I tried it” into a check that runs on every release. ## What a case contains [Section titled “What a case contains”](#what-a-case-contains) A case is one customer message plus the checks it must pass. You write cases on the agent’s **Test** tab in the console, or under `evals` in the agent’s YAML file. | Check | Console field | What passes | | --------------- | --------------------------------------------------- | --------------------------------------------------------------------------------------- | | Desired outcome | **Desired customer outcome** | A grader model judges that the reply achieved the outcome you describe. | | Answer contains | **Answer must contain** | The reply includes this text. | | Answer excludes | **Answer must not contain** | The reply does not include this text. | | Sub-agent | **Expected sub-agent**, **Must not call sub-agent** | The agent did, or did not, call that sub-agent. | | Routing | **Routed by** | For fast routing agents: the route was chosen by fast routing, by the model, or either. | | Tool | **Expected tool** | The agent called this tool. | A case passes only when every check it sets passes. Good cases target the mistakes that would hurt most: a wrong answer, a missing tool call, a promise the agent must not make, or the wrong specialist. ## How a run works [Section titled “How a run works”](#how-a-run-works) Each case runs as a single turn in an isolated test conversation, against the exact candidate being published. Read tools run for real and their results count as ground truth. Write actions never run in an eval; an agent that correctly proposes a write is treated as having taken that action. The **grader** is a model that reads the case’s desired outcome and a record of the turn: the customer’s message, every tool call with its arguments and result, any proposed actions, and the final reply. It judges only against the desired outcome, every requirement in it must hold, and a reply that states facts no tool returned fails. If the grader cannot reach a verdict, the case does not pass. A failed case shows the grader’s short rationale. You can run the suite while you work: in the console’s publish dialog with **Run tests**, or with `caplo eval` (which pushes the project first) or `caplo agent eval run` for one agent’s saved draft. ## The publication gate [Section titled “The publication gate”](#the-publication-gate) Publishing runs the suite and records the result in the release. The workspace’s **Agent publication requirements**, set by an Owner or Admin under **Settings** > **General**, decide what the result means: | Setting | Options | | --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | | **Eval requirement** | **Required**: every case must pass, and an agent with no cases cannot publish. This is the default. **Disabled**: results are shown but do not block publishing. | | **Passing routing cases per sub-agent** | For agents that use fast routing: how many passing cases with a **Routed by** check each sub-agent needs, from 1 to 10. The default is 2. | The requirements apply to every agent in the workspace; there are no per-agent exceptions. Disabling evals does not disable Caplo’s own checks: configuration, tool and knowledge eligibility, and Fast decisions for fast routing still apply. A release keeps the policy it was published under. Eval cases are not pinned in a release, so you can add or change cases at any time. The next publish runs the current suite. ## Related [Section titled “Related”](#related) * [Write evals](/agents/evals/) * [Test an agent](/agents/testing/) * [Publish an agent](/agents/publishing/) * [Multi-agent](/concepts/multi-agent/): fast routing and its eval coverage.

# Knowledge

> How knowledge bases, documents, review, versions and audiences work, and how agents use them to answer.

A **knowledge base** is a set of documents your agents can search to answer questions, such as product guides, policies or FAQs. An agent with knowledge looks up relevant passages while it answers, instead of relying on what its model already knows. Knowledge bases belong to the workspace, not to one agent. You manage them under **Knowledge** in the console, and any number of agents can attach the same base. ## Documents and review [Section titled “Documents and review”](#documents-and-review) You add documents to a knowledge base as files: PDF, DOCX, HTML, Markdown, plain text, and PNG, JPG or WebP images, up to 25 MB each. Each file goes through the same steps before agents can use it: 1. **Extract.** Caplo extracts the text, including text in images and the page layout. 2. **Review.** You check the extracted text and the passages (chunks) agents will retrieve. Look for missing pages, broken tables, unreadable images and anything sensitive that should not be there. 3. **Approve.** An Owner or Admin approves the document. Builders can create knowledge bases and upload files, but only Owners and Admins approve documents and publish versions. This keeps a person accountable for what agents tell customers. ## Versions [Section titled “Versions”](#versions) Approved documents become available to agents only when an Owner or Admin publishes a **version** of the knowledge base. Caplo indexes the version, and once it is ready agents can search it. Versions are immutable: files you add or change later stay in the draft until you review them and publish another version. When you publish an agent, its release pins the knowledge version that was current at that moment. A new knowledge version does not change live answers until you publish the agent again. This means you can review exactly what a release knows, and an upload can never silently change what customers are told. See [Agents and releases](/concepts/agents-and-releases/). ## Audience [Section titled “Audience”](#audience) Each knowledge base has an **Audience**: | Audience | Who it serves | | --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | **Public** | Anyone talking to the agent. | | **Verified customers only** | Only customers who have signed in during the conversation, on a channel that allows customer sign-in. Use it for content that should not reach anonymous visitors, such as account-specific procedures. | A change of audience applies from the next published version. ## Keeping knowledge in sync [Section titled “Keeping knowledge in sync”](#keeping-knowledge-in-sync) To keep a knowledge base in step with a folder of files in your repository, use `caplo knowledge sync`. It uploads new and changed files, removes ones that are gone, and with `--approve` and `--publish` approves them and publishes a version in one step. Approving this way skips reviewing the extracted text, so use it for content you already trust. ## Related [Section titled “Related”](#related) * [Give an agent knowledge](/agents/knowledge/) * [Evaluations](/concepts/evaluations/): add eval cases that check answers drawn from your documents. * [`caplo knowledge sync`](/reference/cli/knowledge/#caplo-knowledge-sync)

# Multi-agent

> How one agent delegates to sub-agents, the two ways a sub-agent can work, how child releases are pinned, and how routing chooses a sub-agent.

An agent can link other agents in the workspace as **sub-agents**. The agent a channel serves is the **entry agent**; it decides when to involve a sub-agent and which one. Splitting work this way keeps each agent’s instructions, tools and knowledge small and focused, for example a concierge that routes to separate orders, product and returns specialists. Each link has a **Use when** description, which tells the parent when this sub-agent is the right choice, and an optional **Do not use when** description, which rules it out for requests that belong elsewhere. Write both as you would brief a colleague. ## Two ways a sub-agent can work [Section titled “Two ways a sub-agent can work”](#two-ways-a-sub-agent-can-work) | In the console | In agent YAML | What happens | | ------------------------------------- | --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | | **Answers and returns to this agent** | `mode: task_tool` | The parent asks the sub-agent in plain words, the sub-agent works with its own tools and knowledge, and returns an answer. The parent then replies to the customer. The sub-agent remembers its earlier requests in the same conversation. | | **Takes over the conversation** | `mode: active_conversation` | The entry agent hands the conversation to the sub-agent, which replies to the customer directly from the next message on until it hands the conversation back. | Use **Answers and returns** when the entry agent should stay in charge and combine answers, and **Takes over** when a specialist should run a longer exchange itself. Only the entry agent can hand the conversation over. Whichever mode you choose, a sub-agent’s write actions are shown to the customer for confirmation in the same way as the entry agent’s. See [Tools and actions](/concepts/tools-and-actions/). ## Child releases are pinned [Section titled “Child releases are pinned”](#child-releases-are-pinned) A link points at a specific published release of the child agent, and the child runs with the tools and knowledge pinned in that release, not its own current draft. A child must have a release before the parent can publish. Publishing a new child release does not change a published parent. To use it, update the link in the parent’s draft and publish the parent again. In a CLI project, `release: latest` on a link resolves to the child’s newest release whenever you push or publish, and `caplo publish` republishes the parents of a child that changed, children first. Agents can delegate further, up to a depth limit: by default at most three levels of sub-agents below an agent. ## Routing: the model or fast routing [Section titled “Routing: the model or fast routing”](#routing-the-model-or-fast-routing) The parent chooses a sub-agent in one of two ways: * **The model decides.** The parent’s own model reads the conversation and either answers or calls a sub-agent. This is the default and needs no setup. * **Fast routing.** A quick decision call picks the sub-agent before the parent’s model runs, in about 0.3 seconds instead of about 2 seconds. When the decision is below the agent’s minimum confidence, the model decides instead. Fast routing has extra requirements, because a wrong route is costly: * **Fast decisions** must be enabled for the workspace by an Owner or Admin. It sends the visitor’s recent messages and your sub-agent descriptions to OpenAI to choose a route. See [Fast decisions](/providers/fast-decisions/). * Every link needs a **Do not use when** description. * While evals are required, publishing needs passing eval cases that check the route to each sub-agent: two per sub-agent by default. See [Evaluations](/concepts/evaluations/). ## Related [Section titled “Related”](#related) * [Sub-agents and routing](/agents/sub-agents-and-routing/): how to link agents and set up routing. * [Agents and releases](/concepts/agents-and-releases/) * [Build your first agent with the CLI](/get-started/quickstart-cli/): a working multi-agent example.

# Tools and actions

> How agents use tool packages and remote MCP servers, the difference between reads and writes, how customers confirm writes, and what each outcome means.

Tools let an agent look things up and take actions in your systems: check an order, find a free appointment slot, create a return. Caplo gets tools from two sources. | Source | What it is | | --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | **Tool package** | Code you write in TypeScript with the `@caplo/tools` SDK, either as a single function or as an MCP server with several tools. Caplo builds it, tests it, and runs it in an isolated sandbox that can reach only the hosts the package declares. Secrets are bound from workspace secrets, never stored in code. | | **Remote MCP server** | An MCP server you already run, connected by URL with its authorization. You review its tools, classify each as a read or a write, and publish the reviewed set. | Both become **immutable versions**. An agent release pins the exact version, so changing a tool’s code has no effect on customers until you publish a new tool version and then a new agent release. See [Agents and releases](/concepts/agents-and-releases/). ## Reads and writes [Section titled “Reads and writes”](#reads-and-writes) Every tool declares its **effect**. * A **read** only looks something up. The agent calls it whenever it needs the information and uses the result straight away. * A **write** changes something: it books, cancels, refunds or submits. By default (`confirmation: required`) a write never runs on the model’s say-so. The agent proposes the exact call, Caplo shows the customer what will happen, and the call runs only after the customer confirms. If the customer declines, nothing runs. A write can set `confirmation: none` to run without asking, but use that only for low-risk changes the customer would always expect. Model output, documents and message text never grant permission to run a write. The effect and confirmation come from your package’s `caplo.yaml`, or from your review of a remote MCP server’s tools, not from hints in the tool’s own code. ## Write outcomes [Section titled “Write outcomes”](#write-outcomes) Once a confirmed write runs, the tool reports one of four outcomes: | Outcome | Meaning | What the customer sees | | -------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- | | Applied | The change happened. | Confirmation that the request succeeded. | | Rejected | Your system definitely did not make the change, for example because the slot was taken. | That the request did not go through. | | Pending | Your system accepted the request but has not finished it. | That the outcome is not confirmed yet, and they should not send it again. | | Unknown | Caplo cannot tell whether the change happened, for example after a timeout or an error. | The same as pending. | Caplo never retries a write blindly, because a retry could book or charge twice. For pending and unknown outcomes, a tool can provide a status check: Caplo asks it later about the original request and records the real outcome when the tool answers. If the outcome stays unknown, someone on your team should check your own system and follow up with the customer. While a write is unresolved, the agent cannot propose another write in the same conversation. See [Write tools](/tools/write-tools/) for how to return these outcomes and add a status check. ## Human follow-up [Section titled “Human follow-up”](#human-follow-up) Some requests should go to a person rather than a tool. An agent can hand the conversation to your team when its channel has a handoff destination, and your team can take over any text conversation from the console. See [Conversations and handoff](/concepts/conversations-and-handoff/). ## Related [Section titled “Related”](#related) * [Tools overview](/tools/) and [Write your first tool](/tools/first-tool/) * [Connect a remote MCP server](/tools/remote-mcp/) * [Give an agent tools](/agents/tools/) * [Secrets and egress](/tools/secrets-and-egress/)

# Workspaces and roles

> How workspaces separate your work, what each of the eight member roles can do, and how to switch between workspaces.

A workspace is the boundary for everything in Caplo. Agents, tool packages, knowledge bases, channels, conversations, secrets, provider keys, usage and billing all belong to one workspace, and nothing is shared between workspaces. Many teams use one workspace per environment, for example one for staging and one for production, and publish to each with the CLI’s [environments](/cli/environments/). The first time you sign in to the console, Caplo creates a workspace for you and makes you its Owner. You can create more from the workspace menu, or with `caplo workspace create`. ## Members and roles [Section titled “Members and roles”](#members-and-roles) Each member has exactly one role in a workspace. Owners and Admins invite people from **Settings** > **Members** with **Invite member**: enter the email addresses, choose a **Role**, and select **Send invitations**. They can also limit invitations to **Allowed email domains** and change or remove members later. A workspace has exactly one Owner, and only the Owner can transfer ownership. | What you can do | Owner | Admin | Builder | Developer | Supervisor | Auditor | Viewer | Billing | | ------------------------------------------------------------------------------------------ | ----- | ----- | ------- | --------- | ---------- | ------- | ------ | ------- | | Create, edit and test agents; upload knowledge | Yes | Yes | Yes | | | | | | | Publish agents; approve knowledge and publish its versions | Yes | Yes | | | | | | | | Build and publish tool packages | Yes | Yes | | Yes | | | | | | Manage workspace secrets and bind them to tools | Yes | Yes | | | | | | | | Configure channels and widget designs | Yes | Yes | Yes | | | | | | | Connect integrations, such as messaging accounts, phone providers and handoff destinations | Yes | Yes | | Yes | | | | | | Manage AI provider keys | Yes | Yes | | Yes | | | | | | Read conversations | Yes | Yes | Yes | | Yes | Yes | Yes | | | Take over conversations, add notes, reveal participants | Yes | Yes | | | Yes | | | | | View usage | Yes | Yes | | | | Yes | | Yes | | Manage the plan, payments, billing details and spend budgets | Yes | | | | | | | Yes | | Invite and manage members | Yes | Yes | | | | | | | | Workspace settings, SSO, customer identity, data retention | Yes | Yes | | | | | | | | Create API clients for CI and scripts | Yes | Yes | | Yes | | | | | | Read the audit log | Yes | Yes | | | | Yes | | | | Transfer ownership | Yes | | | | | | | | Every role except Auditor can also read agents, tools, channels and integration status. Auditor reads agents, channels, conversations, usage and the audit log, but not tools or integrations. A few combinations are worth knowing: * **Builders cannot publish.** A Builder prepares and tests an agent; an Owner or Admin reviews and publishes it. * **Developers cannot edit agents.** A Developer builds tool packages and integrations that Builders then attach to agents. * **A CLI project that contains both agents and tool packages** needs an Owner or Admin to push and publish it. Caplo checks permissions on every request, so the CLI, Tool Studio and the API enforce the same rules as the console. An [API client](/cli/ci-cd/) can be granted only actions that the member creating it holds. ## Switching workspaces [Section titled “Switching workspaces”](#switching-workspaces) In the console, the workspace menu in the top bar shows the current workspace’s name. Open it to switch to another workspace you belong to, or select **Create workspace**. If a workspace requires company single sign-on, you may be asked to sign in through your identity provider when you enter it. The CLI acts on one workspace at a time: * `caplo workspace use "<NAME>"` selects the workspace for later commands. * `--workspace` (or `-w`) on any command, or the `CAPLO_WORKSPACE` environment variable, overrides it for that command. * `caplo workspace list` shows the workspaces you belong to, and `caplo auth status` shows the selected one. See [Workspaces in the CLI](/cli/workspaces/) for details. ## Related [Section titled “Related”](#related) * [Agents and releases](/concepts/agents-and-releases/): what Builders and Admins create and publish. * [Conversations and handoff](/concepts/conversations-and-handoff/): what Supervisors do in the inbox. * [Plans](/billing/) and [spend budgets](/usage/spend-budgets/): what the Billing role manages.

# Define an agent in YAML

> Write an agent as a YAML file, edit it in the console's YAML editor or with caplo agent, and move a console agent into a CLI project.

Everything on an agent’s **Setup**, **Tools & actions**, **Knowledge** and **Sub-agents** tabs can be written as one YAML file. The console’s YAML editor and the `caplo` CLI read the same format, so you can keep agents in a repository, review changes in pull requests, and publish from CI. Every field is listed in the [Agent YAML reference](/reference/agent-yaml/). ## The agent file [Section titled “The agent file”](#the-agent-file) An agent file is one YAML document with `apiVersion: "v2.0.0"` (`v2` and `v2.0` also work; `v1` files are refused), `kind: Agent`, and the agent’s fields. This file defines a support agent with two tools, a knowledge base, a returns sub-agent and human handoff: 
```plaintext
apiVersion: "v2.0.0"
kind: Agent
name: Support Desk
description: Answers order and returns questions for Northwind customers.
instructions: |-
  You are the Northwind support agent.
  Answer questions about orders, delivery and returns.
  Look orders up with the order tools before you describe their status.
  If you cannot find an answer, say so and offer to connect the customer with a person.
greeting: Hi, I'm the Northwind support agent. How can I help with your order today?
model:
  provider: Anthropic
  name: claude-haiku-4-5-20251001
  temperature: 0.3
  responseLimit: 800
tools:
  - order-desk/lookup_order
  - order-desk/track_shipment
knowledgeBases:
  - Returns policy
actions:
  - transfer
subAgents:
```

# Write and run evals

> Define eval cases for an agent, run them from the console or the CLI, and meet the publication gate and workspace publication requirements.

An eval case is a customer message and what should happen when the agent answers it. Each case runs as one turn of an isolated test conversation against the agent’s saved draft. Its checks pass or fail automatically, and a grader model judges whether the reply achieved the case’s desired outcome. By default a workspace publishes an agent only when every case passes. For the ideas behind this, see [Evaluations](/concepts/evaluations/). ## Case fields [Section titled “Case fields”](#case-fields) | YAML field | Console label | Required | Description | | ------------------ | ------------------------------ | -------- | --------------------------------------------------------------------------------------------------------------------------------------- | | `name` | **Case name** | Yes | Up to 80 characters, unique within the agent. The CLI matches cases by name. | | `input` | **Customer message** | Yes | The one message the customer sends. Up to 8,000 characters. | | `desiredOutcome` | **Desired customer outcome** | Yes | The correct decision or next step, including the evidence it needs. A grader model judges every run against it. Up to 4,000 characters. | | `answerContains` | **Answer must contain** | No | A phrase the reply must include. | | `answerExcludes` | **Answer must not contain** | No | A phrase the reply must not include, such as a promise the agent must not make. | | `tool` | **Expected tool** | No | A tool the agent must call, named as in its `tools` list, for example `order-desk/lookup_order`. | | `subAgent` | **Expected sub-agent** | No | A sub-agent the agent must call: its name, or its file key in a project. | | `avoidSubAgent` | **Must not call sub-agent** | No | A sub-agent the agent must not call. Must differ from `subAgent`. | | `routedBy` | **Routed by** | No | `fast`, `model` or `any`: how an agent with fast routing must have routed the case. See [Routing cases](#routing-cases). | | `uncertainty` | **If the answer is uncertain** | No | What the agent should say or ask instead of guessing. A note for reviewers; runs do not check it. | | `prohibitedAction` | **Prohibited action** | No | A promise or action a reviewer should reject. A note for reviewers; runs do not check it. | Of the optional fields, runs check `answerContains`, `answerExcludes`, `tool`, `subAgent`, `avoidSubAgent` and `routedBy`. If an uncertain answer or a forbidden action matters, also state it in `desiredOutcome` so the grader judges it, or add an `answerExcludes` phrase. The console asks for at least one of **Answer must contain**, **Answer must not contain**, **Expected sub-agent** or **Expected tool** on every case. The console also offers **Tool failure to simulate**; live runs do not support it, and a case that sets it cannot pass, so leave it empty. An agent can have up to 100 cases. ## What every run checks [Section titled “What every run checks”](#what-every-run-checks) Besides the case’s own fields, every case is checked for these: | Check | Passes when | | ------------------ | ----------------------------------------------------------------- | | Turn completed | The turn ended with a reply. | | Desired outcome | The grader model judges that the reply achieved `desiredOutcome`. | | No business action | The test did not carry out a write in your systems. | | Within limits | The turn stayed within its delegation and tool limits. | When the grader cannot reach a verdict, the case ends as an error with **The desired outcome could not be graded** and does not pass. Run it again. ## Add cases [Section titled “Add cases”](#add-cases) * Console 1. Open the agent and select the **Test** tab. It lists the agent’s cases with the result of the latest run. 2. Select **Add case**, fill in the fields, and select **Save case**. Cases save immediately; they are not part of the draft. 3. Expand a case to see its checks, its last result and the reason a check failed. **Edit** and **Remove** change it. ![The Test tab of an agent listing its eval cases and their last results](/_astro/agent-evals.Cv7lHaBB_2sGKnm.webp) * CLI In a project, list cases under `evals` in the agent file: 
  ```plaintext
  evals:
    - name: Reports a shipped order
      input: What's the status of order SO-1002?
      desiredOutcome: Looks the order up and says it has shipped, without inventing a delivery date.
      answerContains: shipped
      tool: order-desk/lookup_order
    - name: Refuses to promise a refund
      input: Just refund me now, I don't want to wait.
      desiredOutcome: Explains the refund process and offers to start a return; does not promise a refund.
      answerExcludes: your refund has been approved
  ```
 `caplo push` (or `caplo agent push -f <file>`) matches the cases to the agent’s suite by name and replaces the suite with them. A file without an `evals` key leaves the suite alone; `evals: []` deletes every case. This list form is the project convention. The console’s **Export YAML** writes cases as `evals: {cases: [...]}` with an `id` on each case, and the CLI accepts that form too; see [Agent YAML](/agents/agent-yaml/#console-and-cli-formats). ## Routing cases [Section titled “Routing cases”](#routing-cases) An agent with [fast routing](/agents/sub-agents-and-routing/#routing) publishes only when the run proves routing works. Add cases that set `routedBy` and name a direct sub-agent in `subAgent`: 
```plaintext
evals:
  - name: Routes an order question
    input: Where is my order SO-1002?
    desiredOutcome: Asks the orders specialist and reports that the order has shipped.
    subAgent: orders
    avoidSubAgent: returns
    routedBy: fast
  - name: Routes a delivery question
    input: My package for order SO-1001 still hasn't arrived.
    desiredOutcome: Asks the orders specialist and reports the order's delivery status.
    subAgent: orders
    routedBy: fast
```
 `routedBy: fast` passes when fast routing picked the sub-agent, `model` when the model did, and `any` when either did. A failed routing check reports which route was used and, for fast routing, its confidence against `minConfidence`. While the workspace requires evals, each direct sub-agent needs a set number of passing routing cases: two by default (see [Publication requirements](#publication-requirements)). When the agent file lists evals, `caplo validate` checks that it has two per sub-agent. The workspace must also have **Fast decisions** turned on; see [Fast decisions](/providers/fast-decisions/). ## Run evals [Section titled “Run evals”](#run-evals) * Console Runs start from the publish dialog. Select **Publish agent**, then **Run tests** under **Agent evals**. The dialog shows how many cases passed, and each failed case with its failed checks. The **Test** tab shows the latest results, and says when they are from an earlier draft or case list. * CLI 
  ```plaintext
  caplo agent eval run "Support Desk"
  caplo agent eval list "Support Desk"
  caplo agent eval get "Support Desk" <run-id>
  ```
 In a project, `caplo eval` pushes the selected agents first, then runs their cases: 
  ```plaintext
  caplo eval agent/support
  ```
 Each case prints `ok` or its failed checks, with the grader’s rationale when the desired outcome was not met. The command exits with status 3 when a case fails or an agent has no cases. A passing run for the same draft and cases is reused instead of running again. Running evals needs an Owner or Admin, or an API key with the `agents:publish` scope. A run takes up to about 10 minutes. Each case is a real turn of the agent and counts toward usage like any other turn. ## Publication gate [Section titled “Publication gate”](#publication-gate) Publishing runs the gate against the exact saved draft and the current case list: * While the workspace requires evals, every case must pass in a run of that draft and those cases, and an agent with no cases cannot publish. Editing either one needs a new run. * With the requirement off, the console and the CLI still run the cases and show the results, but failed cases do not block publishing, and an agent with no cases publishes. * A release does not pin eval cases. When only the cases change, `caplo publish` runs them against the released draft and keeps the release. * The platform checks of the latest run (no business action, within limits) must pass even when the eval requirement is off. ### Publication requirements [Section titled “Publication requirements”](#publication-requirements) An Owner or Admin sets the workspace’s rules in **Settings > General > Agent publication requirements**. They apply to every agent in the workspace; releases already published keep the policy they were published under. | Setting | Options | Default | | --------------------------------------- | ---------------------------------------------------------------------------------- | -------- | | **Eval requirement** | **Required**: all evals must pass. **Disabled**: results do not block publication. | Required | | **Passing routing cases per sub-agent** | 1 to 10 | 2 | With the requirement disabled, eval results are advisory and fast routing coverage is not enforced, but fast routing still needs Fast decisions turned on. Caution Disabling the eval requirement lets releases reach customers without proof that they behave. Prefer fixing or removing a failing case. # Hand off to a person or end a call

> Allow an agent to transfer a conversation to a human or end a voice call, and see what happens when it does.

Conversation actions let an agent do more than reply: hand the conversation to a person, or end a voice call when the caller is done. An agent has no actions unless you allow them. | Action | YAML value | Console label | What the agent can do | | -------- | ---------- | ----------------------- | ---------------------------------------------------------------------------------------------------------- | | Transfer | `transfer` | **Transfer to a human** | Hand the conversation to a person through the channel’s handoff destination, with a one-line reason. | | End | `end` | **End call** | End a voice call, with a goodbye, once the caller has nothing more they need. Applies to voice calls only. | ## Allow an action [Section titled “Allow an action”](#allow-an-action) An action needs permission in two places: on the agent, and on the channel entry point that serves it. The agent decides when to use an action; the channel decides whether it is available there and where a transfer goes. 1. **On the agent.** In the console, open the agent’s **Tools & actions** tab and check the actions under **Conversation actions**, then select **Save draft**. In an agent file, list them under `actions`: 
   ```plaintext
   actions:
     - transfer
     - end
   ```
 2. **Publish** a release with the action. Adding an action suggests a minor version bump, removing one a major bump. See [Publish an agent](/agents/publishing/). ![Conversation actions on the agent Tools & actions tab, with Transfer to a human checked](/_astro/agent-actions.DlhXtSFD_ZN3HOs.webp) 3. **On the channel.** For a website widget, open the entry point’s **Conversation** tab and allow the action under **Conversation actions**; for a transfer, choose a Chatwoot handoff destination as the **Transfer destination**. An action the published agent does not allow shows **Unavailable: enable this action in the agent and publish a version.** For a phone channel, set **Transfer calls to** (a phone number or SIP address) and **Transfer type** in the channel’s **Conversation** step; see [Phone](/channels/phone/). For WhatsApp, Messenger and Instagram, see [Handoff to Chatwoot](/channels/handoff-to-chatwoot/). ![Conversation actions on a website entry point, with a Chatwoot transfer destination](/_astro/entry-actions.CgwxwGl-_Z1O5FDX.webp) Tell the agent in its [instructions](/agents/instructions-and-model/) when to hand off, for example “Offer to connect the customer with a person when they ask for a refund over 100 euros, or when you cannot resolve the issue after two tries.” Without guidance, the model decides on its own. ## What happens on a transfer [Section titled “What happens on a transfer”](#what-happens-on-a-transfer) When the agent transfers a chat, the conversation is marked **Handed off** and the agent stops replying. What follows depends on the destination: * **Chatwoot destination.** Caplo opens a conversation in your Chatwoot inbox and relays messages both ways, so your team replies from Chatwoot and the visitor stays in the same chat. * **Caplo console.** Operators with inbox access see the conversation in **Monitor > Conversations**, where they can **Take over** and reply, and **Return to agent** when they are done. On a phone call, the caller is transferred to the number or SIP address set on the entry point, either straight away (cold) or after the person who answers is briefed and accepts (warm). For the full flow, including ownership and what the visitor sees, see [Conversations and handoff](/concepts/conversations-and-handoff/). ## Test actions [Section titled “Test actions”](#test-actions) Try a handoff in the console’s [live test](/agents/testing/) or with `caplo agent chat`, then add an [eval case](/agents/evals/) such as “Customer asks for a person” with a desired outcome that names the handoff, so every publish checks the behavior.

# Set instructions and model

> Name an agent, write its instructions and greeting, and choose the model, temperature, response limit and reasoning settings it runs with.

Every agent starts with the same core: a name, instructions that define its behavior, a greeting, and the language model it runs on. These settings live in the agent’s draft. Nothing you change here reaches customers until you [publish a release](/agents/publishing/) and point a channel at it. ## Create an agent and set its basics [Section titled “Create an agent and set its basics”](#create-an-agent-and-set-its-basics) * Console 1. Open **Build > Agents** and select **Create agent**. 2. Enter an **Agent name** and, optionally, a **Description**, then select **Create draft**. The agent opens on its **Setup** tab. 3. Under **Instructions**, write the **Agent instructions** and the **Greeting message**. 4. Expand **Advanced settings** and choose a **Model**. Adjust **Temperature** and **Response limit** if you need to. 5. Select **Save draft**. ![The agent editor: the Setup tab with the Live test panel beside it](/_astro/agent-editor.DyjJ5xJN_cRmx2.webp) You need a role that can build agents (Owner, Admin or Builder) to edit a draft. Only Owners and Admins can publish it. * CLI Write a starter agent file, edit it, then save it as the agent’s draft: 
  ```plaintext
  caplo agent init -f support.yaml --name "Support Desk"
  caplo agent validate -f support.yaml
  caplo agent push -f support.yaml
  ```
 `caplo agent push` creates the agent when the workspace has no agent with that name, and otherwise replaces its draft. The basics look like this in the file: 
  ```plaintext
  name: Support Desk
  description: Answers order and returns questions.
  instructions: |-
    You are the Northwind support agent.
    Answer questions about orders, delivery and returns.
    If you do not know something, say so instead of guessing.
  greeting: Hi, how can I help with your order today?
  model:
    provider: Anthropic
    name: claude-haiku-4-5-20251001
    temperature: 0.4
    responseLimit: 800
  ```
 See [Agent YAML](/agents/agent-yaml/) for the whole file. ## Fields [Section titled “Fields”](#fields) | Console label | YAML field | Required | Limits and default | | ---------------------- | ------------------------------ | -------- | --------------------------------------------------------------- | | **Agent name** | `name` | Yes | Up to 80 characters. Unique in the workspace, ignoring case. | | **Description** | `description` | No | Up to 240 characters. What the agent helps with, for your team. | | **Agent instructions** | `instructions` | Yes | Plain text. | | **Greeting message** | `greeting` | Yes | The first message of every new conversation on a channel. | | **Model** | `model.provider`, `model.name` | Yes | A provider and model from the workspace’s model list. | | **Temperature** | `model.temperature` | No | 0 to 1. Default 0.4. | | **Response limit** | `model.responseLimit` | No | 64 to 128,000 tokens. Default 1,024. | ### Instructions [Section titled “Instructions”](#instructions) The instructions are the agent’s standing brief: its purpose, tone, what it may and may not do, and when to use its tools, knowledge and sub-agents. Keep them about behavior. Channel and voice settings belong to the channel, not here, so the same agent can serve several channels. Caplo adds a short block of platform guidance and a reply style after your instructions on every turn, for example asking the agent to answer only from its instructions, the conversation and its tool results. You can replace or turn off those blocks in the agent’s [policy](/agents/policy-and-limits/). Practical tips: * Name the tools and sub-agents the agent should use, and when. The model sees their descriptions, but a sentence in the instructions makes the choice reliable. * Say what to do when the agent cannot answer: ask a question, say it does not know, or offer a person. * Put facts that change often in a [knowledge base](/agents/knowledge/) or a [tool](/agents/tools/), not in the instructions, so you can update them without editing the agent. ### Greeting [Section titled “Greeting”](#greeting) The greeting opens every new conversation when the agent serves a channel and starts every test chat. A draft without one cannot be tested or published. ## Choose a model [Section titled “Choose a model”](#choose-a-model) The **Model** list shows the models Caplo can run for this workspace, grouped by provider (Anthropic and OpenAI). Each model shows where its calls are billed: * **Caplo Managed**: Caplo’s provider account, charged to your workspace usage. * **Your key**: your own provider key, set in **Manage > Integrations > Service providers**. See [Bring your own key](/providers/bring-your-own-key/). A provider that is turned off in Integrations shows **Enable in Integrations** and cannot be chosen. If the draft names a model the workspace no longer offers, it shows as **Not available in this environment**, and you must pick another model before you can test or publish. In an agent file, `model.provider` is the provider’s display name (`Anthropic` or `OpenAI`) and `model.name` is the model ID shown in the console list, such as `claude-haiku-4-5-20251001`. The CLI does not list models; read the IDs from the console. Changing the provider or model of a published agent suggests a major version bump when you publish, because answers can change in kind. ### Temperature and response limit [Section titled “Temperature and response limit”](#temperature-and-response-limit) **Temperature** controls how varied replies are. Lower values give more consistent answers, which suits support and transactional agents; the default 0.4 is a good start. **Response limit** is the most tokens one reply may use. Each model also has a tested maximum output, and Caplo checks the limit against it when you test or publish, so a value above the model’s maximum is refused at that point rather than when you save. A thinking budget, if you set one, counts toward this limit. ## Reasoning settings [Section titled “Reasoning settings”](#reasoning-settings) Some models can reason before they reply. Reasoning can improve answers to multi-step questions, at the cost of slower and more expensive turns. Set it under **Advanced settings > Agent loop**, or in the agent file’s `policy.reasoning`: | Console label | YAML field | Values | Applies to | | -------------------- | --------------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | | **Reasoning effort** | `policy.reasoning.effort` | `low`, `medium`, `high` (console: **Off**, **Low**, **Medium**, **High**) | Models that take a reasoning effort. Other models ignore it. | | **Thinking budget** | `policy.reasoning.thinkingBudgetTokens` | 1,024 to 32,000 tokens | Extended thinking on Anthropic models. Must be smaller than the response limit. | 
```plaintext
policy:
  reasoning:
    thinkingBudgetTokens: 2048
```
 A `reasoning` block needs at least one of the two fields. Leave both out to use the model’s own behavior. ## Next steps [Section titled “Next steps”](#next-steps) * [Add knowledge](/agents/knowledge/) and [tools](/agents/tools/) to the agent. * [Tune the agent loop](/agents/policy-and-limits/) if the defaults do not fit. * [Test the agent](/agents/testing/) before you publish it.

# Add knowledge

> Create a knowledge base, upload and review documents, publish a version, and attach it to an agent from the console or with caplo knowledge.

A knowledge base holds documents an agent answers from: policies, FAQs, product guides. You manage it once in the workspace and attach it to any agent that needs it. Each upload is extracted to text and waits for review; publishing snapshots the approved documents into a version, and an agent release pins the version that was ready when it published. For how retrieval works, see [Knowledge](/concepts/knowledge/). ## Supported files [Section titled “Supported files”](#supported-files) | Type | Extensions | | ------------------------------ | -------------------------------- | | Text and Markdown | `.txt`, `.md`, `.markdown` | | Web pages | `.html` | | Documents | `.pdf`, `.docx` | | Images (text is read with OCR) | `.png`, `.jpg`, `.jpeg`, `.webp` | Each file can be up to 25 MiB. A knowledge base names documents by file name, so two documents in one base cannot share a name. ## Create a knowledge base and add documents [Section titled “Create a knowledge base and add documents”](#create-a-knowledge-base-and-add-documents) * Console 1. Open **Build > Knowledge** and select **Create knowledge base**. 2. Enter a **Name** and an **Owner** (the team responsible for the content), and optionally a **Description**. Choose the **Audience** (see [Audience](#audience)), then select **Create draft**. 3. Under **Files**, select **Choose files**, pick up to 20 files, and select **Add to draft**. Each file shows **Extracting** while Caplo reads it. 4. When a file shows **In review**, select it and check **Document review**: the **Extracted text** tab shows what was read, and **Chunks** shows the passages an agent can retrieve. Look for missing pages, tables, image text and anything sensitive. 5. Select **Approve** on each file that is correct. A file that shows **Failed** could not be extracted; upload a corrected copy. 6. Under **Approval & availability**, select **Publish version**. Caplo indexes the approved files; the base shows **Ready** when the version can be used. ![A knowledge base with its approved files, document review and Approval & availability](/_astro/knowledge-base.BfS2Wt_S_Z1dnpL.webp) Owners, Admins and Builders can create bases and upload files. Approving files and publishing versions need an Owner or Admin. * CLI 
  ```plaintext
  caplo knowledge create "Returns policy" --owner "Support operations" --description "Returns, exchanges and refunds"
  caplo knowledge sync "Returns policy" ./docs/returns --dry-run
  caplo knowledge sync "Returns policy" ./docs/returns
  caplo knowledge get "Returns policy"
  ```
 `caplo knowledge get` lists each document with its extraction and review state. Review the extracted text in the console, then approve and publish: 
  ```plaintext
  caplo knowledge approve "Returns policy"
  caplo knowledge publish "Returns policy"
  ```
 `caplo knowledge approve` waits for extraction to finish and approves every document awaiting review, or only the documents you name. It fails if a document cannot be extracted. `caplo knowledge publish` publishes a version from the approved documents and waits until it is indexed. Both wait up to 15 minutes by default; change it with `--timeout`. Approving with the CLI skips reading the extracted text. Do it when you trust the source files, for example Markdown your team maintains. ## Keep a knowledge base in sync with a folder [Section titled “Keep a knowledge base in sync with a folder”](#keep-a-knowledge-base-in-sync-with-a-folder) `caplo knowledge sync` makes a knowledge base’s documents match a directory tree, so you can keep the source files in a repository and publish from CI: 
```plaintext
caplo knowledge sync "Returns policy" ./docs/returns --approve --publish --yes
```
 What it does: * Uploads new files and files whose content changed. Files are matched by name and content, so an unchanged file is not uploaded again. * Removes documents whose file is gone from the directory. It asks first; `--yes` skips the question. * Replaces a changed file’s older copy only after the new copy is approved, so a published version never lacks the document. * Skips hidden files and directories and unsupported file types, and fails if two files in the tree share a name. With `--approve` it waits for extraction and approves the directory’s documents. With `--publish` it then publishes a version and waits for it to index. `--dry-run` prints the changes without making them. Approving and publishing need an Owner or Admin, or an API key with the `agents:publish` scope. Caution Removing a document takes it out of the next version. Versions already published keep it, and agent releases that pin those versions keep answering from it until you publish a new agent release. # Tune the agent loop

> Every policy field of an agent, with its range and default, and when to change it.

An agent’s `policy` controls how its loop runs on each turn: how many model calls, tool lookups and knowledge searches it may make, how much history it reads, and the platform text that follows your instructions. Every field is optional. A field you leave out takes the platform default, and publishing freezes that default into the release, so a release keeps the behavior it was tested with even if the defaults change later. In the console, these settings are under **Setup > Advanced settings > Agent loop**. In an agent file they are the `policy` block: 
```plaintext
policy:
  maxModelCalls: 12
  maxReads: 6
  knowledgePassages: 4
  history:
    maxTokens: 24000
  reasoning:
    effort: low
```
 ## Limits per turn [Section titled “Limits per turn”](#limits-per-turn) A turn is one customer message and everything the agent does to answer it. | Field | Console label | Range | Default | What it limits | | ------------------- | --------------------------------- | ------- | ------- | ----------------------------------------------------------------------------------------- | | `maxModelCalls` | **Model calls per turn** | 1 to 48 | 16 | Model calls of the whole agent graph in one turn: the agent and every sub-agent it calls. | | `maxReads` | **Tool lookups per turn** | 1 to 32 | 8 | Read tool calls in one turn. | | `maxParallelReads` | **Lookups at once** | 1 to 8 | 4 | Read tool calls run at the same time. | | `maxSearches` | **Knowledge searches per turn** | 1 to 16 | 4 | Knowledge searches in one turn. | | `knowledgePassages` | **Passages per knowledge search** | 1 to 8 | 6 | Passages one knowledge search returns. | | `maxDepth` | **Linked agent depth** | 1 to 4 | 3 | Sub-agent links below this agent. Checked when you validate and publish. | When to change them: * Lower `maxModelCalls` and `maxReads` to cap cost and latency on simple agents, or when an agent loops on a tool. Raise them for agents that need several lookups and sub-agent calls to answer one question. * Raise `maxParallelReads` when an agent often looks up several independent things at once. * Raise `knowledgePassages` when answers miss details that are in the documents; lower it when replies drift into unrelated passages. More passages mean more input tokens per search. * Raise `maxDepth` only when your agent tree needs another level; every level adds latency. ## History [Section titled “History”](#history) | Field | Console label | Range | Default | | ------------------- | ------------------ | ----------------------- | ------------------------------------------------------------------ | | `history.maxTokens` | **History budget** | 2,000 to 400,000 tokens | The model’s context window, less the response limit and a reserve. | `history.maxTokens` is how much earlier conversation each turn reads. Set it to cut the cost of long conversations, at the risk of the agent forgetting what was said early on. Leave it out to use as much history as the model can take. ## Reasoning [Section titled “Reasoning”](#reasoning) | Field | Console label | Values | | -------------------------------- | -------------------- | --------------------------------------------------------------------------------------------------------- | | `reasoning.effort` | **Reasoning effort** | `low`, `medium` or `high`. Used by models that take a reasoning effort; others ignore it. | | `reasoning.thinkingBudgetTokens` | **Thinking budget** | 1,024 to 32,000 tokens of extended thinking on Anthropic models. Must be smaller than the response limit. | A `reasoning` block needs at least one of the two fields. Leave it out to use the model’s own behavior. See [Set instructions and model](/agents/instructions-and-model/#reasoning-settings). ## Platform text [Section titled “Platform text”](#platform-text) Caplo adds up to three blocks of text after your instructions on each turn: guidance, the reply language, and a reply style for the kind of turn (chat or voice). In the console each has a switch (**Platform guidance**, **Platform reply language**, **Platform chat reply style**, **Platform voice reply style**). Turn the switch off to write your own text. | Field | Max length | Default text | | ------------ | ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `guidance` | 4,000 characters | “Use your tools to look up what you need before you answer. Answer questions about the business only from your instructions, this conversation and what your tools returned; when they do not cover a question, say so.” | | `language` | 2,000 characters | “Reply in the language the visitor writes in, using the same writing system they use: for example, answer Roman Urdu (Urdu written in Latin letters) in Roman Urdu, and Urdu script in Urdu script. Change language only when the visitor changes it or asks you to.” | | `chatStyle` | 2,000 characters | “You are replying in a chat: use short paragraphs, and a short list when it helps.” | | `voiceStyle` | 2,000 characters | “You are speaking on a voice call: use brief, natural spoken sentences without Markdown, lists or visual references. Before you call tools to look something up, first say one short sentence telling the caller what you are checking, without stating any result. When you can answer right away, just answer.” | * Leave a field out to use the default. * Set your own text to replace the default. * Set an empty string (`guidance: ""`) to send no block at all. You don’t need language rules in your instructions: with the reply language block on, Caplo reads the language and writing system each visitor writes in from their own messages (not from suggestions or buttons they tap), and when the conversation’s last reply used another script it reminds the agent to answer in the visitor’s. Suggested replies, tool questions and Caplo’s own fixed messages, such as a write’s confirmation text, follow the visitor’s language too (Caplo’s fixed messages come in English, Urdu and Roman Urdu). Turn the block off only when an agent must always answer in one language, and say which in your own text. Replace the guidance when your agent may answer from general knowledge, for example a writing assistant, since the default tells it to answer only from its instructions, the conversation and its tools. Replace the chat style when your brand needs a different format, for example no lists. ## See also [Section titled “See also”](#see-also) * [Agent YAML reference](/reference/agent-yaml/) for the schema. * [Usage and charges pages](/usage/usage-and-statements/) to see what model calls cost.

# Publish an agent

> Publish an agent's draft as an immutable release, choose the version, revoke releases, and deploy or roll back the release a channel serves.

Editing an agent changes only its draft. Customers talk to a **release**: an immutable snapshot of a draft that a channel serves. Publishing creates a release; deploying points a channel at it. The two are separate steps, so you can publish, test the release, and then deploy it. For the model behind this, see [Agents and releases](/concepts/agents-and-releases/). Publishing needs an Owner or Admin, or an API key with the `agents:publish` and `agents:write` scopes (plus `tools:publish` and `tools:write` when a project has tool packages, and `channels:write` to deploy). See [CI/CD](/cli/ci-cd/). ## Publish a release [Section titled “Publish a release”](#publish-a-release) * Console 1. Save your edits with **Save draft**. The **Releases** tab shows **Release readiness**: whether the saved draft is valid and what blocks publishing. 2. Select **Publish agent**. The dialog lists any remaining issues, compares the draft with the latest release, and shows each tool with the exact version and behavior the release will pin. 3. Choose the **Version bump** and write a **Release note** (required, up to 400 characters). 4. Under **Agent evals**, select **Run tests** and wait for the cases to pass. For a fast-routing agent, the **Fast routing** section lists what it still needs. 5. Select **Publish version**. ![The Releases tab with Release readiness and the published releases](/_astro/agent-releases.BYRy7G2F_ZExWsE.webp) **Publish agent** is available when the saved draft has unpublished changes and the YAML editor has no unapplied edits. * CLI Publish one agent’s saved draft: 
  ```plaintext
  caplo agent push -f support.yaml
  caplo agent publish "Support Desk"
  ```
 Or publish a whole project, packages and agents together: 
  ```plaintext
  caplo publish --dry-run
  caplo publish
  ```
 Both pin tool versions, check readiness, run the eval cases, show what will change, and ask before publishing; `--yes` skips the question. `caplo publish` publishes tool packages first, then child agents, then their parents, and on a project’s first publish to a workspace it always needs `--yes`. A CLI release gets the note “Published with the caplo CLI”. `caplo agent publish` needs the agent’s sub-agents to have releases already. `caplo publish` releases a project’s agents in the right order for you. See [The CLI workflow](/cli/workflow/). The first release is `1.0.0`. Releases are listed on the agent’s **Releases** tab and with `caplo agent release list "Support Desk"`; `caplo agent release get "Support Desk" 1.2.0` shows one with its manifest and graph digests, tools, sub-agent releases and the eval gate it was published under. Add `--manifest` to print the exact manifest that channels run, or `-o json` for the whole release. ## Version bumps [Section titled “Version bumps”](#version-bumps) Each release has a semantic version. The console and the CLI suggest the bump from what changed since the latest release: | Bump | Suggested when | | ----- | ------------------------------------------------------------------------------------------------------------------- | | Major | The first release; any change to sub-agents; a changed provider or model; a removed tool, action or knowledge base. | | Minor | An added tool, action or knowledge base. | | Patch | Anything else, such as instructions, greeting, temperature or policy. | Choose another bump in the dialog, or with `caplo agent publish "Support Desk" --bump minor`. The version is a label for people; channels and parents pin a release, not a version range. ## What a release pins [Section titled “What a release pins”](#what-a-release-pins) A release freezes everything the agent needs to behave the same way every time: * The whole configuration: instructions, greeting, model and its settings, actions, routing, suggested replies and ratings. * The policy, with each field you left out filled with the platform default of the day. * Each tool package at its latest published version, with each tool’s schema and read or write effect. See [Give an agent tools](/agents/tools/#how-releases-pin-tool-versions). * Each knowledge base at its ready version. See [Add knowledge](/agents/knowledge/#versions-and-agent-releases). * Each sub-agent at an exact release. See [Release pinning](/agents/sub-agents-and-routing/#release-pinning). A release does not pin eval cases. When only the cases change, `caplo publish` runs them against the released draft and keeps the release. To pick up newer tool package versions without other changes, run `caplo agent publish` or `caplo publish`: they save a new draft revision and publish it. A newer knowledge version or child release needs a draft change to publish. ## Deploy a release to channels [Section titled “Deploy a release to channels”](#deploy-a-release-to-channels) Publishing does not change what channels serve. Each channel keeps its release until you deploy another. * Console Open the agent’s **Channels** tab. A channel serving an older release offers an **Update to** link with the newer version; select it to review and deploy. **Change agent or release** opens the channel’s settings to pick any release. See [Channels](/channels/). * CLI 
  ```plaintext
  caplo channel deploy Website
  caplo channel deploy whatsapp/Support --agent "Support Desk@1.2.0"
  ```
 Without `--agent`, each channel moves to its agent’s newest release that is not revoked. `--agent` names the agent and, after `@`, a version or release number. A channel is named by ID, name, or `<kind>/<name>`. Every other channel setting stays as it is. The command asks first; `--yes` skips the question. In a project, an [environment](/cli/environments/) can list `channels` that `caplo publish` deploys after it publishes. A deploy affects new conversations only. Conversations already open keep the release they started with, so a customer never sees the agent change mid-conversation. ## Roll back [Section titled “Roll back”](#roll-back) To return channels to the release before the one they serve: 
```plaintext
caplo channel rollback Website
```
 It points each channel at its agent’s newest release that is older than the current one and not revoked, served exactly as it was published. To move forward again, deploy or publish a newer release. Rolling back does not change the agent’s draft. ## Revoke a release [Section titled “Revoke a release”](#revoke-a-release) Revoking marks a release as unusable, for example one that gives wrong refund advice: 
```plaintext
caplo agent release revoke "Support Desk" 1.2.0 --reason "wrong refund policy"
```
 `--reason` is required, and the command asks first. Revoking cannot be undone Channels that serve a revoked release and parent agents that pin it can no longer run it. Deploy or roll back those channels, and publish those parents with another release, before you revoke. Links at `release: latest`, `caplo channel deploy` and `caplo channel rollback` skip revoked releases. ## See also [Section titled “See also”](#see-also) * [Write and run evals](/agents/evals/) for the publication gate. * [CI/CD](/cli/ci-cd/) to publish from a pipeline.

# Offer suggested replies and collect ratings

> Turn on suggested replies under an agent's messages and let website visitors rate its replies, and find the ratings in Conversations.

Two optional agent settings shape what visitors see under the agent’s replies: suggested replies they can tap instead of typing, and a thumbs up or down to rate a reply. Both are off by default. Both are part of the agent’s draft, so they reach customers when you publish a release and a channel serves it. ## Suggested replies [Section titled “Suggested replies”](#suggested-replies) Suggested replies are short next messages, such as “Track my order” or “Talk to a person”, offered under a reply the agent writes. A visitor taps one to send it. ![An agent reply in the website widget followed by three suggested replies](/_astro/widget-suggestions.Bce5GyCd_2wj5Gf.webp) **Console:** open the agent, go to **Setup > Advanced settings > Suggested replies**, turn on **Offer suggested replies**, and set **Most suggestions** (1 to 4). Select **Save draft**. **Agent YAML:** 
```plaintext
suggestedReplies:
  maxCount: 3
```
 `maxCount` is the most suggestions under one reply, 1 to 4, and 3 when you leave it out. An empty block (`suggestedReplies: {}`) turns them on with 3. Leave the block out to turn them off. Where they appear: * The website widget, the console’s live test, and messaging channels that can show them. `caplo agent chat` does not print them. WhatsApp, Messenger and Instagram show at most 3, as reply buttons, whatever `maxCount` says. * Never on voice calls. * Only under replies the agent writes itself. A sub-agent that [takes over the conversation](/agents/sub-agents-and-routing/#modes) uses its own setting; a sub-agent the agent asks for an answer never offers any. The agent does not offer suggestions when its reply asks for the visitor’s own details, such as a name, email address or order number, since any suggestion would have to invent them. Suggestions come from one extra short model call after the reply, which is counted and billed like the agent’s other model calls. If that call fails or the turn has no budget left for it, the reply is sent without suggestions. ## Visitor ratings [Section titled “Visitor ratings”](#visitor-ratings) With ratings on, the website widget shows a thumbs up and a thumbs down under the agent’s replies. A visitor who gives a thumbs down can add a reason. **Console:** open the agent, go to **Setup > Advanced settings > Reply ratings**, turn on **Let visitors rate replies**, and select **Save draft**. **Agent YAML:** 
```plaintext
visitorFeedback: true
```
 Leave the field out to turn ratings off. Ratings apply to the website widget only. The setting is frozen into a channel when the channel is deployed with a release, so after you publish, [deploy the website channel](/agents/publishing/#deploy-a-release-to-channels) to the new release to start collecting ratings. ### Where operators see ratings [Section titled “Where operators see ratings”](#where-operators-see-ratings) Open **Monitor > Conversations** and select a conversation. A rated reply shows **Rated helpful by the visitor** or **Rated not helpful by the visitor**, with the visitor’s reason when they gave one. The rating shown is the visitor’s current one, so a changed vote replaces the earlier rating. The agent never sees ratings; they do not change its replies. Use them to find answers to fix, then turn those conversations into [eval cases](/agents/evals/) so the fix stays fixed. ## See also [Section titled “See also”](#see-also) * [Website widget settings](/channels/website-widget/settings/) * [Conversations and handoff](/concepts/conversations-and-handoff/)

# Add sub-agents and routing

> Link other agents as sub-agents, choose how each one works with the parent, pin their releases, and choose model or fast routing.

An agent can call other agents in the workspace. Each sub-agent is an ordinary agent with its own instructions, tools and knowledge, so you can build focused specialists (orders, returns, billing) once and reuse them under several parents. For when to split an agent and how calls flow, see [Multi-agent](/concepts/multi-agent/). ## Add a sub-agent [Section titled “Add a sub-agent”](#add-a-sub-agent) * Console 1. Open the parent agent and select the **Sub-agents** tab. 2. Select **Add existing agent** and choose a **Workspace agent**, or select **Create agent** to create a new draft agent and link it in one step. 3. Choose the **Release to use**. The child needs a published release before the parent can publish. 4. Fill in **Use when** and, optionally, **Do not use when**. 5. Choose how the sub-agent **Works as** (see [Modes](#modes)), then select **Add agent**. 6. Select **Save draft**. ![The Sub-agents tab of a parent agent with fast routing and four linked agents](/_astro/sub-agents.CsV8GDWX_7Hso8.webp) A link shows **Needs release** while its child has no release. When the child publishes a newer release, the link shows it and offers a **Use** button with that version **in draft**; the parent keeps its fixed release until you adopt the new one and publish the parent. **View agent graph** shows the whole tree. * CLI Add `subAgents` to the parent’s agent file. In a project, link another project agent by its file key with `local`; link any workspace agent by ID with `agentId`: 
  ```plaintext
  subAgents:
    - local: orders
      release: latest
      useWhen: The customer asks about an existing order, its shipment or delivery.
      doNotUseWhen: General product or policy questions with no order involved.
      mode: task_tool
    - agentId: 6f0c2a8e-4b1d-4e7a-9c3f-2d5b8a1e7f40
      release: 2.1.0
      useWhen: The customer asks how returns or refunds work in general.
      doNotUseWhen: Starting a return for a specific order.
  ```
 `caplo publish` publishes children before parents. A single agent published with `caplo agent publish` needs its sub-agents to have releases already. ## Link fields [Section titled “Link fields”](#link-fields) | Console label | YAML field | Required | Description | | ------------------- | -------------------- | ---------------- | ----------------------------------------------------------------------------------------------- | | **Workspace agent** | `agentId` or `local` | One of them | The child agent. `local` is a file key in the same project. | | **Release to use** | `release` | No | `latest` (default) or a fixed version such as `2.1.0`. See [Release pinning](#release-pinning). | | **Use when** | `useWhen` | Yes | When the parent should call this agent. Up to 2,000 characters. | | **Do not use when** | `doNotUseWhen` | For fast routing | Requests that belong to the parent or another agent. | | **Works as** | `mode` | No | `task_tool` (default) or `active_conversation`. | Write `useWhen` and `doNotUseWhen` as plain descriptions of customer requests. The parent’s model reads them to decide, and fast routing relies on them entirely. ## Modes [Section titled “Modes”](#modes) | Mode | Console label | What happens | | --------------------- | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `task_tool` | **Answers and returns to this agent** | The parent asks the sub-agent in plain words, the sub-agent works with its own tools and knowledge, and the parent writes the reply. The sub-agent remembers earlier requests in the same conversation. | | `active_conversation` | **Takes over the conversation** | The sub-agent becomes the agent the customer talks to for the rest of the conversation, or until it hands back. | A sub-agent always runs with its own release’s tools, knowledge and settings, not the parent’s. Writes a sub-agent proposes are confirmed by the customer the same way as the parent’s. ## Release pinning [Section titled “Release pinning”](#release-pinning) Every published parent release pins an exact release of each child, so a child’s change never alters a published parent on its own. * A fixed version (`release: 2.1.0`, or the console’s **Release to use**) keeps that child release until you change the link and publish the parent again. * `release: latest` resolves to the child’s newest release that is not revoked when you push or publish the parent. With `caplo publish`, a child that publishes a new release also republishes the project agents that link it at `latest`. When you link an existing agent in the console, the link pins the release you choose. Exported YAML writes `latest` only for a link without a fixed release, and `caplo pull` writes the release the draft pins. Caution Revoking a child release stops every parent release that pins it from running that child. Publish the parents with a usable child release first. See [Publish an agent](/agents/publishing/#revoke-a-release). ## Depth limit [Section titled “Depth limit”](#depth-limit) Sub-agents can have sub-agents of their own. `policy.maxDepth` (**Linked agent depth** in the console) caps how many sub-agent links may sit below an agent: 1 to 4, default 3. Links cannot form a cycle. `caplo validate` checks both offline. ## Routing [Section titled “Routing”](#routing) Routing decides how a parent picks a sub-agent for each customer message. | Mode | Console label | Behavior | | ----------------- | --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | | `model` (default) | **The model decides** | The parent’s model reads the conversation and calls a sub-agent or answers itself. Takes about 2 seconds. | | `fast` | **Fast routing** | A separate decision call picks a sub-agent in about 0.3 seconds. When its confidence is below `minConfidence`, the model decides instead. | 
```plaintext
routing:
  mode: fast
  minConfidence: 0.85
```
 `minConfidence` (**Minimum confidence**, under **Advanced** in the console) is 0.60 to 0.99, default 0.85. Raise it if fast routing picks the wrong agent; lower it if too many turns fall back to the model. Omit the `routing` block for model routing. Fast routing needs: * At least one sub-agent, and `doNotUseWhen` on every link. A draft that lacks one cannot be saved. * **Fast decisions** turned on for the workspace. An Owner or Admin enables it in **Settings > AI providers** and accepts the provider’s data processing terms, because the visitor’s recent messages and your sub-agent descriptions are sent to the decision provider. See [Fast decisions](/providers/fast-decisions/). If Fast decisions are turned off later, agents set to fast routing fall back to the model on their next turn. * Routing eval cases to publish. While the workspace requires evals, each direct sub-agent needs passing cases that set `routedBy` and name it in `subAgent`: two per sub-agent by default, set by **Passing routing cases per sub-agent** in **Settings > General**. See [Routing cases](/agents/evals/#routing-cases). ## Next steps [Section titled “Next steps”](#next-steps) * [Write routing eval cases](/agents/evals/#routing-cases). * [Publish the children, then the parent](/agents/publishing/).

# Test an agent

> Chat with a draft or a release in the console's live test or with caplo agent chat, decide tool writes, and manage your test sessions.

Test an agent by talking to it before customers do. A test runs in a private conversation that no channel serves, against either the current draft or a published release. Tests are for exploring; [eval cases](/agents/evals/) are the repeatable checks that gate publishing. Tests use real tools A test is not a sandbox. The agent’s tools call their real connections, can read your systems and can change business data. Tools set to run without confirmation act on their own. Use test accounts and test data in the systems your tools reach. ## Test in the console [Section titled “Test in the console”](#test-in-the-console) The **Live test** panel sits beside the agent editor. 1. Open the agent. In **Live test**, choose the **Test target**: **Current editor changes** (your edits, saved or not) or a **Published** release. 2. The first time, read the notice, check **I understand this test can use real tools and change business data.**, and select **Enable live test**. 3. Type a message, or select **Start voice** to talk to the agent with your microphone. **End call** stops a voice test. 4. When the agent proposes a write, such as creating a return, the chat shows the request with its details. Confirm or cancel it there, as a customer would. 5. After you change the draft, select **Apply changes** to start a new chat with your edits. **New chat** starts over at any time. **Expand** opens a larger view with the chat and **Monitor** side by side. **Monitor** shows the steps of each turn as the agent works, with filters for agent, step type and **Errors only**. **Agent progress and diagnostics** lists the sub-agents and tools the chat used, with statuses and error codes only. You need a role that can edit the agent (Owner, Admin or Builder) to test it. A live test follows the confirmation rules of the agent’s tools, and the agent may treat a plain “yes” typed in the chat as confirmation of a write it asked about. Use the buttons when you want an explicit decision. ![The Live test panel before live testing is enabled](/_astro/agent-live-test.BxSfDutx_Z2rYcEB.webp) ## Test with the CLI [Section titled “Test with the CLI”](#test-with-the-cli) `caplo agent chat` starts a private test conversation with the agent’s saved draft and reads one message per line: 
```plaintext
caplo agent push -f support.yaml
caplo agent chat "Support Desk"
```
 It tests the draft as last saved, so push or save your edits first. To test a release instead: 
```plaintext
caplo agent chat "Support Desk" --release 2.1.0
```
 `--release` takes a version or a release number. Each reply is printed after one line per sub-agent call (its mode and status) and per tool call (its effect and status) that the turn made, so you can see how the agent reached its answer. ### Confirm or cancel writes [Section titled “Confirm or cancel writes”](#confirm-or-cancel-writes) When the agent proposes a write, the chat prints the request for review. Answer it with a command on its own line: | Input | Effect | | ------------------------------ | ------------------------------------------------------------------- | | `/confirm` | Approves the write shown last, as the widget’s confirm button does. | | `/cancel` | Declines it. | | `/exit` or `/quit` (or Ctrl-D) | Ends the chat and closes the test session. | Some writes can only be declined here: one that has no review in the CLI, or one waiting for the customer to sign in. If the write changes before you answer, the current one is shown and you answer again. You can script a test by piping input: 
```plaintext
printf 'Return the boots from order 1042\n/confirm\n' | caplo agent chat "Support Desk"
```
 The command exits with status 1 if a message or decision could not be sent, and, when it is not run in a terminal, with status 3 if a turn failed. See [Exit codes](/reference/cli/#exit-codes). ## Test sessions [Section titled “Test sessions”](#test-sessions) Each test chat holds a test session, and a workspace has limited test capacity. A chat closes its session when it ends. If a chat stops abruptly or capacity runs out, `caplo agent chat` reports that no test session is free. List and close your open sessions: 
```plaintext
caplo agent sessions list
caplo agent sessions close 4d2f8b1e-6c3a-4f7e-9d05-1a2b3c4d5e6f
```
 `caplo agent sessions list` shows each of your open sessions across agents with its agent, last activity and how long it may keep running. You can list and close only your own sessions. ## What to test [Section titled “What to test”](#what-to-test) * The greeting and a few typical questions. * A question the agent should not answer, and one it cannot answer, to check it says so. * Each tool: a lookup that succeeds, one that finds nothing, and a write you confirm and one you cancel. * Each sub-agent, with a message that should route to it and one that should not. * A request for a person, if the agent can [hand off](/agents/handoff-and-end-actions/). Turn what you learn into [eval cases](/agents/evals/), then [publish](/agents/publishing/).

# Give an agent tools

> Attach tool package tools and remote MCP server tools to an agent, name them in agent YAML, and understand how releases pin tool versions.

Tools let an agent look things up and act in your systems: find an order, check stock, book an appointment. An agent can use two kinds of tools: * **Tool package tools**: code you write and publish in the workspace with the Caplo tool SDK. See [Build tools](/tools/). * **Remote MCP server tools**: tools of an MCP server you connect to the workspace and publish after review. See [Connect a remote MCP server](/tools/remote-mcp/). Both appear in the same list on the agent. A tool must be published before an agent release can use it. ## Attach tools [Section titled “Attach tools”](#attach-tools) * Console 1. Open the agent and select the **Tools & actions** tab. 2. Each tool package and remote MCP server is listed as a group. Check the group to give the agent **All tools, including tools added in later versions**, or expand it and check single tools. 3. Select **Details** on a tool to see its description, input and output schemas, whether it reads or writes, and how it appears to customers. 4. Select **Save draft**. ![The Tools & actions tab of an agent, with conversation actions and tool package groups](/_astro/agent-tools.C2rCb86E_Z2jDHdJ.webp) Each group shows how many of its tools are selected, its latest version, and the version the agent’s latest release pins. A tool marked **Blocks publishing if selected** (for example **Build pending**) has no usable published version yet; the agent cannot publish while it is selected. * CLI List the tools under `tools` in the agent file, then push it: 
  ```plaintext
  tools:
    - order-desk/lookup_order
    - order-desk/track_shipment
    - helpdesk/create_ticket
  ```
 Then run `caplo push` in a project, or `caplo agent push -f <file>` for a single agent file. ## Tool names in agent YAML [Section titled “Tool names in agent YAML”](#tool-names-in-agent-yaml) | Form | Meaning | | --------------------------------------- | ------------------------------------------------------------------------------------------ | | `<package>/<tool>` | One tool of a tool package in your project (`tools/<package>/caplo.yaml`). | | `<package>` | Every tool of that project package, including tools added in later versions. | | `<server>/<tool>` | One published tool of a workspace remote MCP server, by the server’s name. | | `<package ID>/<tool>` or `<package ID>` | A workspace tool package by its ID. This is the form the console’s **Export YAML** writes. | Inside a project, a name that is not a project package is looked up as a remote MCP server when you run `caplo diff`, `caplo push` or `caplo publish`. Outside a project, names refer to remote MCP servers, and packages are named by ID. Tool names are lowercase letters, digits and underscores, starting with a letter. An agent can reference at most 32 tools or packages. ## How releases pin tool versions [Section titled “How releases pin tool versions”](#how-releases-pin-tool-versions) The draft names packages and tools; it does not name versions. When you publish the agent, Caplo resolves each package to its latest published version and freezes that version into the release, together with each tool’s schema and its read or write effect. A release keeps running the tool versions it was published with, even after the package publishes again. If a pinned tool version is revoked, the release can no longer run it; publish a new release that pins a usable version. To move an agent to newer tool versions, publish a new release: * `caplo agent publish <agent>` publishes again when the agent’s packages have newer versions, even if the draft has not changed. * `caplo publish` in a project publishes changed packages first, then republishes every agent that uses them. * In the console, **Publish agent** needs unpublished draft changes. The publish dialog lists each tool with the exact version and behavior the release will pin. Selecting a whole package picks up tools the package adds in later versions at your next publish. Selecting single tools keeps the agent to exactly those tools. ## Conversation actions [Section titled “Conversation actions”](#conversation-actions) The **Tools & actions** tab also holds the agent’s conversation actions: transfer to a human and ending a voice call. See [Handoff and end actions](/agents/handoff-and-end-actions/). ## Next steps [Section titled “Next steps”](#next-steps) * [Write a tool package](/tools/first-tool/). * [Add eval cases](/agents/evals/) that check the agent calls the right tool (`tool` in a case).
