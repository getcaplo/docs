# Log in and use API keys

> Log in to the caplo CLI as yourself, see where the session is kept, change CLI settings, and create API keys for CI and automation.

The CLI authenticates in one of two ways: * **As you**, after `caplo auth login`. Commands act with your workspace role, the same as in the console. * **As an API client**, when `CAPLO_API_KEY` holds an API key. Commands act with the key’s scopes. Use this in CI and other automation where nobody can log in. ## Log in [Section titled “Log in”](#log-in) 
```sh
caplo auth login
```
 1. The CLI opens your browser at the Caplo sign-in page. If it does not open, copy the URL the CLI prints. 2. Sign in as you do in the console. The browser then shows that you are logged in to the Caplo CLI, and you can close it. 3. The CLI prints your name and email. If you belong to exactly one workspace, it selects that workspace. If you belong to several, run `caplo workspace use <name>` to choose one; see [Workspaces](/cli/workspaces/). The browser returns to a short-lived listener on `127.0.0.1` on your machine, so the browser and the CLI must run on the same computer. The sign-in must finish within five minutes. ### On a machine without a browser [Section titled “On a machine without a browser”](#on-a-machine-without-a-browser) On a remote server, in a container, or over SSH, use the device flow: 
```sh
caplo auth login --device
```
 The CLI prints a URL and a code. Open the URL on any device, sign in, and confirm the code; the CLI finishes as soon as you do. `--no-browser` only stops the CLI from opening a browser itself. It still needs a browser on the same machine to finish, so prefer `--device` when there is none. ### Check and end the session [Section titled “Check and end the session”](#check-and-end-the-session) 
```sh
caplo auth status
caplo auth logout
```
 `caplo auth status` shows who you are logged in as, the API and sign-in server, where the session is stored, and the selected workspace. With `CAPLO_API_KEY` set, it shows the API client, its workspace and its scopes instead. `caplo auth logout` deletes the stored session from your machine and then ends it on the server. If ending it on the server fails, the CLI says so; the local copy is already gone. ## Where the session is stored [Section titled “Where the session is stored”](#where-the-session-is-stored) Logging in creates a long-lived session. The CLI keeps it as a refresh token and gets short-lived access tokens from it as needed; access tokens stay in memory and are never written to disk. Several `caplo` commands can run at once safely. | Storage | Where | When | | -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- | | `keychain` (default) | The operating system’s credential store: macOS Keychain, Windows Credential Manager, or the Secret Service (such as GNOME Keyring) on Linux, under the service name `caplo` | Desktops and laptops | | `file` | `credentials.json` in the configuration directory, readable only by your user (mode 0600) | Machines without a credential store, such as a minimal Linux server | To use file storage, log in with `--insecure-storage`, or set it first with `caplo config set credential-storage file`. The choice is saved and applies to later logins too. Caution Anyone who can read `credentials.json` can act as you in Caplo until you log out. Use file storage only on a machine and account you control, and prefer an [API key](#api-keys-for-automation) for unattended jobs. The configuration directory is `CAPLO_CONFIG_DIR` if set, otherwise `$XDG_CONFIG_HOME/caplo` or `~/.config/caplo` on macOS and Linux, and `%AppData%\caplo` on Windows. It holds `config.yaml` with your settings and selected workspace, and `credentials.json` when you use file storage. ## CLI settings [Section titled “CLI settings”](#cli-settings) `caplo config` shows and changes the settings in `config.yaml`: 
```sh
caplo config list
caplo config get api-url
caplo config set credential-storage file
```
 | Key | Default | What it is | | -------------------- | ------------------------------------ | ------------------------------------------------ | | `api-url` | `https://api.caplo.si` | The Caplo API the CLI calls. | | `issuer` | `https://auth.caplo.si/realms/caplo` | The sign-in server. | | `client-id` | `caplo-cli` | The sign-in client the CLI identifies as. | | `credential-storage` | `keychain` | Where the session is kept: `keychain` or `file`. | `caplo config list` also shows the selected workspace. You only need to change `api-url`, `issuer` or `client-id` if Caplo support gives you different values. Changing `api-url` clears the selected workspace. After changing a setting, run `caplo auth login` again. When you log in, the API and sign-in server come from, in order: the `--api-url` and `--issuer` flags, the `CAPLO_API_URL` and `CAPLO_ISSUER` environment variables, the saved settings, then the defaults above. A successful login saves them. To keep two separate logins on one machine, give each its own `CAPLO_CONFIG_DIR`. ## API keys for automation [Section titled “API keys for automation”](#api-keys-for-automation) An API client is a workspace identity for CI and scripts. It is not a member: it has no role, cannot use the console, and can only do what its scopes allow in its own workspace. Each client can have several keys, so you can rotate a key without downtime. Keys start with `caplo_sk_`. ### Who can create one [Section titled “Who can create one”](#who-can-create-one) Workspace Owners, Admins and Developers can manage API clients. You can only give a client scopes whose actions your own role holds: for example, a Developer can create a client with tool scopes but not with `agents:write` or `agents:publish`. See [Workspaces and roles](/concepts/workspaces-and-roles/). ### Create a client [Section titled “Create a client”](#create-a-client) * Console 1. Open **Settings**, then **API access**. 2. Click **Create client**, enter a **Client name**, and turn on the permissions it needs. 3. Click **Create key** and copy the key from **Copy your API key**. It is shown only once. * CLI Log in as yourself, select the workspace, then: 
  ```sh
  caplo workspace api-client create github-deploy \
    --scope agents:write,agents:publish,tools:write,tools:publish
  ```
 The key is printed once on standard output, so you can pipe it straight into your CI’s secret store. Repeat `--scope` or separate scopes with commas. Store the key as a secret in your CI system right away. Caplo keeps only a hash of it and cannot show it again. ### Scopes [Section titled “Scopes”](#scopes) A write or publish scope includes the read scope of the same resource. | Scope | Console label | Allows | | ---------------- | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `agents:read` | Read agents | Read agents, releases, eval suites and runs, and knowledge bases | | `agents:write` | Edit agents and knowledge | Create agents, save drafts and eval suites, create knowledge bases and upload documents | | `agents:publish` | Publish agents and knowledge | Run evals, publish and revoke agent releases, archive and delete agents, change the workspace’s publication requirements (including turning off the eval requirement), approve documents and publish knowledge versions | | `tools:read` | Read tools | Read tool packages, builds, versions, logs, remote MCP servers and secret names | | `tools:write` | Edit tools | Create and upload packages, build them, run remote fixtures, archive and delete packages, review remote MCP server tools | | `tools:publish` | Publish tools | Publish and revoke package versions, publish remote MCP server tools, set a package’s own secret values | | `channels:read` | Read channels | Read channels and the release each serves | | `channels:write` | Deploy to channels | Point channels at a release and roll them back. It also allows creating, editing, pausing and deleting channels and editing and publishing widget designs, so grant it only to automation you trust with your channels. | The workspace also accepts `conversations:read`, `usage:read`, `endpoints:read` and `endpoints:write`, but no Caplo API accepts API keys for them yet. See [API keys](/admin/api-keys/). ### Use the key [Section titled “Use the key”](#use-the-key) Set two environment variables. The CLI then authenticates as the client for every command, instead of any login on the machine: 
```sh
export CAPLO_API_KEY=<API_KEY>
export CAPLO_WORKSPACE=<WORKSPACE_ID>
caplo auth status
```
 `CAPLO_WORKSPACE` (or `--workspace`, or a project [environment](/cli/environments/)) must name the client’s workspace by ID, not by name, because a key cannot list workspaces. The CLI checks that the key belongs to that workspace before it does anything else. `caplo workspace get` while logged in, or the console, shows the ID. The key calls `CAPLO_API_URL` if set, then the saved `api-url`, then `https://api.caplo.si`. ### What works with an API key [Section titled “What works with an API key”](#what-works-with-an-api-key) | Commands | Scopes needed | | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | | `caplo validate`, `caplo test`, `caplo identity` | None: they do not call the Caplo API | | `caplo diff`, `caplo pull`, `caplo agent list`, `get` and `pull` | `agents:read`, plus `tools:read` when packages are involved | | `caplo push`, `caplo agent push` | `agents:write`, plus `tools:write` when the project has packages | | `caplo eval`, `caplo agent eval run` | `agents:write` and `agents:publish`, plus `tools:write` with packages | | `caplo publish`, `caplo agent publish` | `agents:write` and `agents:publish`, plus `tools:write` and `tools:publish` with packages, plus `channels:write` when the environment deploys channels | | `caplo tool` list, push, build, publish and version commands, `caplo tool secret set` and `unset` | `tools:read`, `tools:write` or `tools:publish` | | `caplo mcp list`, `get`, `tools`, `review` and `publish` | `tools:read`, `tools:write` or `tools:publish` | | `caplo secret list` and `usage`, `caplo tool secret list` | `tools:read` | | `caplo knowledge` | `agents:read`; `agents:write` to create and sync; `agents:publish` to approve and publish | | `caplo channel list` and `get` | `channels:read` and `agents:read` | | `caplo channel deploy` and `rollback` | `channels:write` and `agents:read` | These need a person’s login and do not work with an API key: * `caplo workspace` commands, including `caplo workspace api-client`: an API client cannot manage workspaces or other clients. * `caplo secret set` and `delete`, and `caplo tool secret bind` and `unbind`: managing workspace secrets needs a member with the secrets permission. * `caplo mcp add`, `update`, `remove`, `check`, `connect` and `refresh`: connecting remote MCP servers needs a member who can manage integrations. * `caplo agent chat` and `caplo agent test`: test conversations belong to a person. If the API refuses a key, the CLI says that an API key cannot do this or that it was revoked. Check the scopes with `caplo auth status`. ### Rotate a key [Section titled “Rotate a key”](#rotate-a-key) Add a new key, switch your CI secret to it, then revoke the old ones: 
```sh
caplo workspace api-client rotate github-deploy
caplo workspace api-client revoke github-deploy --except <NEW_KEY_ID_OR_PREFIX>
```
 `rotate` prints the new key once and leaves the old keys active, so nothing breaks while you update the secret. `caplo workspace api-client list` shows each client’s scopes and the prefixes of its active keys. In the console, use **Add rotation key** on the client. ### Revoke keys [Section titled “Revoke keys”](#revoke-keys) 
```sh
caplo workspace api-client revoke github-deploy
caplo workspace api-client revoke github-deploy --key <KEY_ID_OR_PREFIX>
```
 Without `--key`, every active key of the client is revoked. The command asks first; pass `--yes` in scripts. Anything still using a revoked key stops working at once. A client’s scopes cannot be changed; to change them, create a new client and revoke the old one’s keys.

# Publish from CI/CD

> Run caplo in GitHub Actions or GitLab CI with an API key to validate and test every change and publish from your main branch.

Keep your [project](/cli/projects/) in Git and let a pipeline publish it: every pull request is validated and its tool fixtures run, and every merge to `main` is evaluated and published. Nobody publishes from a laptop, and the release history matches your commit history. In CI there is nobody to log in, so the CLI authenticates with an **API key** instead. See [API keys for automation](/cli/authentication/#api-keys-for-automation) for how keys and scopes work. ## Set up the key [Section titled “Set up the key”](#set-up-the-key) 1. Log in as a workspace Owner or Admin, so you can grant agent scopes, and select the workspace you publish to. 2. Create an API client with the scopes a publish needs, and send its key straight into your repository’s secrets without printing it. With the [GitHub CLI](https://cli.github.com): 
   ```sh
   caplo workspace api-client create github-deploy \
     --scope agents:write,agents:publish,tools:write,tools:publish \
     | gh secret set CAPLO_API_KEY
   ```
 Add `channels:write` if an [environment](/cli/environments/#deploy-channels) deploys channels. Leave out the `tools` scopes if the project has no tool packages. 3. Store the workspace ID as `CAPLO_WORKSPACE`. It is not secret, but keeping it next to the key keeps them in step: 
   ```sh
   caplo workspace get -o json
   gh secret set CAPLO_WORKSPACE --body <WORKSPACE_ID>
   ```
 With an API key, the workspace must be given by ID, never by name. ## GitHub Actions [Section titled “GitHub Actions”](#github-actions) Save this as `.github/workflows/caplo.yml`. It pins the CLI version, so a new CLI release never changes your pipeline until you update the pin. 
```yaml
name: Caplo


on:
  pull_request:
  push:
    branches: [main]


permissions:
  contents: read


env:
  CAPLO_VERSION: v0.4.0


jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 24
      - name: Install the Caplo CLI
        run: |
          curl -fsSL "https://raw.githubusercontent.com/getcaplo/homebrew-tap/$CAPLO_VERSION/install.sh" | sh
          echo "$HOME/.local/bin" >> "$GITHUB_PATH"
      - name: Install tool package dependencies
        run: |
          for dir in tools/*/; do
            if [ -f "$dir/package.json" ]; then npm ci --prefix "$dir"; fi
          done
      - run: caplo validate
      - run: caplo test


  publish:
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    needs: check
    runs-on: ubuntu-latest
    concurrency: caplo-publish
    env:
      CAPLO_API_KEY: ${{ secrets.CAPLO_API_KEY }}
      CAPLO_WORKSPACE: ${{ secrets.CAPLO_WORKSPACE }}
    steps:
      - uses: actions/checkout@v4
      - name: Install the Caplo CLI
        run: |
          curl -fsSL "https://raw.githubusercontent.com/getcaplo/homebrew-tap/$CAPLO_VERSION/install.sh" | sh
          echo "$HOME/.local/bin" >> "$GITHUB_PATH"
      - run: caplo auth status
      - run: caplo eval
      - run: caplo publish --yes
```
 What each part does: * **`check`** runs on every pull request and push. `caplo validate` and `caplo test` need no key and call no workspace, so they also run for pull requests from forks. `npm ci` needs each package’s `package-lock.json` committed. * **`publish`** runs only on pushes to `main`. `caplo auth status` prints the API client and its scopes, which makes a wrong key easy to spot in the log. `caplo eval` pushes the drafts and runs every agent’s eval cases, so a failing case stops the job before anything is published. `caplo publish --yes` then publishes bottom up, reusing a passing eval run wherever the draft has not changed since. * **`--yes`** is required: without a terminal, a publish that would ask for confirmation stops with exit code 2. It also covers the project’s first publish to the workspace. * **`concurrency`** stops two publishes from running against the same workspace at once. The install script checks the archive’s SHA-256 checksum before installing. To also gate publishing on a reviewer, put the `publish` job in a [GitHub environment](https://docs.github.com/actions/deployment/targeting-different-environments/using-environments-for-deployment) with required reviewers. Caution Do not run `caplo push`, `caplo eval` or `caplo publish` on pull requests against the workspace that serves customers. `push` and `eval` overwrite the workspace drafts with the pull request’s files, and two open pull requests would overwrite each other. Use a separate staging workspace for that, or limit pull requests to `caplo validate`, `caplo test` and `caplo diff`. ### Show the plan on pull requests [Section titled “Show the plan on pull requests”](#show-the-plan-on-pull-requests) To see what a merge would change, add a step to `check` with a key that has only `agents:read` and `tools:read`: 
```yaml
      - run: caplo diff
        env:
          CAPLO_API_KEY: ${{ secrets.CAPLO_READ_KEY }}
          CAPLO_WORKSPACE: ${{ secrets.CAPLO_WORKSPACE }}
```
 `caplo diff -o json` prints the same plan as one JSON document, to post as a comment or check with a policy; see [Plans as JSON](/cli/scripting/#plans-as-json). ### Staging and production [Section titled “Staging and production”](#staging-and-production) With [environments](/cli/environments/) in `caplo.yaml`, give each its own API client and secret, and select the environment per job: 
```yaml
      - run: caplo publish --env staging --yes
        env:
          CAPLO_STAGING_KEY: ${{ secrets.CAPLO_STAGING_KEY }}
```
 For production, run a separate job, for example on `workflow_dispatch` or a tag, that sets both keys. With `promoteFrom: staging`, the CLI reads staging with `CAPLO_STAGING_KEY` and refuses any agent staging has not released from the same source: 
```yaml
      - run: caplo publish --env prod --yes
        env:
          CAPLO_PROD_KEY: ${{ secrets.CAPLO_PROD_KEY }}
          CAPLO_STAGING_KEY: ${{ secrets.CAPLO_STAGING_KEY }}
```
 Do not also set `CAPLO_WORKSPACE` in these jobs unless it matches the environment’s `workspace` exactly; a different value stops the command with exit code 2. ## GitLab CI [Section titled “GitLab CI”](#gitlab-ci) Add `CAPLO_API_KEY` and `CAPLO_WORKSPACE` under **Settings**, **CI/CD**, **Variables** in GitLab, masked and protected so only protected branches can read them. Then in `.gitlab-ci.yml`: 
```yaml
stages: [check, publish]


variables:
  CAPLO_VERSION: v0.4.0


default:
  image: node:24
  before_script:
    - curl -fsSL "https://raw.githubusercontent.com/getcaplo/homebrew-tap/$CAPLO_VERSION/install.sh" | sh
    - export PATH="$HOME/.local/bin:$PATH"


check:
  stage: check
  script:
    - for dir in tools/*/; do if [ -f "$dir/package.json" ]; then npm ci --prefix "$dir"; fi; done
    - caplo validate
    - caplo test


publish:
  stage: publish
  resource_group: caplo-publish
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
  script:
    - caplo eval
    - caplo publish --yes
```
 ## Exit codes [Section titled “Exit codes”](#exit-codes) Pipelines stop on any non-zero exit code. The code tells you where to look: | Code | Meaning in CI | Typical fix | | ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- | | `0` | Success, including nothing to publish | | | `1` | An error, such as a refused API key, a missing scope, a network failure or a failed build | Read the error line; check scopes with `caplo auth status` | | `2` | A usage error: a missing `--yes`, a workspace given by name with an API key, `--workspace` disagreeing with `--env`, or `channels:write` missing for a channel deploy | Fix the command or the variables | | `3` | A failed gate: validation, tool fixtures, eval cases, or a promotion with no matching release | Fix the files, or publish to the `promoteFrom` environment first | | `130`, `143` | The job was cancelled | Rerun it | A publish that fails partway keeps what it already published, such as tool versions or child agent releases. Fix the cause and run it again; unchanged resources are skipped. See [Scripting](/cli/scripting/) for output formats and environment variables.

# Publish to several environments

> Define staging and production environments in caplo.yaml, vary agent settings per environment, deploy channels, and promote only what passed the previous environment.

An environment is a named workspace that a project publishes to, such as `staging` or `prod`. Keep one workspace per environment so that testing never touches what customers use. With environments, one set of agent files publishes to every workspace, with small per-environment differences, and production can be limited to exactly what staging released. ## Define environments [Section titled “Define environments”](#define-environments) Add an `environments` map to the project’s `caplo.yaml`: 
```yaml
apiVersion: v1
kind: Project
name: shop
agents: agents/*.yaml
tools: tools/*
environments:
  staging:
    workspace: <STAGING_WORKSPACE_ID>
    apiKeyEnv: CAPLO_STAGING_KEY
    channels:
      concierge: [Staging website]
  prod:
    workspace: <PROD_WORKSPACE_ID>
    apiKeyEnv: CAPLO_PROD_KEY
    promoteFrom: staging
    agents:
      concierge:
        model: {temperature: 0.2}
        suggestedReplies: null
    channels:
      concierge: [Website, twilio/Support line]
```
 | Field | Required | Description | | ------------- | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `workspace` | Yes | The workspace ID. A workspace name also works when you are logged in, but an [API key](/cli/authentication/#api-keys-for-automation) needs the ID. | | `apiKeyEnv` | No | The name of an environment variable that holds this environment’s API key, such as `CAPLO_PROD_KEY`. When that variable is set, the CLI uses it instead of `CAPLO_API_KEY`. | | `promoteFrom` | No | Another environment. A publish here only goes ahead for agents that environment already released from the same source. See [Promote a release](#promote-a-release). | | `agents` | No | Agent fields by agent file key, merged over the agent files. See [Vary agents per environment](#vary-agents-per-environment). | | `channels` | No | Channels by agent file key. After a publish, each listed channel is pointed at the agent’s newest release. See [Deploy channels](#deploy-channels). | Environment names start with a lowercase letter and use only lowercase letters, digits and hyphens. `promoteFrom` must name another environment and must not loop back. ## Use an environment [Section titled “Use an environment”](#use-an-environment) Pass `--env` (`-e`), or set `CAPLO_ENV`, on `caplo validate`, `diff`, `push`, `eval` and `publish`: 
```sh
caplo diff --env staging
caplo publish --env prod
```
 Selecting an environment does three things: 1. **Workspace.** The command acts on the environment’s workspace. If `--workspace` or `CAPLO_WORKSPACE` names a different one, the command stops with exit code 2 instead of guessing. 2. **Credentials.** If the environment’s `apiKeyEnv` variable is set, the command authenticates with that key. Otherwise it uses `CAPLO_API_KEY` if set, and your login if not. 3. **Agent fields.** The environment’s `agents` fields are merged over the agent files before anything is compared or pushed. Without `--env` or `CAPLO_ENV`, project commands act on the [selected workspace](/cli/workspaces/) and use the agent files unchanged. ## Vary agents per environment [Section titled “Vary agents per environment”](#vary-agents-per-environment) Under `agents`, each key is an agent file key and each value is a partial agent file. It merges over the file like a JSON merge patch: * Mappings merge key by key, so `model: {temperature: 0.2}` changes only the temperature and keeps the model name. * `null` removes a field, so `suggestedReplies: null` turns suggested replies off in that environment. * Any other value, including a list, replaces the field entirely. Use this for settings that should really differ, such as model, temperature, greeting or limits. Knowledge base and remote MCP server names already resolve in each command’s own workspace, so you rarely need to override them. `caplo validate` checks every environment’s fields merged over each file, whether or not you pass `--env`. With `--env`, it also checks the agents exactly as that environment publishes them. ## Deploy channels [Section titled “Deploy channels”](#deploy-channels) An environment’s `channels` lists, for each agent key, the channels that should serve that agent: 
```yaml
channels:
  concierge: [Website, twilio/Support line, <CHANNEL_ID>]
```
 Name a channel by its name, by its ID, or as `<kind>/<name>` when two channels share a name. Kinds are `website`, `whatsapp`, `messenger`, `instagram`, `twilio` and `telnyx`; `caplo channel list` shows yours. After `caplo publish --env <name>` publishes, it points each listed channel at its agent’s newest release, if the channel does not serve it already. That happens even when this publish made no new release. The plan lists each channel as `channel/<kind>/<name>` with a `deploy` step, and the publish confirmation covers it. New conversations get the new release; conversations already open keep theirs. Every other channel setting stays as it is. The agent must have a release in that workspace. With an API key, deploying channels needs the `channels:write` scope. The CLI checks this before it starts, so a missing scope stops the publish with exit code 2 before anything changes. ## Promote a release [Section titled “Promote a release”](#promote-a-release) `promoteFrom` makes an environment accept only what the previous one released. Each release the CLI publishes from a project records a **source digest** of the agent: * its agent file as written, byte for byte, before any environment’s fields apply * the files of the project packages it uses, as `caplo push` uploads them * the source of its project sub-agents, in the same way `caplo.yaml` and environment fields are not part of the digest, so production can use different settings and still match staging. Any edit to the agent file, a package it uses, or a project sub-agent, even a comment, changes the digest. When you publish to an environment with `promoteFrom`, every agent the publish would release must have a release in the `promoteFrom` environment with the same digest that is not revoked. The plan prints the matching release for each agent. If one is missing, the publish stops with exit code 3 before changing anything, naming the agents that need publishing there first. 1. Publish to staging and test there: 
   ```sh
   caplo publish --env staging
   ```
 2. When staging is good, publish the same commit to production: 
   ```sh
   caplo publish --env prod
   ```
 The plan shows lines such as `agent/concierge matches staging release 1.3.0`. Confirm to publish. 3. If you changed anything in between, publish to staging again first. Production refuses a source staging has not released. To read the `promoteFrom` environment, the CLI uses that environment’s own `apiKeyEnv` key when its variable is set, and otherwise your login. A key for one workspace cannot read another, so when you publish with an API key, the `promoteFrom` environment needs `apiKeyEnv` and that variable must hold a key of its workspace with at least `agents:read`: 
```sh
CAPLO_STAGING_KEY=<STAGING_KEY> CAPLO_PROD_KEY=<PROD_KEY> caplo publish --env prod --yes
```
 Caution Releases are numbered per workspace, so the same source can be 1.3.0 in staging and 2.1.0 in production. Compare environments by source digest, which the plan prints, not by version number. # Install the CLI

> Install the caplo command-line tool on macOS, Linux or Windows, check the download, and keep it up to date.

The `caplo` CLI is a single binary for macOS, Linux and Windows on ARM64 (Apple silicon, Graviton) and AMD64 (Intel, AMD). Every release is published on the [Caplo releases page](https://github.com/getcaplo/homebrew-tap/releases) with a checksum file and a signature. Running tool package fixtures on your machine (`caplo test` and `caplo tool test`) also needs Node.js 24 and the package’s dependencies installed. On Windows those commands run under WSL; everything else works natively. ## Install [Section titled “Install”](#install) * macOS With [Homebrew](https://brew.sh): 
  ```sh
  brew install getcaplo/tap/caplo
  ```
 Or with the install script, which needs no Homebrew and no `sudo`: 
  ```sh
  curl -fsSL https://cli.caplo.si/install.sh | sh
  export PATH="$HOME/.local/bin:$PATH"
  ```
 Add the `export` line to your shell profile (for example `~/.zshrc`) so `caplo` stays on your `PATH` in new terminals. * Linux With [Homebrew](https://brew.sh): 
  ```sh
  brew install getcaplo/tap/caplo
  ```
 Or with the install script. It needs `curl`, `tar` and `sha256sum`; on Ubuntu or Debian install them first with `sudo apt-get install curl ca-certificates tar coreutils`. 
  ```sh
  curl -fsSL https://cli.caplo.si/install.sh | sh
  export PATH="$HOME/.local/bin:$PATH"
  ```
 Add the `export` line to your shell profile (for example `~/.bashrc`) so `caplo` stays on your `PATH` in new terminals. * Windows Windows has no installer. Download the archive and put `caplo.exe` on your `PATH`. 1. Open the [releases page](https://github.com/getcaplo/homebrew-tap/releases) and download `caplo_<VERSION>_windows_amd64.zip` (or `windows_arm64` on an ARM device) and `checksums.txt` from the latest release. 2. [Check the archive](#verify-a-download) against `checksums.txt`. 3. Extract `caplo.exe` to a folder of your own and add that folder to your user `PATH`. In PowerShell, from the download folder: 
     ```powershell
     $dir = "$env:LOCALAPPDATA\Programs\caplo"
     Expand-Archive .\caplo_<VERSION>_windows_amd64.zip -DestinationPath $dir
     $userPath = [Environment]::GetEnvironmentVariable("Path", "User")
     [Environment]::SetEnvironmentVariable("Path", "$userPath;$dir", "User")
     ```
 4. Open a new terminal so it picks up the new `PATH`. Use one installation method. If you install with both Homebrew and the script, two copies end up on your `PATH` and the one that runs depends on its order. ## Check the installation [Section titled “Check the installation”](#check-the-installation) 
```sh
caplo version
```
 It prints the CLI version, the commit it was built from, and the Go version and platform. `caplo --version` prints the version alone, and `caplo version -o json` prints the same details as JSON. Next, [log in](/cli/authentication/). ## Install script options [Section titled “Install script options”](#install-script-options) The script detects your operating system and architecture, downloads the matching archive and `checksums.txt` from the release over HTTPS, checks the archive’s SHA-256 hash, and only then replaces `caplo` in the install directory. It never runs `sudo` and never edits your shell profile. Set these variables on the `sh` side of the pipe: | Variable | Default | Effect | | ------------------- | -------------- | --------------------------------------------------------------------------------------------- | | `CAPLO_VERSION` | `latest` | The release to install, as `vX.Y.Z`, for example `v0.4.0`. Only stable versions are accepted. | | `CAPLO_INSTALL_DIR` | `~/.local/bin` | The directory to install `caplo` into. It is created if missing. | To pin both the script and the CLI to one release, fetch the script from that release’s tag: 
```sh
curl -fsSL https://raw.githubusercontent.com/getcaplo/homebrew-tap/v0.4.0/install.sh \
  | CAPLO_VERSION=v0.4.0 CAPLO_INSTALL_DIR="$HOME/bin" sh
```
 You can also download `install.sh`, read it, and run it yourself. The same script is attached to every release. ## Verify a download [Section titled “Verify a download”](#verify-a-download) The install script and Homebrew check the SHA-256 hash for you. When you download an archive by hand, check it yourself: download `checksums.txt` from the same release into the folder that holds the archive. * macOS 
  ```sh
  shasum -a 256 --ignore-missing -c checksums.txt
  ```
 * Linux 
  ```sh
  sha256sum --ignore-missing -c checksums.txt
  ```
 * Windows 
  ```powershell
  (Get-FileHash .\caplo_<VERSION>_windows_amd64.zip -Algorithm SHA256).Hash.ToLower()
  Select-String "windows_amd64.zip" .\checksums.txt
  ```
 The two hashes must be identical. A matching line ends in `OK`. If the hash does not match, delete the archive and download it again. ### Check the signature [Section titled “Check the signature”](#check-the-signature) Each release also signs `checksums.txt` with a keyless [Sigstore](https://www.sigstore.dev) signature, so you can confirm that Caplo published the checksums and not someone else. Download `checksums.txt.sigstore.json` from the release and verify it with [cosign](https://docs.sigstore.dev/cosign/system_config/installation/): 
```sh
cosign verify-blob checksums.txt \
  --bundle checksums.txt.sigstore.json \
  --certificate-identity-regexp '@getcaplo\.com$' \
  --certificate-oidc-issuer https://accounts.google.com
```
 It prints `Verified OK`. A verified `checksums.txt` plus a matching hash means the archive is the one Caplo released. ## Update [Section titled “Update”](#update) * macOS 
  ```sh
  brew update && brew upgrade getcaplo/tap/caplo
  ```
 If you used the install script, run it again. It installs the latest release over the old binary. * Linux 
  ```sh
  brew update && brew upgrade getcaplo/tap/caplo
  ```
 If you used the install script, run it again. It installs the latest release over the old binary. * Windows Download the new archive, check it, and extract `caplo.exe` over the old one. Your login, settings and selected workspace are kept across updates. ## Uninstall [Section titled “Uninstall”](#uninstall) 1. End your session so it stops working on the server too: 
   ```sh
   caplo auth logout
   ```
 2. Remove the binary: `brew uninstall caplo` for Homebrew, or delete `caplo` from the install directory (`~/.local/bin` by default). On Windows, delete the folder that holds `caplo.exe` and remove it from your `PATH`. 3. Optionally delete the configuration directory: `~/.config/caplo` (or `$XDG_CONFIG_HOME/caplo`) on macOS and Linux, `%AppData%\caplo` on Windows, or the directory `CAPLO_CONFIG_DIR` names. See [Authentication](/cli/authentication/#where-the-session-is-stored) for what it holds.

# Work with a project

> Keep agents and tool packages as files in a caplo project, understand caplo.yaml, and choose what each command acts on.

A project is a folder, usually a Git repository, that holds a set of agents and the tool packages they use as plain files. The project commands (`caplo validate`, `diff`, `push`, `test`, `eval`, `publish` and `pull`) read the folder, compare it with a workspace, and create or update what changed. Review changes in pull requests, then publish from your terminal or [from CI](/cli/ci-cd/). ## Create a project [Section titled “Create a project”](#create-a-project) 
```sh
caplo init support
caplo init shop --template summit
```
 `caplo init [dir]` creates the project in `dir`, or in the current directory, which must be missing or empty. The project name defaults to the folder name; set another with `--name`. A name starts with a lowercase letter and uses only lowercase letters, digits and hyphens. | Template | What you get | | ----------------- | --------------------------------------------------------------------------------------------------------------------------------- | | `blank` (default) | One agent with a starter eval case | | `summit` | A sample outdoor shop: a concierge agent with fast routing, three specialist sub-agents, and two tool packages with test fixtures | The `summit` template creates this layout: 
```text
shop/
  caplo.yaml                  the project file
  agents/
    concierge.yaml            one agent file per agent
    gear.yaml
    orders.yaml
    returns.yaml
  tools/
    order-desk/               one directory per tool package
      caplo.yaml              the package's own caplo.yaml
      package.json
      tsconfig.json
      src/
      tests/
    store-stock/
      ...
```
 Each tool package gets `package.json` and `tsconfig.json` from the current tool SDK templates. Run `npm install` in each package before you run its fixtures; `caplo init` prints the commands. To start from an agent that already exists in a workspace, use [`caplo pull`](#pull-an-existing-agent) instead. ## The project file [Section titled “The project file”](#the-project-file) The project’s `caplo.yaml` sits at the root of the folder: 
```yaml
apiVersion: v1
kind: Project
name: shop
agents: agents/*.yaml
tools: tools/*
```
 | Field | Required | Description | | -------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------- | | `apiVersion` | Yes | Always `v1`. | | `kind` | Yes | Always `Project`. This is what tells it apart from a tool package’s `caplo.yaml`. | | `name` | Yes | The project name: a lowercase letter, then lowercase letters, digits and hyphens. Releases published from the project record it. | | `agents` | No | Glob for agent files, relative to the project root. Default `agents/*.yaml`. | | `tools` | No | Glob for tool package directories, relative to the project root. Default `tools/*`. | | `environments` | No | Named workspaces the project publishes to. See [Environments](/cli/environments/). | Unknown fields are an error. Globs must stay inside the project, and they skip hidden files and folders such as `.DS_Store`. A directory the `tools` glob matches is a package only if it contains a `caplo.yaml`; others are ignored. ## Agent files [Section titled “Agent files”](#agent-files) Each agent is one YAML file in the agent YAML format the console exports, with `apiVersion: v2.0.0`. Files with `apiVersion` v1 are refused. See [Agent YAML](/agents/agent-yaml/) for how to write one and the [agent YAML reference](/reference/agent-yaml/) for every field. The file name without `.yaml` is the agent’s **key**, for example `orders` for `agents/orders.yaml`. Keys start with a lowercase letter and use only lowercase letters, digits and hyphens. Other agents in the project link to an agent by its key, and selectors can use it, so renaming the file is a breaking change inside the project. The agent’s `name` field is what customers and the console see. Inside a project, agent files refer to other resources like this: | In the agent file | Refers to | | ---------------------------------- | -------------------------------------------------------------------------------------------------------- | | `subAgents: [{local: orders}]` | The project agent with key `orders` | | `subAgents: [{agentId: <ID>}]` | Any agent already in the workspace | | `tools: [order-desk/lookup_order]` | Tool `lookup_order` of the project package named `order-desk`; `order-desk` alone selects all its tools | | `tools: [crm/find_contact]` | A published tool of the workspace’s remote MCP server named `crm`, when no project package has that name | | `tools: [<PACKAGE_ID>/<TOOL>]` | A tool of any workspace package, by package ID | | `knowledgeBases: [Returns policy]` | The workspace knowledge base with that name, or an ID | A package’s name is the `name` in its own `caplo.yaml`, not its folder name. Names of remote MCP servers and knowledge bases are looked up in the workspace a command acts on, so the same file works in several workspaces. A sub-agent link with `release: latest`, or with no `release`, follows the child’s newest release; see [Sub-agents and routing](/agents/sub-agents-and-routing/). ## How files map to the workspace [Section titled “How files map to the workspace”](#how-files-map-to-the-workspace) The CLI matches project files to workspace resources **by name**: agents by their `name` field and packages by their package name. It never stores workspace IDs in your files. * A name the workspace does not have yet is created on the next push or publish. * A name it has is updated. * Nothing is ever deleted. Renaming an agent in its file therefore creates a new agent and leaves the old one in place. After a publish, `caplo publish --prune` archives agents that an earlier publish of this project created and that the project no longer defines. * If the workspace agent with that name is archived, the command stops. Restore the agent in the console, or rename it in the file. Agent names must be unique in the project, ignoring case. ## Select part of a project [Section titled “Select part of a project”](#select-part-of-a-project) Without arguments, `diff`, `push`, `test`, `eval` and `publish` act on the whole project. Pass selectors to act on part of it: 
```sh
caplo push agent/orders
caplo test tool/order-desk
caplo publish "agent/Shop Concierge" tool/store-stock
```
 | Selector | Selects | | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | | `agent/<KEY_OR_NAME>` | One agent, by file key or by its `name`; a key wins over a name. It brings its project sub-agents and the project packages they use. | | `tool/<PACKAGE>` | One project package, by package name. | `caplo publish` also brings the project agents that link a selected agent at `release: latest`, because publishing the child publishes them again. A selector that matches nothing is a usage error. ## Run commands from anywhere in the project [Section titled “Run commands from anywhere in the project”](#run-commands-from-anywhere-in-the-project) Project commands look for the project file in the current directory, then in each parent directory, skipping tool packages’ own `caplo.yaml` files. So you can run them from inside `agents/` or a package folder. To point at a project elsewhere, pass `-C` (`--dir`): 
```sh
caplo validate -C ~/src/shop
```
 ## Check a project offline [Section titled “Check a project offline”](#check-a-project-offline) 
```sh
caplo validate
```
 `caplo validate` checks the project without calling the workspace: * `caplo.yaml` and every package’s `caplo.yaml` * every agent file against the agent schema, and unique file keys and agent names * references to project agents and packages, and the tools an `mcp` package declares * sub-agent link cycles, and each agent’s depth limit: at most `policy.maxDepth` (1 to 4, default 3) links below it * fast routing: at least one sub-agent and `doNotUseWhen` on every link, and, when the file has evals, two cases with `routedBy` per sub-agent * every [environment](/cli/environments/) in `caplo.yaml`, with its agent fields applied Problems are printed with their file and the command exits with code 3. Tools of remote MCP servers are checked against the workspace on `diff`, `push` and `publish`. `diff`, `push`, `test`, `eval` and `publish` run the same checks first and stop on any problem. ## Pull an existing agent [Section titled “Pull an existing agent”](#pull-an-existing-agent) To bring an agent you built in the console under version control: 
```sh
caplo pull "agent/Shop Concierge"
caplo pull agent/concierge ./shop
```
 `caplo pull` writes the agent, every sub-agent it links, and their eval cases as agent files. It also pulls the source of any package they use that the project lacks into the `tools` directory. Agents the project already defines are written to their existing files; new ones get a file named after the agent. The target is the project at the directory you give, or the project above `-C`. If there is none, the CLI creates a new project there, but never inside another project. Links name the exact release the draft pins, because a draft does not record `release: latest`; change them back to `release: latest` if you want parents to follow new child releases. Tools of remote MCP servers stay as `<server>/<tool>`. Caution `caplo pull` overwrites the agent files it writes. Commit or stash local changes first so you can review the difference. Next, see the [day-to-day workflow](/cli/workflow/).

# Script the CLI

> Machine-readable output, exit codes, environment variables, non-interactive use and shell completion for the caplo CLI.

Everything you need to call `caplo` from scripts, Makefiles and pipelines. For a ready-made pipeline, see [CI/CD](/cli/ci-cd/). ## Output formats [Section titled “Output formats”](#output-formats) Commands that show data take `--output` (`-o`) with `table` (the default), `json` or `yaml`: 
```sh
caplo agent list -o json
caplo workspace get -o yaml
caplo version -o json
```
 This covers the `list` and `get` commands, `caplo auth status`, `caplo config list`, `caplo version`, and `caplo workspace api-client` `list`, `create` and `rotate`. With `json` or `yaml`, standard output holds only that document, so you can pipe it straight into `jq`; prompts, warnings and errors go to standard error. Other commands print plain text meant for people. `caplo config get <key>` prints just the value: 
```sh
API_URL=$(caplo config get api-url)
```
 ### Plans as JSON [Section titled “Plans as JSON”](#plans-as-json) `caplo diff`, `caplo push --dry-run` and `caplo publish --dry-run` print their plan as one JSON or YAML document with `-o json` or `-o yaml`. `push` and `publish` accept `-o` only together with `--dry-run`, so the output stays a single document; without it they stop with exit code 2. | Field | Description | | -------------- | ------------------------------------------------------------------------------------------------------------------------------- | | `project` | The project name | | `workspace` | `id` and `name` of the workspace; with an API key the name is the ID | | `environment` | The `--env` environment, if any | | `changes` | `true` if any resource has a step | | `resources` | One entry per package, agent and channel, in the order the command acts on them | | `firstPublish` | Publish only: `true` on the project’s first publish to this workspace | | `promotions` | Publish only, with `promoteFrom`: per agent, the environment it promotes `from`, the `source` digest and the matching `release` | Each entry in `resources` has: | Field | Description | | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | | `resource` | `tool/<package>`, `agent/<key>` or `channel/<kind>/<name>` | | `steps` | What the command does, in order, from `create`, `update`, `save-evals`, `build`, `test`, `evaluate`, `publish`, `archive` and `deploy`; empty when unchanged | | `summary` | The line the table shows | | `files` | A package’s changed files, prefixed `+` added, `-` removed, `~` changed | | `reasons` | Why an agent publishes or is evaluated | | `current`, `next` | The current release or package version, and the release a publish makes | | `diff` | A unified diff of the agent’s draft and eval cases | For example, to run a step only when a publish would change something: 
```sh
if caplo publish --dry-run -o json | jq -e '.changes' > /dev/null; then
  echo "Publishing"
fi
```
 ## Exit codes [Section titled “Exit codes”](#exit-codes) | Code | Meaning | | ----- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `0` | Success. | | `1` | An error: the API refused the request, a file could not be read, a build failed, or the command failed in another way. | | `2` | A usage error: an unknown command or flag, a wrong argument, a confirmation that needs `--yes` because there is no terminal, or conflicting settings such as `--workspace` disagreeing with `--env`. | | `3` | A failed check: project validation, tool fixtures, eval cases, a promotion with no matching release, or a failed `caplo identity verify-assertion` check. | | `130` | Interrupted with Ctrl-C. A second Ctrl-C ends the process at once. | | `143` | Ended with SIGTERM. | Errors are printed to standard error as one line starting with `error:`. For a failed validation, each problem is printed above it with its file. ## Environment variables [Section titled “Environment variables”](#environment-variables) | Variable | Effect | | ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `CAPLO_API_KEY` | Authenticate as an API client with this key instead of your login. See [API keys](/cli/authentication/#api-keys-for-automation). | | `CAPLO_WORKSPACE` | The workspace for every command, by ID or name, unless `--workspace` is given. With an API key it must be the ID. | | `CAPLO_ENV` | The project [environment](/cli/environments/) for `validate`, `diff`, `push`, `eval` and `publish`, unless `--env` is given. | | `CAPLO_API_URL` | The API that `caplo auth login` saves, unless `--api-url` is given, and the API an API key calls. | | `CAPLO_ISSUER` | The sign-in server that `caplo auth login` uses, unless `--issuer` is given. | | `CAPLO_CONFIG_DIR` | The configuration directory, instead of the default below. Use a separate one per Caplo login. | | `XDG_CONFIG_HOME` | On macOS and Linux, the configuration directory is `$XDG_CONFIG_HOME/caplo` when `CAPLO_CONFIG_DIR` is not set; otherwise `~/.config/caplo`. On Windows it is `%AppData%\caplo`. | An environment’s `apiKeyEnv` in `caplo.yaml` names one more variable per environment, such as `CAPLO_PROD_KEY`; see [Environments](/cli/environments/#define-environments). ## Run without a terminal [Section titled “Run without a terminal”](#run-without-a-terminal) Commands that change something important ask first: `caplo publish`, `caplo agent publish`, `caplo channel deploy` and `rollback`, `caplo knowledge sync` when it removes documents, release and version revokes, archive, delete and remove commands, and secret unset, unbind and delete. Pass `--yes` (`-y`) to skip the question. When standard input is not a terminal, these commands do not read an answer from it. Without `--yes` they stop with exit code 2, so piping `y` into them does not work. `caplo publish` also requires `--yes` on a project’s first publish to a workspace, even in a terminal. ### Secrets from standard input [Section titled “Secrets from standard input”](#secrets-from-standard-input) Commands that take a secret never accept it as an argument, so it does not end up in your shell history or process list. They read it from a hidden prompt in a terminal, or from standard input otherwise: 
```sh
printf %s "$ORDERS_API_KEY" | caplo secret set orders-api-key
printf %s "$ORDERS_API_KEY" | caplo tool secret set ORDERS_API_KEY -p order-desk
```
 One trailing newline is removed; `printf %s` avoids adding one in the first place. Values are 1 to 8192 bytes. Remote MCP server credentials come from standard input or from a named environment variable, for example `caplo mcp add` with `--secret-stdin` or `--secret-env <VARIABLE>`. See [Secrets and egress](/tools/secrets-and-egress/) and [Remote MCP servers](/tools/remote-mcp/). API keys work the other way round: `caplo workspace api-client create` and `rotate` print the new key on standard output once, so you can pipe it into a secret store. With `-o json`, the key is in the `secret` field. ## Shell completion [Section titled “Shell completion”](#shell-completion) `caplo completion` prints a completion script for `bash`, `zsh`, `fish` or `powershell`. To try it in the current shell: 
```sh
source <(caplo completion zsh)
```
 To load it in every new zsh session, add that line to `~/.zshrc`. For bash, install the `bash-completion` package and save the script once: 
```sh
# macOS with Homebrew
dir="$(brew --prefix)/etc/bash_completion.d"
caplo completion bash > "$dir/caplo"


# Linux
caplo completion bash | sudo tee /etc/bash_completion.d/caplo > /dev/null
```
 For fish, run `caplo completion fish > ~/.config/fish/completions/caplo.fish`. For PowerShell, add `caplo completion powershell | Out-String | Invoke-Expression` to your profile. Homebrew installs do not set up completion for you. The [CLI reference](/reference/cli/#caplo-completion) lists the options.

# Build, test and publish a project

> The everyday caplo loop for a project, from validating files to publishing releases bottom up, and what each step changes in the workspace.

This page walks through the loop you repeat while building a [project](/cli/projects/). Every command below acts on the whole project unless you pass [selectors](/cli/projects/#select-part-of-a-project) such as `agent/orders` or `tool/order-desk`, and on the [selected workspace](/cli/workspaces/) unless you pass [`--env`](/cli/environments/). ## The loop at a glance [Section titled “The loop at a glance”](#the-loop-at-a-glance) 1. **Edit** agent files and tool code in your editor. 2. **Validate** offline with `caplo validate`. 3. **Test tools** locally with `caplo test`. 4. **Review** the difference from the workspace with `caplo diff`. 5. **Push** drafts with `caplo push`, then try the agent in a test chat. 6. **Evaluate** the drafts with `caplo eval`. 7. **Publish** releases with `caplo publish`. 8. **Pull** changes someone made in the console with `caplo pull`, when needed. Steps 2 to 4 change nothing in the workspace. Steps 5 and 6 change only drafts, which customers never see. Only step 7 creates releases. ## Validate [Section titled “Validate”](#validate) 
```sh
caplo validate
```
 Checks schemas, references, link cycles, the sub-agent depth limit, fast routing rules and every environment, without network access. It exits with code 3 and lists each problem with its file. The other project commands run the same checks first. See [Check a project offline](/cli/projects/#check-a-project-offline). ## Test tool packages [Section titled “Test tool packages”](#test-tool-packages) 
```sh
caplo test
caplo test tool/order-desk -v
```
 Runs each selected package’s fixtures on your machine, the same way as `caplo tool test`: it bundles the package like the Caplo builder and runs the fixtures in Node.js 24. It calls no workspace. Run `npm install` in each package first. A failing fixture exits with code 3; `-v` also prints log lines for passing fixtures. See [Test tools](/tools/testing/). ## Review the difference [Section titled “Review the difference”](#review-the-difference) 
```sh
caplo diff
caplo diff agent/concierge -o json
```
 Compares each package’s files with its workspace draft, and each agent file and its eval cases with the agent’s draft and eval suite. It prints a plan, one line per resource, and a unified diff for each changed agent. A new agent is shown against nothing. With `-o json` or `-o yaml`, it prints the plan as one document that a pipeline can post on a pull request; see [Scripting](/cli/scripting/#plans-as-json). ## Push drafts [Section titled “Push drafts”](#push-drafts) 
```sh
caplo push
caplo push --dry-run
```
 `caplo push` prints the plan, then: 1. Uploads each changed package as its workspace draft and builds it, streaming the build log. 2. Saves each agent file as its agent’s draft, children before parents, creating any agent the workspace does not have. 3. Saves each agent’s `evals` as its eval suite. An agent file without an `evals` key leaves the suite alone. Nothing is published. `--dry-run` prints the plan and diffs and stops. If nothing changed, push says so and does nothing. Caution A push replaces the workspace draft with your file. Edits someone made to that draft in the console since your last push are overwritten. Pull them first with `caplo pull` if you want to keep them. ### Try it in a test chat [Section titled “Try it in a test chat”](#try-it-in-a-test-chat) 
```sh
caplo agent chat "Shop Concierge"
```
 This opens a private test conversation with the agent’s draft in your terminal; you can also use the console’s test chat. A test conversation runs linked sub-agents from their **releases**, not their drafts, so a sub-agent you have never published cannot answer yet. Push tells you when that is the case and names the `caplo publish agent/<key>` that releases it. See [Test an agent](/agents/testing/). ## Evaluate [Section titled “Evaluate”](#evaluate) 
```sh
caplo eval
caplo eval agent/concierge
```
 Pushes the selection like `caplo push`, then runs each selected agent’s eval cases against its saved draft in isolated test conversations and prints the result of every case. A grader model also judges each case’s `desiredOutcome`; a failed case prints its rationale, and a case it could not grade counts as failed. If a passing run already exists for the same draft and eval cases, it is reused instead of run again. It exits with code 3 when any case fails or a selected agent has no eval cases. See [Evals](/agents/evals/) for how to write cases. ## Publish [Section titled “Publish”](#publish) 
```sh
caplo publish
caplo publish agent/orders --dry-run
caplo publish --yes
```
 `caplo publish` validates the project, works out what needs releasing, prints the plan with diffs, and asks `Publish to workspace <name>? [y/N]`. Then it publishes **bottom up**: 1. **Tool packages.** Each package that changed or has an unpublished build is pushed, built, tested with its fixtures in the workspace’s test runner, and published as a new version. 2. **Child agents.** Each sub-agent’s draft is saved, pinned to the package versions just published, its eval cases run, and it is published as a release. 3. **Parent agents.** Each parent’s draft is saved pinned to its children’s new releases, evaluated and published, until the top of the project. Every agent it publishes needs at least one eval case, and every case must pass. If a step fails, publishing stops there; what was already published stays published. ### What gets a new release [Section titled “What gets a new release”](#what-gets-a-new-release) An agent is published when any of these is true: * its file or eval cases differ from the workspace * its saved draft has never been published * a project package it uses publishes a new version, or its packages have newer versions than its release * a project sub-agent it links at `release: latest` publishes a new release An agent whose eval cases alone changed since its release is evaluated against the new cases and **keeps** its release, because a release does not include eval cases. Everything else is left unchanged and shown as `unchanged` in the plan. The plan shows each new version. A first release is 1.0.0. After that, changing the model or provider, changing sub-agent links, or removing a tool or knowledge base is a major bump; adding one is a minor bump; anything else is a patch. A new child release forces a major bump of its parents. ### Confirming [Section titled “Confirming”](#confirming) | Situation | What happens | | --------------------------------------------------------------- | ----------------------------------------------------------------------------- | | A terminal, after the project’s first publish to this workspace | The CLI asks; answer `y` to publish | | `--yes` (`-y`) | Publishes without asking | | No terminal, such as CI, without `--yes` | Stops with exit code 2 | | The project’s first publish to a workspace, without `--yes` | Stops with exit code 2, even in a terminal, so you review the full plan first | `--dry-run` prints the plan and stops. Add `-o json` to get the plan as a document. ### Clean up removed agents [Section titled “Clean up removed agents”](#clean-up-removed-agents) 
```sh
caplo publish --prune
```
 Agents are never deleted when you remove their file. `--prune` adds an `archive` step to the plan for each agent that an earlier publish of this project created and that the project no longer defines, and archives them after publishing. It works on the whole project only, so it takes no selectors. Archived agents can be restored in the console. ## Pull console changes [Section titled “Pull console changes”](#pull-console-changes) 
```sh
caplo pull "agent/Shop Concierge"
```
 Writes the agent’s current draft, its sub-agents and their eval cases back into the project files, so you can commit changes made in the console. See [Pull an existing agent](/cli/projects/#pull-an-existing-agent). ## Next [Section titled “Next”](#next) * Publish to staging and production from the same files: [Environments](/cli/environments/). * Run this loop in a pipeline: [CI/CD](/cli/ci-cd/). * Every flag of these commands: [project command reference](/reference/cli/project/).

# Choose a workspace

> List, create and select workspaces with the caplo CLI, and control which workspace each command acts on.

Every command that reads or changes agents, tools, channels or knowledge acts on one workspace. The CLI remembers a selected workspace, and you can override it per command or per shell. For what a workspace holds and what each role can do, see [Workspaces and roles](/concepts/workspaces-and-roles/). ## List and inspect [Section titled “List and inspect”](#list-and-inspect) 
```sh
caplo workspace list
caplo workspace get
caplo workspace get "Acme Support"
```
 `caplo workspace list` shows each workspace you belong to with your role, its status and its ID; the selected one is marked with `*`. `caplo workspace get` shows one workspace, by default the selected one. Both take `-o json` or `-o yaml`. ## Select a workspace [Section titled “Select a workspace”](#select-a-workspace) 
```sh
caplo workspace use "Acme Support"
```
 You can name a workspace by its exact name or its ID. If two of your workspaces share a name, use the ID. The selection is saved in your [CLI configuration](/cli/authentication/#cli-settings) and applies to every later command. You rarely need to select one by hand: `caplo auth login` keeps your previous selection if you still belong to it, and selects your only workspace if you belong to exactly one. Changing the `api-url` setting clears the selection. ## Create a workspace [Section titled “Create a workspace”](#create-a-workspace) 
```sh
caplo workspace create "Acme Staging"
```
 You become its Owner, and the CLI selects it. Invite teammates in the console under **Settings**, **Members**. ## Which workspace a command uses [Section titled “Which workspace a command uses”](#which-workspace-a-command-uses) For each command, the CLI takes the first of these that is set: 1. The `--workspace` (`-w`) flag, for one command: `caplo agent list -w "Acme Staging"`. 2. The `CAPLO_WORKSPACE` environment variable, for every command in that shell or CI job. 3. The workspace selected with `caplo workspace use`. Project commands that take `--env` use the [environment’s](/cli/environments/) workspace instead. If `--workspace` or `CAPLO_WORKSPACE` names a different workspace, the command stops with a usage error (exit code 2) rather than guess which one you meant. Unset `CAPLO_WORKSPACE`, or set it to exactly the value in `caplo.yaml`, when you use environments. ## With an API key [Section titled “With an API key”](#with-an-api-key) When `CAPLO_API_KEY` is set, the workspace is always the key’s own workspace, and you must name it by ID with `--workspace`, `CAPLO_WORKSPACE` or an environment. A name is refused because a key cannot list workspaces. The `caplo workspace` commands themselves need a person’s login. See [API keys for automation](/cli/authentication/#api-keys-for-automation). API clients are managed under `caplo workspace api-client`; that is covered on the [authentication page](/cli/authentication/#create-a-client).

```sh

```
 Starts a private test conversation with the agent’s saved draft, or with a release named by –release, and reads one message per line from standard input. Each reply is printed with the sub-agents and tools the turn used. End with Ctrl-D, /exit, or /quit; the test session is closed when the chat ends. A write awaiting a decision is shown as its review, as a review of the whole plan, or as a write that can only be declined: one with no review here, or one waiting for the customer to sign in. /confirm or /cancel decides the write shown last, as the widget’s buttons do; ordinary text never approves a write. If the write changed meanwhile, the current one is shown to answer again, and a refused (409) message or decision is reported without ending the chat. A message or decision that was not sent makes the command exit 1 at its end; without a terminal, a failed turn makes it exit 3. Replies arrive on the agent-test event stream. It resumes after the last event when it reconnects, reloads the history on a reset, reconnects with a fresh token when asked to reauthenticate, and retries network failures, 429, and 5xx, but not an unknown host, a rejected TLS certificate, or another 4xx. When no test session is free, caplo agent test list and caplo agent test close free one. **Examples** 
```sh
caplo agent chat "Shop Concierge"
caplo agent chat "Shop Concierge" --release 2.1.0
printf 'Where is order 1042?\n/confirm\n' | caplo agent chat "Shop Concierge"
```

Other files are skipped, and so are hidden files and directories. –approve waits for extraction and approves the directory’s documents, which skips reviewing their extracted text in the console; it needs agents:publish. –publish then publishes a version from the approved documents and waits for it to index. It asks for confirmation before removing documents; –yes skips it. –dry-run prints the changes only. **Examples** 
```sh

```

# caplo mcp

> Connect remote MCP servers and publish their reviewed tools.

Connect remote MCP servers and publish their reviewed tools. 
```sh
caplo mcp
```

 **Commands** * [`caplo workspace api-client`](#caplo-workspace-api-client) * [`caplo workspace create`](#caplo-workspace-create) * [`caplo workspace get`](#caplo-workspace-get) * [`caplo workspace list`](#caplo-workspace-list) * [`caplo workspace use`](#caplo-workspace-use) ## caplo workspace api-client [Section titled “caplo workspace api-client”](#caplo-workspace-api-client) Manage API clients and their keys for CI and automation. 
```sh
caplo workspace api-client
```
 An API client authenticates CI and automation without a person’s login. Set CAPLO_API_KEY to one of its keys and CAPLO_WORKSPACE (or –workspace, or a project environment’s workspace) to its workspace ID, and caplo commands act as the client with its scopes, at CAPLO_API_URL, else the configured API, else production. caplo auth status shows the client and its scopes. A key cannot list workspaces, so a workspace named by name is refused. Scopes: agents:read, agents:write, agents:publish tools:read, tools:write, tools:publish channels:read, channels:write conversations:read, usage:read endpoints:read, endpoints:write A write or publish scope includes its read scope, and a member can grant only the actions their own role holds. A CI publish needs agents:write and agents:publish, and tools:write and tools:publish when the project has packages. An environment that deploys channels needs channels:write, which a publish checks before it starts. Channel commands also read agents, and knowledge commands use the agent scopes. A project environment can name its own key variable with apiKeyEnv; see caplo publish. **Examples** 
```sh

```
 Adds a key to the API client and prints it on standard output, once. The client’s other keys stay active, so CI keeps working while you replace the key; then revoke the old ones with caplo workspace api-client revoke \<client> –except \<new key>. **Examples**
