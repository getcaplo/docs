# Manage API keys

> Create API clients and keys in the console, choose scopes, rotate and revoke keys, and use a key with the caplo CLI.

An **API client** is a workspace identity for CI pipelines and scripts. It is not a member: it has no role and cannot sign in to the console. It can do only what its **scopes** allow, in its own workspace. Each client has one or more **keys**, secret strings that start with `caplo_sk_`; several active keys let you rotate without downtime. Owners, Admins and Developers manage API clients in **Settings** > **API access** (under **Developer**). For using keys from the CLI side, see [Log in and use API keys](/cli/authentication/#api-keys-for-automation). ## Create a client [Section titled “Create a client”](#create-a-client) * Console 1. Open **Settings** > **API access** and select **Create client**. 2. Enter a **Client name** (up to 80 characters) and turn on the **Permissions** it needs. Grant only what the job uses. 3. Select **Create key** and copy the key from **Copy your API key**. * CLI 
  ```plaintext
  caplo workspace api-client create github-deploy \
    --scope agents:write,agents:publish,tools:write,tools:publish
  ```
 The key is printed once on standard output. The key is shown only once. Caplo keeps only a hash of it and cannot show it again, so store it in your CI’s secret store straight away. A client’s name and scopes cannot be changed, and a client cannot be deleted. To change scopes, create a new client and revoke the old client’s keys. ## Scopes [Section titled “Scopes”](#scopes) A write or publish scope includes the read scope of the same resource: `agents:publish` can also read agents. | Scope | Console label | Allows | | -------------------- | -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `agents:read` | **Read agents** | Read agents, drafts, releases and the workspace’s publication requirements; knowledge bases and their documents; eval suites and runs. | | `agents:write` | **Edit agents and knowledge** | Create agents and save drafts; create and change knowledge bases, upload and delete documents; create and save eval suites. | | `agents:publish` | **Publish agents and knowledge** | Run evals; publish and revoke releases and pin their tool versions; archive and delete agents; approve documents and publish knowledge versions; change the workspace’s [agent publication requirements](/admin/workspace-settings/#agent-publication-requirements). | | `tools:read` | **Read tools** | Read tool packages, their files, builds and build logs, versions, test runs and invocation logs; remote MCP servers; the names of package and workspace secrets and where they are bound. | | `tools:write` | **Edit tools** | Create, change and delete packages and their files; install dependencies; start and cancel builds; run remote fixture tests; review the tools of remote MCP servers. | | `tools:publish` | **Publish tools** | Publish and revoke package versions; publish remote MCP server tools; set and remove a package’s own secret values. | | `channels:read` | **Read channels** | Read channels, the release each serves, and widget designs. | | `channels:write` | **Deploy to channels** | Create, change, pause, resume and delete channels; deploy and roll back releases; create, edit and publish widget designs and upload their assets. | | `conversations:read` | **Read conversations** | Accepted, but no Caplo API accepts API keys for conversations yet. | | `usage:read` | **Read usage** | Accepted, but no Caplo API accepts API keys for usage yet. | | `endpoints:read` | **Read endpoints** | Accepted, but no Caplo API uses it. | | `endpoints:write` | **Manage endpoints** | Accepted, but no Caplo API uses it. | agents:publish is broad `agents:publish` lets a key publish agents, and it can also delete agents and turn off the workspace’s eval requirement. Give it only to pipelines that publish, and keep that key in a protected CI environment. No scope covers members, roles, SSO, billing, workspace secrets, integrations or other API clients. Those always need a person. See [What works with an API key](/cli/authentication/#what-works-with-an-api-key) for the CLI commands each scope enables. ### What you can grant [Section titled “What you can grant”](#what-you-can-grant) You can create a client, or add a key to one, only if your role holds every action its scopes grant. For example: * A **Developer** can grant `agents:read`, the tool scopes and `channels:read`, but not `agents:write`, `agents:publish`, `channels:write`, `conversations:read` or `usage:read`. * An **Admin** or **Owner** can grant any scope. This also applies to rotation: a Developer cannot add a key to a client that an Admin created with `agents:publish`. ## Rotate a key [Section titled “Rotate a key”](#rotate-a-key) 1. Add a new key: **Add rotation key** on the client in the console, or `caplo workspace api-client rotate github-deploy`. 2. Replace the old key in your CI’s secret store and check that jobs pass. 3. Revoke the old key. The client’s other keys keep working until you revoke them, so nothing breaks during the switch. ## Revoke keys [Section titled “Revoke keys”](#revoke-keys) In the console, select **Revoke** next to a key. With the CLI: 
```plaintext
caplo workspace api-client revoke github-deploy --key <KEY_ID_OR_PREFIX>
caplo workspace api-client revoke github-deploy --except <NEW_KEY_ID_OR_PREFIX>
caplo workspace api-client revoke github-deploy
```
 The first revokes one key, the second every key but the new one after a rotation, and the third every active key. Anything using a revoked key stops working at once, and a revoked key cannot be restored. Each key in the console shows its prefix, when it was created and when it was last used, so you can find keys nobody uses any more. `caplo workspace api-client list` shows each client’s scopes and active key prefixes. ## Use a key [Section titled “Use a key”](#use-a-key) Set the key and the workspace ID in the environment, and `caplo` commands run as the client: 
```plaintext
export CAPLO_API_KEY=<API_KEY>
export CAPLO_WORKSPACE=<WORKSPACE_ID>
caplo auth status
```
 Name the workspace by its ID, shown in [General settings](/admin/workspace-settings/#general), because a key cannot list workspaces. For pipelines, see [CI/CD](/cli/ci-cd/). Every key creation and revocation is recorded in the [audit log](/operate/audit-log/). ## Related [Section titled “Related”](#related) * [Log in and use API keys](/cli/authentication/) * [CI/CD](/cli/ci-cd/) * [Workspaces and roles](/concepts/workspaces-and-roles/)

# Manage members and roles

> Invite people to a workspace, choose and change their roles, restrict invitations to your domains, transfer ownership, and remove members.

Open **Settings**, then **Members**. Every member can see the list; Owners and Admins invite, change roles and remove people. Each member has one role, and what each role can do is in the [roles table](/concepts/workspaces-and-roles/#members-and-roles). **Role permissions** on the same page shows the full permission matrix. A workspace has exactly one Owner. The Owner role cannot be given by invitation or role change, only by [transferring ownership](#transfer-ownership). ## Invite members [Section titled “Invite members”](#invite-members) 1. Select **Invite member**. 2. Under **Email addresses**, paste up to 50 addresses, separated by commas or one per line, or select **Upload CSV** to read them from the first column of a CSV file. 3. Choose a **Role**: Admin, Builder, Developer, Supervisor, Auditor, Viewer or Billing. 4. Select **Send invitations**. Each person gets an email with a link to sign in and join. An invitation: * Expires after 7 days. **Resend** sends a new link and restarts the 7 days; **Revoke** cancels it. * Must be accepted by someone signed in with that exact email address, verified by their sign-in provider. * Is refused for someone who is already a member or already has a pending invitation. If the workspace [requires SSO](/admin/sso-and-scim/#require-sso), the invitee must sign in through your identity provider to join. With SSO onboarding or SCIM provisioning, people can also join without an invitation; see [SSO and SCIM](/admin/sso-and-scim/). ### Limit invitations to your domains [Section titled “Limit invitations to your domains”](#limit-invitations-to-your-domains) Under **Invitation policy**, enter up to 20 **Allowed email domains**, such as `company.com, company.co.uk`, and save. Invitations to any other domain are then refused. Leave it empty to allow any domain. The policy applies to new invitations, not to members who have already joined. ## Change a member’s role [Section titled “Change a member’s role”](#change-a-members-role) Choose a new role in the member’s **Role** menu and confirm **Change role**. It takes effect on their next action; if you change your own role, your access changes at once. The Owner’s role cannot be changed here. ## Transfer ownership [Section titled “Transfer ownership”](#transfer-ownership) Only the Owner can transfer ownership, and only to an active member. 1. On your own row, select **Transfer ownership**. 2. Choose the **New Owner**. 3. Select **Transfer ownership**. The new Owner gets the Owner role and you become an Admin immediately. The transfer is recorded in the [audit log](/operate/audit-log/). Only the new Owner can transfer it back. ## Remove a member [Section titled “Remove a member”](#remove-a-member) Select **Remove** on the member’s row and confirm **Remove member**. They lose access to this workspace; their other workspace memberships are not affected. To remove the Owner, transfer ownership first. Members provisioned by SCIM are suspended rather than removed when your identity provider deactivates them. Suspension revokes their API keys the same way, and restoring the member does not bring the keys back. See [SCIM provisioning](/admin/sso-and-scim/#scim-provisioning). ## Related [Section titled “Related”](#related) * [Workspaces and roles](/concepts/workspaces-and-roles/) * [SSO and SCIM](/admin/sso-and-scim/) * [Audit log](/operate/audit-log/)

# Manage workspace secrets

> Create, rotate and delete the workspace secrets that tool packages use, see where each is bound, and know who can manage them.

A **workspace secret** is a credential, such as an API key for your store, that you save once and bind to every tool package that needs it. Rotating it updates every bound package. This page covers managing the secrets themselves; to declare secrets in a package and bind them, see [Secrets and network access](/tools/secrets-and-egress/). Values are write-only. Once saved, neither the console nor the CLI shows a value again, and the [audit log](/operate/audit-log/) records changes without values. ## Who can do what [Section titled “Who can do what”](#who-can-do-what) | Action | Roles | | ----------------------------------------------------------------------------- | ------------------------------------------------------------- | | See the list of workspace secrets and where they are bound | Owner, Admin, Builder, Developer, Supervisor, Viewer, Billing | | Create, rotate and delete workspace secrets; bind and unbind them to packages | Owner, Admin | API keys can list secrets with `tools:read` but cannot create, rotate, delete or bind them. ## Create a secret [Section titled “Create a secret”](#create-a-secret) * Console 1. Open **Settings** > **Secrets** (under **Developer**) and select **Create secret**. 2. Enter a **Name**: lowercase letters, digits and hyphens, starting with a letter, 2 to 64 characters, such as `shop-prod`. 3. Optionally add a **Description** (up to 500 characters) of what it is for. 4. Enter the **Value** (up to 8,192 bytes) and select **Create secret**. * CLI The value is read from a hidden prompt, or from standard input when it is not a terminal, so it never appears in your shell history: 
  ```plaintext
  caplo secret set shop-prod --description "Shop API production key"
  ```
 In a script, pipe it from your secret store: `printf '%s' "$SHOP_KEY" | caplo secret set shop-prod`. A new secret is **Not bound** until you bind it to a package from **Tools**, in the package’s **Secrets** dialog, or with `caplo tool secret bind`. See [Provide the values](/tools/secrets-and-egress/#provide-the-values). ## Rotate a secret [Section titled “Rotate a secret”](#rotate-a-secret) * Console Select **Rotate** next to the secret, enter the **New value**, and select **Rotate value**. * CLI Run `caplo secret set` with the existing name. Without `--description`, it keeps the current description. 
  ```plaintext
  caplo secret set shop-prod
  ```
 Every bound package uses the new value in live calls within a minute. There is no overlap period, so if your provider supports two active credentials, create the new one there, rotate the secret in Caplo, wait a minute, then revoke the old credential at the provider. ## See where a secret is used [Section titled “See where a secret is used”](#see-where-a-secret-is-used) The list shows each secret with **Bound** and the number of package secrets that use it, or **Not bound**, and when it was last updated. For the packages and names behind the count: 
```plaintext
caplo secret list
caplo secret usage shop-prod
```
 ## Delete a secret [Section titled “Delete a secret”](#delete-a-secret) You can delete a secret only when no package secret is bound to it. In the console, select **Delete**: if it is in use, Caplo lists the package secrets to unbind first; otherwise confirm **Delete secret**. With the CLI, `caplo secret delete shop-prod` refuses a bound secret and lists its bindings. Deleting cannot be undone The value is removed for good. Unbinding a package secret first means live calls of tools that need it fail until you set or bind a value again. ## Related [Section titled “Related”](#related) * [Secrets and network access](/tools/secrets-and-egress/) * [`caplo secret` reference](/reference/cli/secret/) * [Manage API keys](/admin/api-keys/)

# Set up SSO and SCIM

> Let your team sign in through your identity provider with OIDC or SAML, verify your domains, require SSO, and provision members with SCIM 2.0.

Workspace SSO lets members sign in to a workspace through your company identity provider instead of Google or an email and password. Everything here is under **Settings** > **Identity & SSO**, and only Owners and Admins can see or change it. On a plan, SSO and SCIM need Enterprise; see [Plans](/billing/). SSO settings belong to one workspace; other workspaces your members belong to keep their own. The usual order is: verify a domain, add and test a connection, activate it, then choose a sign-in policy. ## Verify a domain [Section titled “Verify a domain”](#verify-a-domain) Caplo uses verified domains to route sign-ins and to admit new members through SSO. 1. Under **Organization domains**, enter the exact domain, such as `company.com`, and select **Add domain**. Wildcards are not accepted. 2. Caplo shows a **DNS TXT verification record**. In your DNS provider, add a TXT record at the **Host** shown, `_caplo-verify.company.com`, with the **Value** shown, which starts with `caplo-verification=`. 3. Select **Check verification**. If the record is not visible yet, wait for DNS to update and check again. A domain can belong to only one workspace. Verifying it never grants anyone Admin access. To remove a domain, first take it out of any connection’s **Routing domain**; the last verified domain cannot be removed while SSO is required or SSO onboarding is on. ## Add an identity connection [Section titled “Add an identity connection”](#add-an-identity-connection) A connection is saved as a draft, tested with a real sign-in, then activated. 1. Under **Identity connections**, select **Add connection**, enter a **Connection name** and choose the **Protocol**, **OIDC** or **SAML**. 2. Enter your provider’s details: * **OIDC**: the **Issuer URL** (HTTPS; Caplo reads the provider’s discovery document), the **Client ID** and the **Client secret**. * **SAML**: choose how to give the provider’s metadata: a **Metadata URL**, an uploaded XML file, or **Enter manually** with the **IdP entity ID**, **IdP sign-in URL** and **IdP signing certificate**. 3. Check **Email attribute or claim** and **Display-name attribute or claim** (`email` and `name` by default) and select **Save draft**. 4. Select **Prepare Redirect URI** (OIDC) or **Prepare provider URLs** (SAML), and register what Caplo shows in your provider: the **Redirect URI** for OIDC; the **Assertion consumer service URL**, **Service provider entity ID** or **Service provider metadata URL** for SAML. 5. Select **Test login**, then **Continue to provider**, and sign in through your provider. A successful sign-in marks the connection **Test passed**. 6. Select **Activate**. Caplo stores the client secret encrypted and never shows it again. Your provider must confirm the user’s email address. Editing an active connection creates a replacement draft; the active configuration keeps working until you test and activate the draft, or **Discard draft**. The protocol cannot be changed; create a new connection instead. You can add several connections, for example one per subsidiary. ### Routing options [Section titled “Routing options”](#routing-options) | Option | What it does | | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | | **Routing domain** | **Any verified organization domain**, or one verified domain this connection serves. | | **Redirect when email domain matches** | Sends people whose email domain matches straight to this provider when they sign in to the workspace. It is discovery, not an access rule. | | **Excluded routing domains** | Domains to skip for redirection, such as `contractors.company.com` or `*.partners.company.com`. | | **Hide from the provider choice** | Members reach the provider only through redirection. | | **Show to members linked to another provider** | Whether members who already sign in through another connection see this one. | The **Workspace login link** in [General settings](/admin/workspace-settings/#general) opens this workspace’s sign-in page, with its SSO options, directly. ### Map groups to roles [Section titled “Map groups to roles”](#map-groups-to-roles) **Group-to-role mapping** sets the role of members who join through SSO onboarding from their groups in your provider. Enter pairs such as `support=Supervisor, builders=Builder`. The provider must send the groups in a `groups` claim (OIDC) or attribute (SAML). * Roles are Viewer, Builder, Developer, Supervisor, Auditor and Billing. Owner and Admin are always assigned by hand. * The role is checked again at every sign-in, so a group change in your provider changes the role. * When several groups match, the first role in this order wins: Supervisor, Developer, Builder, Auditor, Billing, Viewer. With no match, the member gets the **New member role**. * Members who joined by invitation or SCIM keep the role you set in **Members**. ## Choose the sign-in policy [Section titled “Choose the sign-in policy”](#choose-the-sign-in-policy) Under **Sign-in policy**, set **Workspace SSO policy**: | Policy | Effect | | ------------ | ------------------------------------------------------------------------------------------------------------------ | | **Disabled** | Members use Google or email and password. Connections cannot be used to enter this workspace. This is the default. | | **Optional** | Members can use company SSO or Google and email and password. | | **Required** | Members can enter the workspace only through an active connection. | **New member onboarding** decides how people join: * **Invitation only** (default): only people you [invite](/admin/members-and-roles/#invite-members) can join. * **Approved SSO onboarding on verified domains**: anyone who signs in through an active connection with a verified email on one of your verified domains joins with the **New member role** (Viewer, Builder or Supervisor) or the role their groups map to. It needs a verified domain, an active connection, and SSO set to **Optional** or **Required**. ### Require SSO [Section titled “Require SSO”](#require-sso) Requiring SSO needs a verified domain, an active, tested connection and **Recovery path confirmed** turned on, and you must check **I understand the sign-in and session impact**. When you save it: * Members signed in with Google or email and password lose access to this workspace at once, Owner included, until they sign in again through your provider. * Existing members keep their roles. * API keys keep working; they do not sign in. Plan for an identity provider outage If your provider is down or misconfigured while SSO is required, nobody can enter the workspace through it. The Owner can lift the requirement: open `https://app.caplo.si/login?workspace=<WORKSPACE_ID>&recovery=1` and sign in with the email and password of their Caplo account, not through SSO. Caplo sets the policy back to **Optional** with **Invitation only** onboarding and records an owner recovery in the [audit log](/operate/audit-log/). This works only while **Recovery path confirmed** is on. ![The Sign-in policy card in Settings, Identity & SSO](/_astro/settings-sso.ByhUM-T2_1amwLG.webp) ## SCIM provisioning [Section titled “SCIM provisioning”](#scim-provisioning) SCIM lets your identity provider add, update and deactivate workspace members automatically. 1. Under **SCIM provisioning**, select **Create token** and copy the **Bearer token**. It is shown once. 2. Turn on **Enable SCIM**. 3. In your identity provider, set the SCIM base URL to the **SCIM 2.0 endpoint** shown, `https://api.caplo.si/v1/identity/workspaces/<WORKSPACE_ID>/scim/v2`, and authenticate with the token as a bearer token. **Rotate token** issues a new token and revokes the old one at once. Turning SCIM off makes the token stop working. ### What Caplo supports [Section titled “What Caplo supports”](#what-caplo-supports) * The **Users** resource, with `POST`, `GET`, `PUT`, `PATCH` (`add`, `replace`, `remove`) and `DELETE`. Groups, bulk operations, sorting and password changes are not supported. * Filters on `userName`, `emails.value` or `externalId` with `eq`, up to 100 results per page. | Attribute | Use | | -------------------------------------------------------------------- | ------------------------------------------------------------- | | `userName` | Required. If `emails` is absent, it must be an email address. | | `emails` | The primary address, or the first one, is the member’s email. | | `name.givenName`, `name.familyName`, `name.formatted`, `displayName` | The member’s display name. | | `externalId` | Your provider’s ID for the user. | | `active` | `false` suspends the member; `true` restores them. | SCIM does not set roles. Provisioned members get the **New member role** when they join; change it later in [Members](/admin/members-and-roles/#change-a-members-role). ### How provisioned users join [Section titled “How provisioned users join”](#how-provisioned-users-join) * A provisioned user becomes a member the first time they sign in through an active connection with that email address. Provisioning alone sends no email. * Provisioned members can enter the workspace only through SSO, even when the policy is **Optional**. Keep the policy at **Optional** or **Required** and at least one connection active. * Deactivating or deleting a user in your provider suspends their membership. Changing their email suspends the old membership. Suspension revokes the API keys the member created, and restoring them does not bring the keys back. * While SCIM is on, SSO onboarding admits only provisioned users. Invitations still work. ### Existing members [Section titled “Existing members”](#existing-members) When your provider provisions an email that already belongs to a member, that member becomes SCIM-managed: from then on your provider can suspend them. Owners and Admins cannot be SCIM-managed; Caplo refuses to provision their email with a conflict error, so leave them out of the SCIM assignment in your provider. ## Related [Section titled “Related”](#related) * [Manage members and roles](/admin/members-and-roles/) * [Workspaces and roles](/concepts/workspaces-and-roles/) * [Audit log](/operate/audit-log/)

# Workspace settings

> Rename a workspace and set its time zone, find its ID and login link, set agent publication requirements, and pause or resume the workspace.

Workspace-wide settings live under **Settings**. Every member can read **General**; Owners and Admins change it. **Workspace controls** is for the Owner only. ## General [Section titled “General”](#general) **Settings** > **General** has three panels. ![Workspace details in Settings, General](/_astro/settings-general.BlLkjf05_VLahS.webp) **Workspace details** | Field | Notes | | ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | **Workspace name** | Up to 80 characters. Shown in the workspace menu and in invitation emails. | | **Workspace timezone** | One of UTC, America/New_York, America/Los_Angeles, Europe/London, Europe/Berlin, Asia/Karachi or Asia/Singapore. It sets the days of the **Overview** date range and the times and date filter of the [audit log](/operate/audit-log/). Billing periods and the Conversations inbox always use UTC. | **Workspace information** * **Workspace ID**: the identifier that `CAPLO_WORKSPACE`, API keys and the SCIM endpoint use. `caplo workspace get` shows it too. * **Workspace login link**: `https://app.caplo.si/login?workspace=<WORKSPACE_ID>`. Share it with your team to open this workspace’s sign-in page directly, with its [SSO](/admin/sso-and-scim/) options. **Open workspace sign-in** opens it. **Agent publication requirements** is described next. ## Agent publication requirements [Section titled “Agent publication requirements”](#agent-publication-requirements) These rules decide what eval results mean when anyone publishes an agent in the workspace. Owners and Admins can change them, and so can an API key with `agents:publish`. | Setting | Choices | Default | | --------------------------------------- | ------------------------------------------------------------------------------------------------ | -------- | | **Eval requirement** | **Required**: all evals must pass. **Disabled**: results do not block publication. | Required | | **Passing routing cases per sub-agent** | 1 to 10: how many passing routed eval cases each direct sub-agent of a fast-routing agent needs. | 2 | Select **Save publication requirements** to apply them. * They apply to every agent in the workspace. There are no per-agent overrides. * Releases already published keep the requirements they were published under. * Platform checks, such as no business action during evals, apply even when the eval requirement is off. For how the gate works, see [Publication requirements](/agents/evals/#publication-requirements) and [Evaluations](/concepts/evaluations/). Caution With **Eval requirement** set to **Disabled**, a release can reach customers without proof that it behaves. Prefer fixing or removing a failing case. ## Pause a workspace [Section titled “Pause a workspace”](#pause-a-workspace) **Settings** > **Workspace controls** (under **Advanced**) holds the emergency switch. Only the Owner can see it. 1. Select **Pause member and API access**. 2. Confirm **Pause workspace**. The badge changes from **Running** to **Paused**. While the workspace is paused: * Caplo refuses requests that need a workspace permission, from members and API keys alike: editing, publishing and deploying agents and tools, reading conversations, and the like. API keys stop authenticating. * Members cannot enter the workspace in the console, and invitations cannot be accepted. * Channels keep serving customers. Pausing the workspace does not stop conversations; to stop an agent answering, pause or turn off its channels. See [Channels](/channels/). To resume, select **Resume workspace** and confirm **Resume workspace**. Everything that was refused works again; nothing is deleted while paused. Pausing locks you out too Once you reload or leave the page, the console can no longer open a paused workspace, even for its Owner, so **Resume workspace** is out of reach. Resume from the same page, or contact [support](/resources/support/) to resume it for you. Pausing and resuming are recorded in the [audit log](/operate/audit-log/). ## Related [Section titled “Related”](#related) * [Manage members and roles](/admin/members-and-roles/) * [Data retention and privacy](/operate/data-and-privacy/) * [Workspaces and roles](/concepts/workspaces-and-roles/)

# Balance and payments

> How the prepaid balance works, which credit is spent first, what happens at zero, and how to add funds, save a card and turn on auto-recharge.

On the Free trial, Standard and Pro, usage is charged to one prepaid balance as it is recorded. It does not roll over. | | **Added funds** | Payments you make with **Add funds**. | 12 months. | | **Auto-recharge** | Automatic payments from your saved card. | 12 months. | | **Promotional credit** | Granted by Caplo. | The expiry shown with it. | | **Adjustment** | Unused plan fee returned when an upgrade costs less than what is left of the current fee. | Does not expire. | Only added funds and auto-recharge pay plan fees. Trial and plan credit pay usage only. ## Spending order [Section titled “Spending order”](#spending-order) Usage spends the credit that expires soonest first. Their usage can take the balance below zero, down to −$1 on the Free trial, −$2 on Standard or −$5 on Pro. Your next payment covers it first. * After the 15 minutes, the agent stops replying in those conversations, and a call in progress ends with the agent’s time-limit warning and goodbye. * Website visitors see “This assistant isn’t available right now. Please try again later.” Messages on WhatsApp, Messenger and Instagram still reach your inbox, but the agent doesn’t reply. * Building, live tests and evaluations keep working. * Adding funds resumes new conversations within about a minute. On the Free trial, an empty balance means choosing a plan. Owners and Billing members are told when the balance falls below $2, or below the auto-recharge threshold, and again when it runs out. ## Add funds [Section titled “Add funds”](#add-funds) You need billing details first: open **Billing details** and add the business or person billed and the billing country. See [Billing details](/billing/receipts-and-invoices/#billing-details). 1. On **Plan & billing**, select **Add funds**. It is available once you are on Standard or Pro. 2. Choose an amount or enter another, from $10 to $500. 3. Select **Add** with the amount. You go to Safepay’s secure page and pay by card, JazzCash or Easypaisa, in US dollars. 4. Back on **Plan & billing**, the console confirms the payment. Funds reach your balance as soon as Safepay confirms it, usually at once. Added funds can be used for 12 months. Unused funds can be refunded within 14 days of adding them; contact [support](/resources/support/) with the receipt number. Caplo takes payments through Safepay for billing accounts in Pakistan. For other billing countries, **Payment method** shows that payments are not available yet; contact [support](/resources/support/). ## Save a card [Section titled “Save a card”](#save-a-card) A saved Visa or Mastercard pays plan renewals that added funds don’t cover, and is needed for auto-recharge. 1. On the **Payment method** card, select **Save a card**. 2. Enter the cardholder’s first and last name and phone number with its country code, such as `+923001234567`. Safepay needs the phone number to save a card. 3. Select **Continue to Safepay** and enter the card on Safepay’s page. Saving a card charges nothing. **Replace card** saves a different one. The billing country can’t change once a card is saved. ## Auto-recharge [Section titled “Auto-recharge”](#auto-recharge) Auto-recharge adds funds from your saved card when the balance falls below a threshold, so agents keep answering. It is available on Standard and Pro with a saved card. 1. On the **Auto-recharge** card, select **Set up**. 2. Turn on **Recharge automatically**. 3. Set **When balance falls below (USD)**, at least $5, and **Add (USD)**, from $10 to $500 and more than the threshold. 4. Optionally set a **Monthly recharge limit (USD)**. Recharging stops for the rest of the calendar month once it is reached. Leave it empty for no limit. 5. Save. The balance is checked about once a minute, after charges are recorded. Each fall below the threshold is recharged once; if the charge fails, Owners and Billing members are told and it is not retried until the balance falls below the threshold again. Each recharge gets a receipt. ## After a payment [Section titled “After a payment”](#after-a-payment) Safepay returns you to **Plan & billing**, which shows the outcome: | Message | Meaning | | -------------------------------------------------- | --------------------------------------------------------------------------------------- | | **Confirming your payment…** | Caplo is waiting for Safepay’s confirmation. | | **Payment received. … is in your balance.** | The funds are added. | | **Payment received. Your plan has changed.** | A plan fee was paid and the plan changed. | | **Payment received, but the plan did not change** | The plan change was no longer allowed. The amount stays in your balance as added funds. | | **Your payment is still being confirmed.** | Safepay hasn’t confirmed yet. The balance updates as soon as it does. | | **The payment did not go through.** | Try again, or pay another way. | | **The payment was cancelled, so nothing changed.** | You left Safepay’s page without paying. | ## Balance activity [Section titled “Balance activity”](#balance-activity) **Balance activity** on **Plan & billing** lists credits added and usage charged, with one line per UTC day of usage. **See charge details** opens the **Charges** tab of [Usage](/usage/usage-and-statements/). ## Related [Section titled “Related”](#related) * [How your bill works](/billing/how-billing-works/) * [Change or cancel your plan](/billing/change-or-cancel/) * [Receipts, statements and invoices](/billing/receipts-and-invoices/)

# Fast decisions

> Turn on OpenAI-powered fast routing for your workspace, see what data it sends, and how agents with sub-agents use it.

Fast decisions let an agent that delegates to sub-agents pick the right sub-agent with one quick decision call, instead of extra rounds of model planning. A routing decision takes about 0.3 seconds instead of about 2 seconds, so customers wait less before the right specialist starts answering. Fast decisions use the OpenAI Decisions API. Because that sends conversation content to OpenAI, it is off until an Owner or Admin accepts OpenAI’s data processing terms for the workspace. After that, each agent still chooses whether to use it. ## What is sent to OpenAI [Section titled “What is sent to OpenAI”](#what-is-sent-to-openai) When an agent uses fast routing, each routing decision sends: * the visitor’s recent messages, and * the descriptions of the agent’s sub-agents (what each one is for, and when not to use it). Agent instructions, tool results, memory and credentials are never sent. Decisions are processed in the United States, the only region offered today. They run on Caplo’s OpenAI account whatever your **OpenAI** key source is under **Integrations** then **Service providers**, and they appear on your bill as Caplo-managed usage. ## Turn on fast decisions [Section titled “Turn on fast decisions”](#turn-on-fast-decisions) 1. In the console, open **Settings** then **AI providers**. 2. In **Fast decisions**, check the **Provider** (OpenAI Decisions API) and **Processing region**. 3. Read the notice about what is sent, then select **I accept the OpenAI data processing terms for this workspace**. OpenAI becomes a subprocessor for routing decisions. 4. Select **Enable fast decisions**. The panel then shows **Enabled**, the terms version you accepted and when the setting changed. The change is recorded in the workspace audit log. Only Owners and Admins can turn fast decisions on or off. Other members see the setting read-only. ## Use fast routing in an agent [Section titled “Use fast routing in an agent”](#use-fast-routing-in-an-agent) Turning on fast decisions does not change any agent by itself. For each agent that delegates to sub-agents: 1. Open the agent’s sub-agent settings and, under **Routing**, choose **Fast routing** instead of **The model decides**. 2. Give every sub-agent link a **Do not use when** description. Fast routing can’t be saved without one on each link. 3. Optionally, under **Advanced**, set **Minimum confidence** (0.60 to 0.99, default 0.85). Below it, the agent’s model decides instead. 4. Publish a release and update the channels that should use it. When a fast decision is not confident enough, or the decision call fails, the agent’s model decides as it would without fast routing, so a conversation is never stuck on routing. See [Sub-agents and routing](/agents/sub-agents-and-routing/) for how to write good sub-agent descriptions and test routing with evaluations. ## Turn fast decisions off [Section titled “Turn fast decisions off”](#turn-fast-decisions-off) In **Settings** then **AI providers**, select **Disable fast decisions** and confirm. Agents set to fast routing fall back to model planning on their next turn, and no data is sent to OpenAI while it is off. Their routing setting is kept, so they use fast routing again if you turn it back on.

# Voice and speech

> How agents hear and speak on voice calls, where to choose speech recognition, voices and realtime models, and what affects the cost of a call.

On a voice call, whether by phone or in the website widget, an agent needs to turn the caller’s speech into text and its own replies into speech. Caplo does this with speech providers and, optionally, a realtime voice model. ## How a voice reply is made [Section titled “How a voice reply is made”](#how-a-voice-reply-is-made) **Speech pipeline** (always used): 1. **Speech recognition** transcribes the caller. 2. The agent’s language model writes the reply, the same way it does in chat. 3. A **voice model** speaks the reply in the chosen voice. **Realtime model** (optional): a realtime voice model writes and speaks each reply itself, so replies start sooner. Speech recognition still transcribes the caller, and the pipeline’s voice still speaks the greeting and the fixed lines such as the transfer and silence messages. ## Providers [Section titled “Providers”](#providers) ![Speech providers on the Service providers page](/_astro/speech-providers.OARBIWDb_z8t8k.webp) * Speech recognition and voice models come from **Deepgram** and **ElevenLabs**, set under **Speech providers**. * Realtime models belong to a language model provider (OpenAI for OpenAI Realtime, Google for Gemini Live) and use its **Language models** key source. Both are in the console under **Integrations** then **Service providers**. Speech providers are **Caplo Managed** by default, so voice works without your own keys. See [Models and providers](/providers/). ## Where to choose them [Section titled “Where to choose them”](#where-to-choose-them) Voice settings belong to the agent, so every channel serving a release uses the same ones. Open the agent’s configuration, then **Advanced settings** then **Voice**: | Setting | What it does | | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | **Voice language** | The language callers speak and the agent answers in. Changing it can replace speech models that do not support the new language; the console tells you when it does. | | **Speech recognition** | The model that transcribes callers. Models are grouped by provider, and each shows the key source its calls use. | | **Key terms** | Up to 50 brand, product and place names callers may say, so recognition writes them correctly. Type a term and press Enter, or paste a list. See [Key terms and pronunciations](#key-terms-and-pronunciations). | | **Voice model** and **Voice** | The model and voice that speak replies. Play a preview of a voice, optionally with your own **Preview sentence**, before you choose. | | **Pronunciations** | How the voice says words it gets wrong: a word, and how to say it written the way it sounds. Play a row to hear it in the chosen voice. | | **Realtime model** and **Realtime voice** | Optional. A realtime model and one of its provider’s voices. | | Fixed lines | What the agent says when it cannot take the call, a turn fails, the call is transferred, the caller is silent or the time limit is near. Leave a line empty to use the platform’s, which Caplo speaks in the voice language: English, or Urdu on Urdu + English calls (the transfer briefing your team hears stays in English). | | **Transcript script** | Rewrites the caller’s transcript into another script, such as Urdu script, before the agent reads it. | | **Start replies early** | Starts the reply while the caller may still be finishing, to answer sooner. | | **Silence check after** and **End call after** | Seconds of caller silence before the silence check line, and before the call ends. 5 to 300 seconds each; the platform defaults are 15 and 10. | Changes apply to new calls after you publish a release and update the channel to it. If you leave voice unset, the agent uses Caplo’s default English speech recognition and voice. Channels decide whether voice is offered: * A phone channel is always voice. * A website channel offers voice only when the channel allows website voice and the entry point’s mode is **Text + voice**. See [Website widget settings](/channels/website-widget/settings/#text-and-voice). ## Key terms and pronunciations [Section titled “Key terms and pronunciations”](#key-terms-and-pronunciations) **Key terms** help speech recognition hear names it does not know. Not every model takes them: | Speech recognition | Key terms | | ----------------------------- | --------------------------------------------------------------------------- | | Deepgram Nova-3 | English on either key source; Urdu + English on your own Deepgram key only. | | Deepgram Flux | English, up to 50 terms. | | ElevenLabs Scribe v2 Realtime | Both languages, up to 50 terms of 20 characters each. | | Deepgram Nova-2 | None. | Deepgram limits how long the terms are in total, so the console shows how much room they use. If the model, language or key source changes to one that cannot take your terms, the console warns you and publishing is blocked until you choose another model or remove them. **Pronunciations** match a word whole and in any case, the longest first where words overlap, and apply to every reply, the greeting and the fixed lines. Replies, captions and transcripts keep the written word. A realtime model speaks its replies itself, so with one set, pronunciations apply to the greeting and fixed lines only. ## What affects cost [Section titled “What affects cost”](#what-affects-cost) A voice conversation can add these charges. See [How your bill works](/billing/how-billing-works/) for how each is billed. | What | Measured in | Billed by | | -------------------------------- | ---------------------------------------------- | ----------------------------------------------------------------------------------------------------- | | Connected call time | Voice minutes, by the second | Caplo platform fee, whatever keys you use. | | Speech recognition | Audio minutes | Caplo on **Caplo Managed**; your provider on **Your key**. | | Key terms | Audio minutes while terms are set | Included in Caplo Managed Deepgram. Caplo on Caplo Managed ElevenLabs; your provider on **Your key**. | | Speaking replies | Characters spoken | Caplo on **Caplo Managed**; your provider on **Your key**. | | Language model or realtime model | Text and audio tokens | Caplo on **Caplo Managed**; your provider on **Your key**. | | Phone carrier | Call time on your own Twilio or Telnyx account | Your carrier. | What makes a call cost more: * **Longer calls**: every connected minute counts, including silence before the call ends. Shorter silence timings end abandoned calls sooner. * **Longer replies**: more characters to speak and more output tokens. Ask for short spoken replies in the agent’s instructions. * **Realtime models**: they bill audio tokens for what they hear and say, on top of the pipeline’s speech recognition. * **Key terms**: Deepgram on your own key and ElevenLabs add a small charge per audio minute while terms are set. Pronunciations are counted as the characters actually spoken. The **Usage** page shows speech to text minutes, text to speech characters and voice minutes by provider, agent or channel. See [Usage and charges pages](/usage/usage-and-statements/).

# Cost reports

> Understand the different cost figures in the console, from model cost estimates in Monitor to billed charges, and how Caplo-managed and your-key costs are separated.

The console shows cost in more than one place, and the figures answer different questions. Use this page to pick the right one and to understand why two figures can differ. | Figure | Where | Answers | Is it what you pay Caplo? | | --------------------------------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- | | **Estimated cost** | **Overview**, and **Conversations** under **Monitor** | Roughly what did the model calls in these conversations cost? | No. | | **Balance activity**, statements and receipts | **Usage & billing** then **Plan & billing** | What was charged to our balance and what did we pay? | Yes, on a plan with a prepaid balance. | | **AI usage** and **Platform** | **Usage & billing** then **Usage**, **Charges** tab | What does a price plan charge, by charge type, agent, channel and model? | Yes, for a workspace billed by a price plan, as an estimate until the month closes. | | Quantities | **Usage & billing** then **Usage**, **Usage** tab | How many tokens, audio minutes, characters and voice minutes did we use? | No prices are shown. | ## Monitor cost estimates [Section titled “Monitor cost estimates”](#monitor-cost-estimates) The **Overview** page has an **Estimated cost** tile, and **Conversations** shows an estimated cost for each conversation and each agent turn, next to its model calls and token counts. These are quick estimates for spotting expensive conversations and agents: * They estimate model calls only, priced from a rate card whose version the tile shows (for example “rate card 2026-10”). * They price every model call the same way, whether it ran on **Caplo Managed** or **Your key**. Each model call in a turn shows which key source it used. * They do not include platform fees, speech or plan credit. * **Partial estimate, some models have no price** means some calls used a model the rate card has no price for. The real cost is higher than shown. * The **Overview** tile is not estimated per channel. Clear the channel filter to see it. The tile says “not billing” for a reason: never reconcile an invoice against these figures. ## Billed cost [Section titled “Billed cost”](#billed-cost) On a plan, what you pay is what was charged to your balance: **Balance activity** on **Plan & billing**, one line per day, and the month’s statement. It covers platform fees for conversations and voice minutes, and Caplo-managed AI and speech at list price with no markup. See [How your bill works](/billing/how-billing-works/). For a workspace billed by a price plan, the **Charges** tab of **Usage** is the figure that matters. See [Usage and charges pages](/usage/usage-and-statements/#charges-tab). It separates: * **Platform**: voice minutes and AI replies, charged whichever key was used. * **AI usage**: Caplo-managed language models and speech, at list price plus the price plan’s markup. Calls on your own keys add no AI usage charge. The **Charges** tab counts how many requests used your keys and which providers, and those providers bill you directly. Group the **Charge breakdown** by **Model** or **Provider** to see where AI usage comes from. ## Caplo-managed and your-key usage [Section titled “Caplo-managed and your-key usage”](#caplo-managed-and-your-key-usage) To compare what runs on Caplo’s accounts with what runs on yours, use the **Usage** tab and set **Keys** to **Caplo-managed** or **Your keys**. Quantities come from what each provider reports, so you can compare your-key usage with the provider’s own usage dashboard. Caplo does not show prices for usage on your keys: your provider’s invoice is the source of truth for that cost. ## Known cost is a lower bound [Section titled “Known cost is a lower bound”](#known-cost-is-a-lower-bound) Caplo counts cost from what each provider reports for each request. Sometimes a report is incomplete: * On the **Usage** tab, a note says how many requests have partial or missing usage from the provider. Their known quantities are included, so totals can rise as reports arrive. * On the **Charges** tab, a note says when Caplo-managed requests used a meter that has no list price yet. Those requests are charged for their priced part only. * In Monitor, a partial estimate means some models have no price. In each case the figure shown is the cost Caplo knows, not more. Treat it as a minimum, and select **Refresh** later for updated numbers. ## Why the figures differ [Section titled “Why the figures differ”](#why-the-figures-differ) If **Estimated cost** in Monitor and what you were charged disagree, the usual reasons are: * Monitor includes calls on your own keys; Caplo charges only Caplo-managed calls. * Charges add platform fees and speech, and on a price plan its markup; Monitor does not. * The two use different price sources: a rate card for Monitor, list prices (and a price plan, where one applies) for charges. ## Related [Section titled “Related”](#related) * [How your bill works](/billing/how-billing-works/) * [Spend budgets](/usage/spend-budgets/) * [Bring your own key](/providers/bring-your-own-key/)

# Spend budgets

> Set monthly budgets for the workspace, an agent or a channel, get email alerts at thresholds, and optionally pause new conversations at the limit.

A spend budget is a monthly limit on what Caplo charges for production conversations, for the whole workspace, one agent or one channel. When charges reach a threshold, Caplo emails your Owners and Billing members. You can also choose to pause new conversations when a budget is reached. Budgets live on the **Spend controls** page, under **Usage & billing** in the console. ## What a budget counts [Section titled “What a budget counts”](#what-a-budget-counts) * Caplo’s charges for production conversations in the current UTC calendar month: platform fees and Caplo-managed AI and speech. See [How your bill works](/billing/how-billing-works/). * Charges before any plan credit or monthly allowance is subtracted, so a budget fills from the first charge of the month. * Not plan fees, Caplo phone number fees, live tests, evaluations or agent building. * Not what your providers bill you for usage on your own keys. Budgets reset on the first day of each UTC month. ## Who can manage budgets [Section titled “Who can manage budgets”](#who-can-manage-budgets) Owners and Billing members can create, change and remove budgets. Admins and Auditors can view them. Every change is recorded in the audit log. ## Create a budget [Section titled “Create a budget”](#create-a-budget) 1. Open **Usage & billing** then **Spend controls** and select **New budget**. 2. Enter a **Name**, for example “Support team”. 3. Under **Applies to**, choose **Whole workspace**, **An agent** or **A channel**. For an agent or channel, choose which one. You can’t change the scope later, and each scope can have only one budget. 4. Enter the **Monthly amount (USD)**. 5. Under **Alert at**, choose one or more thresholds: 50%, 80%, 90% or 100%. 6. Under **When the budget is reached**, choose **Alert only** or **Pause new conversations**. 7. Select **Create budget**. A new budget shows **Not checked yet** until Caplo has compared it with the month’s charges, which takes about a minute. ## Alerts [Section titled “Alerts”](#alerts) Each threshold sends one email per budget per month, to every active Owner and Billing member of the workspace. The **Alert delivery** card lists who receives them, and **Recent alerts** shows the 50 most recent alerts with the amount spent when each was sent. ## Pause new conversations [Section titled “Pause new conversations”](#pause-new-conversations) With **Pause new conversations**, when charges in the budget’s scope reach the monthly amount: * New conversations in that scope are refused. For a workspace budget, that is every channel; for an agent or channel budget, only that agent or channel. * Conversations already in progress continue and finish normally. * The pause lasts until the next month starts, or until you raise the amount, switch the budget to **Alert only** or remove it. * Owners and Billing members get an email saying new conversations are paused, even if you did not choose the 100% threshold. Caution Pausing affects your customers. Charges are checked about once a minute, so the total can go slightly over the amount before new conversations stop, and conversations in progress keep adding charges. Use a lower threshold alert to act before a pause is needed. ## Read the page [Section titled “Read the page”](#read-the-page) The tiles at the top show **Charges this month** (production only), **Forecast at month end** at the month’s pace so far (shown once 10% of the month has passed), **Budgets at risk** and **Alerts this month**. ![The Spend controls page](/_astro/spend-controls.DFzsnlJB_Z1Brw0G.webp) Each budget’s row shows what it has spent this month, its forecast, its thresholds, what happens at the limit and its status: | Status | Meaning | | ------------------- | --------------------------------------------------------------------- | | **On track** | Below the amount and not forecast to reach it. | | **Forecast over** | Below the amount, but forecast to go over by month end. | | **Over budget** | At or over the amount, with **Alert only**. | | **Paused** | At or over the amount, and new conversations in its scope are paused. | | **Not checked yet** | No charges have been compared with this budget yet. | ## Resume or change a budget [Section titled “Resume or change a budget”](#resume-or-change-a-budget) To resume conversations a budget paused, open it with **Edit** and raise the **Monthly amount (USD)** above the month’s charges, or switch it to **Alert only**, then select **Save budget**. New conversations are accepted again once Caplo applies the change, usually within a minute. To remove a budget, open it with **Edit** and select **Remove budget**. Its alerts stay in the history, and any conversations it paused are allowed again. A budget pause is separate from your balance. On a plan with a prepaid balance, new conversations also stop when the balance is used up or the workspace is paused, whatever your budgets say; see [Balance and payments](/billing/balance-and-payments/#when-the-balance-reaches-zero).
